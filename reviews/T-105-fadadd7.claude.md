Findings:
1. manager.py:785-797 with runtime.py `EngineLoop._run`/`_engine_failed`. Non-blocking. Is raising still right? Only partly.
   A boot that raises still stops Core: `reconcile_orphans` raising goes to `_failed()`, then `exit_code = 3`. `booted = True` and the swept keys hold before that exit, which is what the test asserts. So `test_T105_a_line_that_fails_does_not_keep_core_down` (test_settings_sources.py:574) and the commit title overstate it. In the runtime, that raise is Core going down. That would be fine for a one-off, but a registry line never goes away. Compaction keeps every unended line forever, and `ExecPaths(xid)` is built before the alive check (manager.py:833-834). So a line that fails deterministically fails on every start, even after its process is gone. I probed this on the archive copy: a spawn line with `execution_id: "not-an-id"` and a dead pid made `boot()` raise ValueError after `booted`, compaction kept the line, and so the next start would exit 3 the same way. Nothing short of hand-editing run/processes.jsonl ends that.
   Not blocking, because spawn lines carry validated ids and only corruption or a planted line reaches this path. But adoption is different from the reconciles. Nothing in the DB is inconsistent: the execution is already terminal, and a safe fallback already exists. Suggestion: treat a line that cannot be parsed (ValueError/KeyError on its own fields) as not ours. Log it and skip it, as `sweep_mcp_configs` skips a non-id directory. On any other error for a live identity, fall back to `kill_identity`, which never raises, and log at error level instead of returning the error. Keep raising for the reconciles.
2. manager.py:846-851. Non-blocking. Should it kill at once, or adopt and wait out the grace? Kill at once is acceptable.
   The grace exists so that a halt the previous Core asked for can finish through the adapter's stop and collect path. With no adapter (an unregistered harness, or the policy is now a stub) or no row (no stream offset or usage, and nothing to record into), `_orphans` could only end in the same identity kill after waiting. Meanwhile the process would run unsupervised, with its mcp.json already swept from under it. Three small gaps:
   (a) The result of `kill_identity` is ignored, and the warning says "killed" even when `kill_pid_tree` returned False: the process exited in between, or taskkill was refused.
   (b) No end line is written, so the line stays unended in the registry forever. Every later boot and every Core-less e-stop probes it again, and on Linux that adds to the starttime-since-boot exposure of the earlier finding 3.
   (c) On POSIX the kill is one SIGTERM, with no retry until the next boot, so "never left running" holds only on Windows, where it is TerminateProcess. The card already notes the POSIX gap for T-102.
3. Whose process can it kill? (brief)
   - Another Core: excluded. run/core.lock is a real OS lock (`msvcrt.locking`/`fcntl.flock`, infra/discovery.py), one Core per ARCHEUS_HOME, and only `LocalNode.spawn` writes `op: spawn` lines (isolation notes use other ops).
   - A restored backup: backups are DB-only (infra/db/backup.py), so the registry is never restored. A no-row line names a process this home really started. A reused pid on a stale line is excluded by create_time on Windows (FILETIME) and macOS. Linux has the residual starttime-since-boot risk from finding 3 of the earlier review, now with no grace on the no-row path.
   - Another user's process: cannot match an identity unless it is the recorded process, which Core started as its own user. The only exception is the check-then-kill window (ponytail note in proc.py), and taskkill /F without rights fails anyway.
   - A planted line: run/processes.jsonl can be written by any process of the same user, which includes a non-isolated execution. A planted spawn line with no row now makes the next boot taskkill /F /T a same-user process by its real identity. That is not an escalation: the same process could kill it directly, `estop_without_core` already kills every unended line, and isolated executions are not granted run/.
   - taskkill /T descendants are still not identity-checked (earlier finding 4).
4. Not addressed, as the card says: the earlier findings 3-5 (Linux starttime, taskkill /T descendants, isolated orphans against R6-A). One pre-existing edge, out of scope: `keep` is keyed by execution id, not (id, seq). An old-seq process of a live execution that is still running is skipped by adoption and by the reconciles alike.
