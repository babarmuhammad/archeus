1. archeus/harnesses/base.py:323-327 with archeus/core/execution/manager.py:323-330. Blocking.
   Problem: an OSError raised before any child exists now becomes SpawnFailed, and `_spawn` refuses it as `binding`, which is uncharged. The task goes back to READY and is dispatched again, and nothing bounds that. When the failure persists (Core's exec dir not writable, disk full, a path too long under ARCHEUS_HOME, an AV lock), it is re-dispatched on every pass, forever.
   Measured on a git-archive copy of c91d4f1 with a scratch test (deleted afterwards). With the prompt write failing permanently, 4 s of `engine.step` + `manager.tick` produced 70 executions, all ABANDONED, stop_reason `binding`, charged False. The task was still READY with max_attempts 2. In the runtime the loop is tight: `tick()` returns truthy, so ExecLoop never takes its EXEC_S idle wait. Each pass writes an Execution row and its events, an exec dir holding a marker and a tombstone, and, if the MCP opt-in is on, an MCP config holding the opted-in keys, which is written and then dropped.
   Before this commit the same persistent failure raised out of `tick()`. ExecLoop's `except Exception` then stopped Core (exit 3). On restart, `_reconcile_one` read the marker with no pid.json as LOST, which is charged, so the failure stopped after max_attempts. This change turns a loud failure that stopped into a silent one that never stops.
   Canonical conflict: p11-design-gate note 11 (D9) says "`binding` again means only a stale plan binding (§7) or provider terms". It made a workspace that cannot be made a **charged** `stop_reason='workspace'`, because the uncharged version looped 395 times in one run. The manager states the same rule at manager.py:288-293 for the settings inventory: "an uncharged end re-dispatches the task, so a failure that persists would start a new execution on every tick, forever". `_workspace` already charges an OSError from `os.makedirs(ExecPaths(e.id).work)`, which is the same tree base.spawn creates. The owner's O7 decision (PV20-S1-GATE §7, 2026-10-08) makes only an *isolation-establishment* SpawnFailed uncharged, and even that only "under a bounded backoff policy" with a breaker. No such mechanism exists yet. A prompt or marker write failure is not isolation establishment.
   Required change: keep the refusal and the tombstone, but charge a pre-child IO refusal. One way: base.spawn raises a SpawnFailed subclass (or a tagged SpawnFailed) for the OSError branch, and `_spawn` refuses it with `stop_reason='workspace'`. `binding` stays for isolation and O7. Then add a test in which the failure persists and the task ends FAILED after max_attempts, alongside the existing one-shot test (which should still reach ENDED_OK on the second attempt with max_attempts 2). If the implementer wants this uncharged, that extends O7 beyond its decided scope and needs a breaker. It is an owner or Codex decision, so the card should then go BLOCKED BY OWNER and not merge as is.
   Related, pre-existing and not introduced here: a Popen failure (`spawn_detached` returning `(None, err)`, then `_refuse`, then `binding`) loops the same way. A scratch probe gave 63 uncharged ABANDONED executions in 4 s. That is the open O7 breaker work. It needs its own card if it is not folded into the fix above.
2. archeus/core/execution/manager.py:142-167 and boot() at :760-788. Non-blocking, follow-up card.
   Problem: first sight lives only in the in-memory `_procs` entry. It holds across ticks, but nothing survives a Core restart. `boot()` reconciles only non-terminal executions, so a terminal execution's process that is still running (exactly T-102's case) is never adopted and never killed by Core after a restart. `base.sweep_mcp_configs(set(self._procs))` also removes its MCP config while the process still runs. 3. claude_sessions/proc.py:257-288 (pre-existing, shared with `_control`'s STOPPING kill). Non-blocking.
   Is it a tree kill? On Windows, yes: `taskkill /F /T` is forced, and /T walks parent-pid links, so a grandchild whose parent already exited is missed. That is acknowledged by the ponytail comment, and a Job is the real fix. On POSIX the kill is SIGTERM (15) to the process group, not SIGKILL, so a process that "ignores the stop" may ignore that too. When a kill does not take, `_orphans` re-issues it on every pass with `did += 1`, so the exec thread spins without idling (on Windows it spawns a taskkill subprocess per pass). A Windows taskkill that partly fails while the root lives makes `adapter.stop` raise StopRefused, which says "not the process this execution started", and `node.kill` then returns 'gone'. The STOPPING path already behaves the same way, so the commit does not make it worse. Worth a note on the card: "tree kill" holds fully on Windows only.

   The process that "ignores the stop" is simulated by patching `adapter.status` to report 'running'. When the kill is issued, the real fake child has halted and usually exited, so `kill_pid_tree` is a no-op on a pid that is gone. Questions asked:
- Is first sight persisted across ticks? Yes: `p['since']` is in the `_procs` entry. The realistic way in is AWAITING_APPROVAL with the halt still exiting, then a user stop, e-stop or account ceiling discards it. In that state `_watch` → `_control` resets `since` to None on every pass, so the grace starts at first orphan sight. A `since` inherited from a STOPPING, PAUSING or HANDING_OFF timer could only start the grace earlier, never later. I found no path where one of those states turns terminal while its process is still in `_procs` and has not been collected. Across a restart, see finding 2.
- Could it kill a process that is still needed? I found none.
  - Hand-off or PreCompact: `_collect` pops the old process before `record_handoff` ends that execution, and the continuation gets a new execution id.
  - Resume: it reuses the id, but only from PAUSED or AWAITING_APPROVAL, which are live and therefore outside the orphan pass. `_step` sends an AWAITING_APPROVAL execution whose process is still in `_procs` to `_watch`, never to `_resume`, so a resume never overwrites a tracked process.
  - New attempt: a new execution id. `_procs` is keyed by id.
  - PID reuse: `node.kill` checks (pid, create_time) first. The window between the check and the kill is acknowledged in proc.py.
- Double kill or collect race: `_orphans` takes only ids outside this tick's live snapshot, and `_collect` pops the entry. An execution ended by a route thread during a tick goes through `_watch` on that tick and `_orphans` on the next, so it can take a second, idempotent kill. That is harmless. A collected terminal execution returns before `record_end` (`_collect` reloads it, sees it ended, and only releases isolation).
- Is `binding` the right failure class with a retry bound? No, and there is no bound. See finding 1.
