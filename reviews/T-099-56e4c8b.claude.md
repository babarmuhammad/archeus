Review of T-099 at 56e4c8b (detached checkout D:/archeus-p20-mcp, base 853f63f). Read-only on product code. The design holds: putting the drop in `mark_ended`, sweeping at boot after the reconciles and keeping the adopted processes is sound. But `mark_ended` is not the funnel for every end of a process. One end path reproducibly leaves `res/mcp.json` on disk until the next Core boot, and several spawn-failure paths never reach `_refuse`. The commit message claims coverage for both.

Findings:

1. archeus/core/execution/manager.py:115-122 (`tick` walks only non-terminal rows), :153, :693-707 (`_stop_account`); archeus/core/application/executions.py:508-510. Severity Medium.
   Problem: an execution that becomes terminal while its process is still in `_procs` is never collected. `_watch`/`_collect` never run for it, so `LocalNode.ended` and `mark_ended` never run either. Its `res/mcp.json` stays on disk, and so does the missing `ended` tombstone and the stale `_procs` entry, until the next Core boot.
   Concrete scenario: account A has two executions. E2 is AWAITING_APPROVAL: `hook_asked` fires inside `serve_hook` while its CLI is still exiting, and manager.py:153 keeps watching it because "the halt is still exiting". E1's stream reports a limit (manager.py:430-435), or usage crosses the ceiling (manager.py:725). Either calls `_stop_account`, then `X.stop`, then `refuse`, and E2 becomes ENDED_KILLED. The next tick's `_read()` skips E2. Reproduced on a git-archive copy with a probe: drive to AWAITING_APPROVAL with the id still in `_procs`, call `x.manager._stop_account(x.acc, 'ceiling', ...)`, wait for the process to exit, then tick 20 times. Result: `in _procs: True, ended: False, mcp: True`.
   Required change: fix the funnel, not this one path. In `tick`, take every `_procs` id whose execution is no longer live; once its process has exited, call `node.ended(handle, code, seq)` and pop it. That also writes the tombstone and stops the leak. Add a test in the probe's shape. Running the sweep periodically would hide the symptom without fixing the cause.

2. archeus/harnesses/base.py:311/315, :321, :332, :347; archeus/node/isolation.py:1602; manager.py:295. Severity Low (the isolated part is latent while isolated dispatch is off).
   Problem: `flag_argv` writes the file inside `adapter.argv()`/`FakeHarness.start()`, before `base.spawn` runs. These failures after that point never pass through `_refuse` or `mark_ended`:
   - an isolated launch that fails after establishment: `open_inherited` or `api.launch` raises, and `IsolatedLaunch.launch` raises `SpawnFailed('isolation: launch_failed ...')` directly. `_fail` covers establishment only.
   - an OSError while writing the `spawning` marker or the prompt.
   - `AlreadySpawned`.
   The manager catches `SpawnFailed` at :295 and calls refuse plus the isolation release, but does not drop the file. It stays until the next boot. The commit message says spawn failure after the argv was built and "an isolation failure" are covered. That is only partly true.
   Required change: in `base.spawn`, after the `AlreadySpawned` checks, make any exception before a child is returned call `drop_mcp_config(paths)`. Do not call `mark_ended` there, because it would overwrite `_fail`'s isolation tombstone. Leave `AlreadySpawned` for seq > 1 alone, since the file then belongs to process k-1, which may still be running. Add a test: a fake isolation whose launch raises, or a failing prompt write.

3. archeus/harnesses/base.py:516-517. Severity Low.
   Problem: the drop runs only after the tombstone write succeeds. `_refuse` and isolation `_fail` both catch that OSError and carry on, so a failed tombstone write leaves the keys on disk until boot. Separately, the callers skip `mark_ended` entirely when `ended` already exists (local.py:241, isolation.py:919, manager.py:940).
   Required change: `try: _write_json(paths.ended, ...)` `finally: drop_mcp_config(paths)`.

4. tests/v1/integration/test_settings_sources.py:277. Nit.
   Problem: `assert ... ==         ExecPaths(e.id).mcp` is 106 characters with a 9-space gap. A line-continuation backslash was lost (the heredoc trap in CLAUDE.md). It is valid Python and means the same thing.
   Required change: rewrap the line.

The six questions:
1. The funnel holds for the observed exit, which covers stop, cancel, e-stop with Core up, kill and grace timeout because all of them go STOPPING → kill → `_collect` → `LocalNode.ended`. It also holds for the hand-off/PreCompact end (`_collect`; the continuation is a new execution id), reconcile (`_tombstone`/`_collect_gone`), isolation establishment failure (`_fail`) and `spawn_detached` failure (`_refuse`). It does NOT hold for finding 1 or finding 2. On Core shutdown, processes stay detached; the next boot either adopts them (file kept) or reconciles and sweeps them (file removed). Core-less e-stop: confirmed that the next boot removes the file. The "died while Core was down" test is that case: `kill_pid_tree`, then a fresh boot.
2. A resume (same id, seq + 1) rebuilds the argv through `adapter.start` → `flag_argv` every time. `base.spawn` starts process k only after process k-1's `ended` exists, and k-1's drop has run by then.
