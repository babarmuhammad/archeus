VERDICT: CHANGES

Review of T-105, commit 9f057fc (on 438d5ca). Read-only: no product code edited, nothing committed. Tests ran from a `git archive 9f057fc` copy.

The mechanism is right. At boot, `_adopt_orphans` (manager.py:799-821) runs after the live reconciles and before compaction and the MCP sweep. It takes into `_procs` every unended registry spawn whose execution is neither live nor already tracked, provided its process is alive by the recorded (pid, create_time). The existing `_orphans` pass then kills it after `grace_s`, or at once when disarmed, and collects it: tombstone, registry end line, and `mark_ended` dropping `mcp.json`. The sweep exemption follows from `_procs` membership at boot. It ends at collection, because `node.ended` writes the tombstone and drops the config. A process already gone is not adopted, so its config is swept as before. One blocking robustness defect: the new step is outside boot's per-item failure handling, so a single unexpected registry line can stop Core from starting at all.

Findings:
1. archeus/core/execution/manager.py:784 and 817-820. Blocking.
   `boot()` promises "One that fails does not stop the others; the first failure is raised after the sweep". The reconciles are wrapped to keep that promise, but `_adopt_orphans(live)` is not. For an unended line whose process is alive, `rows.get(...)` returns None when the execution row is not in this database, and `.entity` raises AttributeError. `self.registry.get(e.harness_id)` raises KeyError or PolicyStubError when that harness is not registered in this Core.
   Either one leaves boot before `compact_registry`, before `sweep_mcp_configs`, before the registry notes are rewritten, before `_sweep_isolation`, and before `booted = True`. The runtime then stops Core (exit 3, runtime.py `_run`), and every later start fails the same way for as long as that process lives. T-102's premise is a process that never exits, so that can be indefinitely. Keyed MCP configs of other ended executions also stay on disk (D7).
   Probed on the archive copy: a registry spawn line naming an execution id absent from the DB, with a live (pid, create_time), made `boot()` raise `AttributeError("'NoneType' object has no attribute 'entity'")`. `booted` stayed False, and another execution's stale `mcp.json` was not swept.
   Reachable without a bug elsewhere: restoring `archeus.db` from a daily backup (infra/db/backup.py `restore`) while a process started after that backup still runs under the same ARCHEUS_HOME, or a home previously driven by a Core with other executors (dev or test). Before this commit such a line was harmless, because compaction kept it.
   Fix (small): handle each line in its own try/except and fold the error into `failed` like the reconciles. Skip a line whose row is missing, logging it or killing it by identity as `estop_without_core` does. That is the implementer's choice, but boot must not stop. Add a test with a stray line.
2. tests/v1/integration/test_settings_sources.py (T105 tests). Non-blocking, test gap.
   No T-105 test pins that adoption compares against the RECORDED create time. Mutant B6, which builds the handle with the create time read now (identity by pid alone), survived all 20 T099/T102/T105 tests. The code is correct today because it goes through `node.alive` with the line's `create_time`. One test with a line whose `create_time` is altered while its pid is a live process would pin "a stranger holding the pid is neither adopted nor killed".
3. claude_sessions/proc.py:187 (Linux `process_create_time`) with LocalNode.compact_registry (local.py:285). Non-blocking, pre-existing primitive with a wider reach now.
   Identity is sound on Windows: GetProcessTimes gives an absolute FILETIME at 100 ns, plus the STILL_ACTIVE check. It is sound on macOS: libproc gives epoch microseconds. On Linux it is `/proc/<pid>/stat` starttime, which is clock ticks since BOOT. Compaction keeps unended lines forever, including lines whose process died without an end line (this commit leaves a gone orphan "to the compaction", which keeps it). So a line that survives a reboot could in principle match a post-reboot process with the same pid and the same start tick. Boot would then adopt it and kill it after the grace, or at once under the e-stop. The probability is very low, and `estop_without_core` and the live reconcile already share the risk. Folding the boot id or btime into the Linux value would close it. Other BSDs compare `ps lstart` at whole-second resolution.
4. claude_sessions/proc.py:278. Non-blocking, pre-existing, not verified.
   The kill after adoption is `taskkill /F /T`, which selects descendants by recorded parent pid. The root is identity-checked; the descendants are not. A process whose real parent died and whose stale PPID now equals our live pid would be included. That holds unless taskkill itself checks creation order, and I did not verify that. A Job object, the existing ponytail note, is the real fix. On POSIX the kill is SIGTERM to the group, as the card says.
5. manager.py:799-821 against p11 R6-A ("no adoption of a live isolated process at boot"). Non-blocking, latent while isolated dispatch is off, not checked.
   Adoption does not look at `_isolated(e, ...)`. For an isolated ended execution it only terminates and reaps, which R6-A allows. But `_collect` still runs `_tail`/`_progress` over the execution-written stream, and boot's `_sweep_isolation(live)` tears the identity down before the kill. This deserves a sentence on the card, or an explicit isolated branch, before isolated dispatch is enabled.
6. Answers to the brief:
   - Another Core instance: excluded. `run/core.lock` (infra/discovery.py) admits one Core per ARCHEUS_HOME, and a Core on another home has its own registry.
   - A user's process with a reused pid: excluded by the (pid, create_time) check, apart from finding 3 on Linux and the acknowledged check-then-kill window.
   - A live execution is never adopted twice. Mutant B3 is caught.
   - Under the e-stop the first pass after boot kills at once. With grace 60 s, mutant B4 (e-stop ignored) fails the T-105 e-stop test itself, and the fake process is a plain 30 s sleep, so only Core's kill can end it within the test's 15 s.
