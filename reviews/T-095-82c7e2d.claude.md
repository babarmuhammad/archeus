## Judgement by question

1. **The named cause holds.** In b26225a, `freeze()` ran `clock.install()` and registered the `request`/`requestfinished`/`requestfailed` listeners only when a test froze. `cache.ts` `invalidate()` arms a 50 ms `setTimeout` per stream frame (cache.ts:136-148), and `this.timer` stays set while that timer is pending, so a timer armed before the freeze stayed native. It fired in real time after `settle()` had returned, and its read came back after `f0`. The CI log (run 38646019877, job v1-client) is consistent with that, though it cannot prove it. After the test's last `_core_map` reads, the SPA device made one more stream-triggered re-read group (`status`, `digest`, `world/graph` x2), which is the execution rule's invalidation set from tokens/invalidation.json. The log does not show when those reads happened relative to the freeze. I reproduced it independently (see Ran): with b26225a's helpers, a changed `world/graph` answer whose frame arrives 15 ms before `freeze()` gave `f0 0 -> 1` (CI's exact symptom). At 5 ms (and in one 15 ms run) the read had not landed even after `settle(page, 10_000)`, so the same race can fail the test's later check (line 279) instead. With 82c7e2d's helpers, every lead from 5 to 35 ms drew before `f0` (`f0=1`, `f1=1`, parked). **Other causes of the same message:** a real `execution.*` frame that arrives after `f0` and changes what the map draws would still fail line 275, because SSE is real-time and the fix only covers what started before `freeze()`. That residual is small in practice. The test's own `hear(FENCE)` step (line 277-279) shows an execution frame with unchanged live work draws nothing on the live map (no marker or pulse there). SLOW emits no state change until the first attempt ends about 30 s in, and the test passed 5 of 5 here even though, at about 3.2 s per run, SLOW's last `working` emit (about 1 s after RUNNING) very likely lands after the freeze. Not a defect of this commit.
2. **Installing the clock at load does not weaken any `_open` caller.** `_open` is used by 29 e2e files. `freeze()` is called only on pages from `_open` (halo, constellation, marker, motion, now, rows, strip). After `install()`, Playwright's clock runs at real-time rate until `pause_at`, so tests that wait in real time still see the app's timers fire: toast 3.0-6.5 s, arrival 5.1 s, thread/cage/skeleton waits. What changes: (a) timers and frames requested before the freeze now freeze with the page, which makes "nothing moves" checks stricter; (b) after the freeze, `Date.now()`/`performance.now()` sit about 1 s ahead of real time instead of near year 57,760, so the min-interval gates (orbit 5 s, execution and row pulses 2 s) now hold against the attempt's own recent events (strip needed an explicit advance; rows, marker and halo pass unchanged); (c) the clock is per BrowserContext, so the second pages in appearance, inspector_resize and work_menu also get a fake clock running at real-time rate. None of them freeze. (d) Before the freeze, rAF is timer-driven rather than tied to vsync. p18's hidden-page check fakes `document.hidden` and reads the app's `data-graph-loop`, so it never depended on native rAF throttling. I found no test that relied on real time passing *after* a freeze for a timer armed before it. The full e2e run (below) passes.
3. **The seconds/milliseconds bug is confirmed.** The installed Playwright 1.61.0, `playwright/_impl/_clock.py` `parse_time()`: a number is seconds (`int(time * 1_000)`), while `run_for` takes millisecond ticks. The old `pause_at(Date.now()+1000)` therefore jumped about 55,700 years, to about year 57,760. The commit message's "about 57,000 years" is loose but immaterial. The orbit change is a **correct consequence, not a weakening**. `Orbit.frame` gates on `performance.now() - last < ORBIT_EVERY_MS` (orbit.ts:44-45, `now: () => performance.now()` at App.tsx:515). The old jump opened that gate by accident. Now `freeze()` + `settle()` leave the attempt's own turn inside 5 s, so `advance(page, EVERY_MS)` states the precondition explicitly. The "second batch inside 5 s: no turn" and "after 5 s the next batch turns" checks still run against the gate, and now on a realistic clock.
4. **Each of the three mutants fails the regression test as claimed.** I ran them through a reviewer-only pytest plugin that patched `test_spa_p16.watch` and `test_spa_motion.freeze` at collection. The checkout was not edited. Results: clock installed at freeze → `a timer set before freeze ran on its own`; read tracking started at freeze → `DID NOT RAISE <class 'AssertionError'>`; `pause_at` given ms → `a timer set before freeze ran on its own`. The same harness with no mutant passes. `wait()`'s message `timed out: the reads in flight answer` matches `match='reads in flight'`.
5. **No product code changed** (see the file list above). On evidence: the card's "CI's faster Linux run hits the window more often" is a hypothesis, not a measurement. The fix has not run on CI's Linux runner (the card says so: "NOT RUN: Linux/CI"), so the CI failure should not be recorded as gone until a pushed run passes. The motion.py sha256 the card records (484921a6d1b2…) matches the committed file. ruff is clean and `diff --check` is clean, both re-run.

## Findings

1. tests/v1/e2e/test_spa_motion.py:152-158 (low, optional). The timer case has only 500 ms of margin. **Problem:** `setTimeout(…, 1500)` is armed, then `freeze()` jumps 1000 ms from the page's `Date.now()`. **Scenario:** if more than about 500 ms of real time passes between those two `evaluate` round trips (a stalled CI runner), the fake timer comes due inside `pause_at` and the test fails falsely with "a timer set before freeze ran on its own". **Change:** none required. Widening the gap (for example a 5000 ms timer and `advance(page, 4100)`) would remove the flake vector without weakening any of the three mutant kills.
2. tests/v1/e2e/motion.py:40-45 (low, optional). `freeze()` does not insist that `watch()` ran first. **Problem:** nothing checks the precondition. **Scenario:** a future test that builds its own context (as test_spa_loading and test_spa_skeleton already do) and calls `freeze()` without `_open` gets the pre-fix behaviour silently, because Playwright's `pauseAt` installs the clock if needed. It fails loudly (a `KeyError` in `settle`) only if it also calls `settle()`. **Change:** none required. `assert page in _FLIGHT, 'watch() before the page loads'` at the top of `freeze()` would make the misuse loud.
3. tests/v1/e2e/test_spa_motion.py:155 (nit). The ms mutant fails with "a timer set before freeze ran on its own", which names the wrong cause: the timer fired because `pause_at` jumped about 55,700 years. **Change:** none required. A one-line check that `Date.now()` after `freeze()` is within a few seconds of before would pin the unit directly.
4. tests/v1/e2e/motion.py:14,31 (nit). `_FLIGHT` now gets an entry for every `_open` page (about 100 per run) and nothing removes it, so it holds Page and Request objects for the whole session. Harmless at this size. **Change:** none required.
