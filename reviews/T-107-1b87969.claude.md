## Info

1. Races are inherent and fail toward "disarmed":
   - A same-key duplicate in flight can read the sentinel before the original's route clears it, and answer `armed: false` a moment before Core is armed.
   - A concurrent e-stop can make any re-arm answer stale.
   - In both cases the SPA's re-read and the `when` gate show the real state.
2. In the busy shape the committed right-PIN re-arm never reset the strike count, and the replay does not either. Prior wrong PINs still count until the next fresh right PIN. That is the count the device actually earned, so it is correct.
3. In the busy shape the event log carries a `core.rearmed` ("the emergency stop was cleared by a user device") while the sentinel stays set. The same is already true of a Core restart between the commit and `clear_estop`. Nothing derives "armed" from that event (server: sentinel only; `armed_seq` is automations), so it is an audit-wording cost of the owner's decision, not a defect.
