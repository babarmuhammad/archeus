# ADR-0042: Conversational directives resolve into the same governed operations as the controls; mission-scoped narrowing applies, widening and standing changes are confirmed

**Status:** DECIDED (the user's decision pass of 2026-09-30, D-13 and D-16; proposed in the third orchestration pass, `9dc1098`) · **Date:** 2026-09-30 · Implementation: P19.5 Core slice (only the verbs for the commands it already owns: `pause all`, `resume all`, `reprioritise`), P19 (grammar and write path for accounts and harnesses, chat `approve`/`reject` as P16 seam S3, the `route_explanation` card), P21 (answers over live work), P22 (model and location directive kinds) · Extends ADR-0006 and ADR-0015 · Reconciliation: [ARCHEUS_V1_CONVERSATIONAL_ORCHESTRATION.md](../ARCHEUS_V1_CONVERSATIONAL_ORCHESTRATION.md) A1, B1, C2, D4, H2

## Decision

**Conversation is another governed input path, never an elevated one.** The model proposes; Core
validates, authorises and executes a command; the command is the one a control would issue.

1. **Grammar first** (ADR-0006). The deterministic grammar gains verbs whose objects resolve
   exactly: `pause all`, `resume all`, `emergency stop` (with confirmation), `stop <running
   mission>` (one confirmation card doing pause then cancel — no new lifecycle edge),
   `approve` / `reject` bound to the `action_hash` of the card on screen (P16 S3),
   `reprioritise <mission>`, `use <account|harness>` / `don't use <account|harness>` for a named or
   the single active mission, `why <object>`, and `status` / `what is running`. No model is
   called; an object that does not resolve to exactly one thing falls through to the brain.
2. **The brain proposes a `resource_directive`** inside `intent.v1`: its scope, prefer and forbid
   lists (accounts, harnesses, models, locations), a tier requirement, a pin. Core resolves every
   name to a real id; **an unresolved or ambiguous name is a clarification card, never a guess.**
   A user's "strongest / best model" is the top-tier requirement, or a pin when a model is named;
   "cheapest acceptable" is the router's default (the smallest tier meeting the requirement).
3. **Scope and kind decide what happens** — mission-scoped narrowing versus standing policy:

   | Directive | Example | Applies |
   |---|---|---|
   | **narrowing** — removes candidates: forbid an account, harness, model or location; a tighter cost band | "Don't use account A for this." · "Keep this work local." · "Don't use this harness for this task." | to the mission the request creates or continues, at once; on the mission card "from your message", reversible there |
   | **preference** — orders already-eligible candidates, makes nothing eligible | "Use account B for this mission." (B is `normal`) · "Use this model if available." | as narrowing: mission-scoped, shown, reversible |
   | **widening** — makes something eligible that was not: names a `last_resort` / `explicit_only` account (ADR-0041), a pin or `required`, a higher tier or cost band, removes a forbid | "Use the shared account for this." · "Only use model X." | a PROPOSED change card; applied only when a user device confirms |
   | **standing** — outlives the request: project defaults, a ResourcePolicy, a routing rule | "Never use account A again." · "From now on prefer B." | a PROPOSED change card; a user device with the `admin` scope confirms; the brain's principal writes nothing |

   - **"This task" narrows the mission** until task-level preferences exist (V1.x-O2); the card
     says so. Applying a narrowing to the whole mission is stricter than asked, never looser.
   - **An ambiguous scope is read as the least persistent one** (the mission), and the card offers
     "make this standing" — so "don't use account A" never mutates the global policy.
   - Each applied directive records its `message_id` and `intent_id` on the preference or policy
     version it produced.
   - Only a message from a user principal can carry a directive; an automation, an execution or
     fetched text cannot.
4. **What a directive can never bypass.** A directive only adds constraints or preferences to the
   requirement (or, once confirmed, lifts a consumption class). Authorisation, P9 policy,
   project rules, data class (ADR-0035), account `limits`, ceilings and budgets (ADR-0041),
   provider terms (ADR-0021), routing rules, e-stop, verification and review all apply exactly as
   for a command from a control.
5. **State is answered from Core.** "What is running", "what is consuming my accounts" and "why"
   are answered from the live-work and consumption reads (ADR-0043) and the RouteDecision, with the
   `status` and `route_explanation` cards; the brain may paraphrase, the card is the record.
6. **Destructive verbs keep their confirmation and step-up**; text from fetched content, meeting
   notes or agent output is never parsed as a command.
   *As built (P19.5 Core slice, 2026-10-01):* `pause all`, `resume all` and
   `reprioritise <mission> [to] <integer>` are grammar verbs over `Missions.pause_all`,
   `resume_all` and `reprioritise`; a `reprioritise` with no number is answered (asked for it),
   an unresolved mission falls through to the brain, and none calls a model. `emergency stop`,
   `stop <running mission>`, `approve`/`reject` (P19 S3), `use`/`don't use` and `what is
   running` are not part of this slice.
7. **Other modalities feed this pipeline.** A future voice modality produces a user `Message` in
   the same conversation (with its input modality recorded) and goes through the same grammar,
   intent, directive and command path; an approval or a destructive confirmation is never accepted
   by voice alone. No second command architecture exists.

## Why

The conversation is the primary interface (the product definition; ADR-0015), yet no
conversational path reaches what the router reads: `intent.v1` has no resource field
(`archeus/core/brain/intent.py:32-59`), a `preference` becomes a knowledge candidate
(`archeus/core/application/conversation.py:355-385`), and `approve`/`reject`/`reprioritise` are
recognised and declined (`archeus/core/application/grammar.py:26-28`). The asymmetry is what makes
a model-read directive safe: narrowing and preference can only remove or order candidates — they
may block work, never widen authority — while anything that widens use or persists beyond the
request passes through the same confirmation and scope a button would.

## Alternatives

Confirm every directive (rejected: a user who says "don't use the shared account" should not be
asked to confirm a restriction); let the brain write mission preferences directly (rejected: its
principal may only propose); a separate "assistant" command channel (rejected: a parallel system
that bypasses the grammar and cards); a separate voice command grammar (rejected: §7).

## Tradeoffs

A misread narrowing directive can block a mission until the user removes it from the card.
