# ADR-0044: The application theme is a per-client preference — System (default), Dark, Light, High Contrast; thread tints stay tints

**Status:** DECIDED (the user's decision pass of 2026-09-30, D-21) · **Date:** 2026-09-30 · Implementation: P19 (with client unification and the Qt shell attach, S7) · Extends ADR-0017; supersedes the "no app-level appearance setting" of the design system §3.3 and plan Appendix B.3 · Reconciliation: [ARCHEUS_V1_CONVERSATIONAL_ORCHESTRATION.md](../ARCHEUS_V1_CONVERSATIONAL_ORCHESTRATION.md) A10, H4

## Decision

1. **Two application-appearance preferences**, chosen in Control → Appearance:
   - `theme` ∈ `system` (default) | `dark` | `light`;
   - `contrast` ∈ `system` (default) | `standard` | `high`.
   The effective theme is the explicit choice, else the OS (`prefers-color-scheme`,
   `prefers-contrast`). **`forced-colors` (Windows contrast themes) always wins** and cannot be
   overridden; `prefers-reduced-transparency` and reduced motion are followed as before.
2. **The application themes are exactly the V1 token sets**: Archeus Dark, Archeus Light and High
   Contrast (dark and light). **APPLICATION THEME ≠ THREAD TINT**: the 39 legacy palettes remain
   thread tints and are never promoted to application themes; skins and worlds stay uncarried
   (ADR-0017). A further application theme can only be a complete token set passing every contrast
   and ΔE gate, added by amending this record — never generated from a palette.
3. **The preference belongs to the client registration**, not the user profile: it is held in the
   client's own storage, as the motion preference already is (`clients/app/src/surfaces/Control.tsx:605`),
   and is not synced. Appearance belongs to the screen and environment (a phone, a desktop), and V1
   has no user settings store. Consequences per deployment mode:
   - **browser tab and Edge `--app`**: the browser profile's storage for the Core origin; a tab
     and an installed PWA on the same origin share it;
   - **PWA over the tunnel**: its own origin, its own choice;
   - **Qt desktop shell**: the shell uses a persistent QtWebEngine profile (the `QtWebEngine/`
     entry already reserved for it, target-architecture §5) so the choice survives restarts —
     a requirement of S7;
   - if Core had to start on a port other than its default, the origin differs and the client
     shows `system` until chosen again — a stated degrade, never a wrong theme.
4. **First launch is `system`/`system`.** No Core read is needed to apply a theme, so it works
   offline: a `'self'` boot script (the CSP forbids inline script) sets the theme and contrast
   attributes on `<html>` before first paint, and the service-worker-cached shell includes it. The
   Qt shell's pre-load background follows the OS scheme and never hardcodes a dark colour.
5. **Tokens**: one source (`clients/app/tokens/tokens.json`); the generator emits each theme under
   an attribute selector plus the `system` mapping in media queries. No token value changes.
6. **TUI**: keeps its own selection (`--light`, `ARCHEUS_TUI_THEME`), with the same names
   (`dark`, `light`); its default is `dark` because a terminal exposes no OS scheme; it reads no
   SPA preference (P17 §11: the TUI reads no settings file under `ARCHEUS_HOME`).
7. **A theme never changes meaning**: state colours and glyphs are fixed across themes, tints carry
   no meaning (ADR-0017, ADR-0026 §3), and nothing in orchestration reads the theme.

## Why

The user wants to choose Archeus's appearance rather than inherit the OS, across a browser tab, the
Qt shell, Edge and the PWA. The earlier rule came from platform guidance for native apps that sit
inside one OS appearance; Archeus runs in shells (a browser, QtWebEngine, a PWA) whose appearance
the user often cannot set per app, so the OS-only rule removes a choice without buying
consistency. Keeping `system` as the default and `forced-colors` as an override preserves every
accessibility property the rule was protecting. Keeping the palettes as tints preserves why
ADR-0017 exists: one colour must mean one thing.

## Alternatives

OS-only (the previous rule; rejected by the user); all 39 palettes as application themes
(rejected: 39 × every state colour cannot hold the contrast and ΔE floors, the ADR-0017 reason);
a synced user-profile preference (rejected for V1: no settings store, and a phone and a desktop
reasonably differ); a Core-stored per-device preference (rejected: needs a Core read before first
paint and offline).

## Tradeoffs

A choice made in the browser does not follow into the Qt shell or the phone; each client is set
once.
