# ADR-0032: Capability evidence — four classes, method apart from class, task-family scoped, no score

**Status:** DECIDED (direction set by the user's directive of 2026-09-30, clauses D, N–Q, Z; this record resolves O-3, O-5, O-6, O-9 and O-13 of the orchestration reconciliation) · **Date:** 2026-09-30 · Implementation: V1.x-O1 · Reconciliation: [ARCHEUS_V1_ORCHESTRATION_RECONCILIATION.md](../ARCHEUS_V1_ORCHESTRATION_RECONCILIATION.md) §9, §10

## Decision

1. **Four classes.** DECLARED (a provider, catalogue, benchmark publisher, harness descriptor or
   the user says so), OBSERVED (Archeus's own recorded outcomes), INFERRED (a claim promoted from
   evidence by an explicit step), UNKNOWN (insufficient evidence; never penalised, shown as
   "unprofiled").
2. **Method is a separate field** from class: `provider_catalogue | provider_docs | benchmark |
   archeus_outcome | human | legacy_editorial`. The class vocabulary is distinct from the
   relation `confidence_tier` (EXTRACTED/INFERRED/AMBIGUOUS, domain-model §5.2), which is not
   reused.
3. **Task family** is a closed, migration-extendable vocabulary on the task contract
   (`task_family`, planner-proposed, Core-validated): `architecture, planning, coding,
   debugging, testing, code_review, security_review, documentation, research, ui_design,
   verification, summarisation`. When absent it is derived: `code_change` → coding, `research` /
   `inspection` → research, `document` → documentation, `presentation` → ui_design,
   `verification` → verification; subject `review` → code_review; own-call purpose `planner` →
   planning, `knowledge_extraction`/`lesson`/`generation` → summarisation. No claim is about
   "general" quality. Setting a family is not choosing a model: the planner still does not choose
   who does the work.
4. **OBSERVED is a deterministic query over recorded history** — Execution × Verification ×
   Review × RouteDecision — never a write to knowledge (domain-model §1.1). Only executions whose
   served model is SERVED or BILLED (ADR-0031 clause 6) count; attribution uses recorded ids
   only; verifier ERROR is excluded; the model's own summary and self-confidence are never
   inputs. Each observation keeps its context (effort, skills, route kind); summaries group by
   **(model revision, harness version, task family)** and report the context breakdown. A summary
   is *sufficient* at `n ≥ 5` on the current revision and harness version; below that it is
   "too few runs".
5. **INFERRED claims** are KnowledgeItems of a new type **`CAPABILITY`** (added by migration in
   V1.x-O1) with a structured body `{subject {model, revision, harness_version, skills[]},
   task_family, claim, polarity, method, sample, context?}` and the existing provenance and
   lifecycle (CANDIDATE → CONFIRMED → SUPERSEDED/RETRACTED/EXPIRED). Promotion is explicit and
   corroboration-gated: **≥ 2 distinct missions** on the same revision and family (the P6 LESSON
   rule; Graphify's gate); the user may confirm or reject; model confidence is never an input.
   An unmatched claim term is stored as `unmapped`, never dropped.
6. **Staleness** is revision-keyed: a new model revision or harness version marks evidence
   gathered on the old one stale (shown, not counted as current). Time decay is post-V1.
7. **DECLARED claims never order or exclude candidates** — including benchmarks, which are dated
   REFERENCE claims about their own task family and are never normalised into a scale.
   DECLARED *facts* (context window, tool support) are catalogue state and remain hard
   requirements in the router's capability and model steps.
8. **No numeric capability score exists anywhere** — not stored, not computed for routing, not
   displayed as a rank.

## Why

A model can be strong in one family and weak in another; only a family-scoped, revision-keyed,
sampled record says which without folklore. Domain-model §1.1 forbids inferring knowledge from
history implicitly, which the query + explicit promotion split satisfies. Graphify mixes label and
method at source; fable-foreman's dated PRIMARY/SECONDARY/OBSERVED matrix and "n/m, never
back-filled" rule show the discipline in practice; Aider's leaderboard record is the shape of an
observation row. The task kinds alone cannot tell architecture from ordinary documents, or
debugging and security review from coding.

## Alternatives

A composite model score (rejected, clause D); claims stored as FACT items (rejected: overloads a
general type and makes evidence queries depend on a convention); a separate claims table
(rejected: duplicates the knowledge lifecycle); a half-life decay now (deferred).

## Tradeoffs

Sample floors mean evidence acts slowly; families may need splitting later (by migration).

## Consequences

Amends domain-model §5.1 (a `CAPABILITY` type in V1.x-O1) and §7.3 (`task_family` on the task
contract), context-and-knowledge §3 (a promotion source). Legacy `MODEL_PROFILES` can never enter
this path (ADR-0031 clause 8).
