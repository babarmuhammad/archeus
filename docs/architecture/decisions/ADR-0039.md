# ADR-0039: Model evaluation is an approved mission over a versioned fixture suite; its evidence is kept apart

**Status:** PROPOSED (the user's directive of 2026-09-30, second orchestration pass, §6, §19; awaiting approval) · **Date:** 2026-09-30 · Implementation: V1.x-O1 · Extends ADR-0031 §4 (EVALUATING) and ADR-0032 §2 (method) · Plan: [ARCHEUS_V1_ORCHESTRATION_PLAN.md](../ARCHEUS_V1_ORCHESTRATION_PLAN.md) C6

## Decision

1. **A suite is versioned repository data:** frozen task contracts over fixture repositories (never
   user code), each with a `task_family` and a deterministic verifier. A suite's verifiers are
   mutation-verified before any result from it is admitted.
2. **A run is a mission** of kind `evaluation`, proposed by the user or an automation and approved
   like any mission (it spends quota), under ordinary policy; every case runs in an isolated
   worktree, is verified and reviewed as usual, and is never merged. A run carries a baseline (an
   APPROVED model on the same suite) and n repetitions.
3. **Results are the ordinary rows** — Execution with served-model provenance, Verification,
   Review — tagged with the suite version; the summary has the leaderboard shape (pass at first and
   second attempt, well-formed output, errors by kind, exhausted context, timeouts, duration, cost,
   model revision, harness version, suite version, date).
4. **Method separates it:** OBSERVED evidence gains `method: archeus_evaluation` beside
   `archeus_outcome`. It is shown apart and never counts toward the workspace sufficiency floor that
   `evidence_order` / `evidence_exclude` require.
5. **An evaluation informs the user; it never moves a model.** EVALUATING → APPROVED stays the
   user's act or a standing rule the user created (ADR-0031 §4). Until a suite has run a model is
   "unprofiled"; nothing is imputed.

## Why

New models must be tested before real work depends on them, and "discovery is not authorisation"
(ADR-0031) needs a safe way to earn trust. A fixture suite is reproducible, contains no user code,
and uses the verification Archeus already trusts; keeping its evidence apart stops a synthetic
benchmark from standing in for how a model does on the user's own work. Aider's leaderboard gives
the record shape, ponytail the baseline-and-repetitions method, fable-foreman the "bounded recon,
never routing to an unevaluated seat" rule.

## Alternatives

External benchmark scores as evaluation (rejected: DECLARED claims about their own tasks,
ADR-0032 §7); evaluating on the user's live missions (rejected: exploration traffic, ADR-0033);
automatic approval after a passing run (rejected: newer ≠ trusted without the user).

## Tradeoffs

Suites must be written and kept current; a run costs quota the user approves.

## Consequences

Amends ADR-0032 §2 (method vocabulary) and reconciliation §12 (evaluation mission concretised). No
new state machine: an evaluation is a mission; its cases are tasks.
