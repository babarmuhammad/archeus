# ADR-0036: Availability is a per-offer state with one reason, separate from routing status; "executable" is the router's answer

**Status:** PROPOSED (the user's directive of 2026-09-30, second orchestration pass, §3, §12–§14; awaiting approval) · **Date:** 2026-09-30 · Implementation: a C-22 defect slice (offers from configured providers), P22 (derivation, probes, read split) · Plan: [ARCHEUS_V1_ORCHESTRATION_PLAN.md](../ARCHEUS_V1_ORCHESTRATION_PLAN.md) A3, C3, D1

## Decision

1. **Two axes, never merged.** *Routing status* (ADR-0031: CATALOGUED → EVALUATING → APPROVED;
   RETIRED) says whether the user trusts a model for real work. *Availability* says whether an
   offer (harness × account × model) can run now. Neither implies the other and the UI shows both.
2. **An offer exists only where an account can address the model.** A model the catalogue knows
   but no configured provider serves is a catalogue row, never an offer. For pi the configured set
   is pi's own `getAvailable()` answer (`pi --list-models`), cached by harness version and its
   config files' mtimes; for Claude Code and Codex a registered account; for a provider proxy its
   `/v1/models`. Offer ids are the harness's vocabulary (`provider/id` for pi), with declared facts
   (context window) carried.
3. **The state is the first failing rung, with its reason:** configured (`NOT_CONFIGURED`) →
   enabled (`DISABLED`) → harness installed and serving the subject (`HARNESS_UNSUPPORTED`) →
   credentials (`AUTH_REQUIRED`) → reachable without inference (`HEALTH_CHECK_FAILED`) → capacity
   (`UNAVAILABLE`, with `until`) → `AVAILABLE`, qualified *unproven* or *served <date>* from the
   last SERVED/BILLED record. Each state carries `reason` and `since`.
4. **CAPABILITY_UNSUPPORTED and EXECUTABLE are subject-relative** and are never stored: they are
   the router's `capability`/`model` eliminations and its preview result for a subject.
5. **One pure derivation, two readers.** `offer_state(offer, snapshot)` is a function of the
   snapshot the router already takes; the router's `installed`, `health` and `model` steps use it,
   and the read API returns it. A client renders the state and reason and computes neither.
6. **Probes.** A no-inference reachability probe runs automatically only against endpoints the
   user configured in a harness's own config (GET, no redirects, short timeout, untrusted
   response); the account auth probe runs periodically as well as at registration. An inference
   probe is automatic only for `price: 0` self-hosted offers; for a metered offer only by the
   user's action or inside an approved evaluation (ADR-0039).
7. **The read never mixes the two lists.** `/v1/models` returns catalogue rows and offers
   separately; `/v1/harnesses` returns offers with their state, never the catalogue.

## Why

pi ships a table of 1,354 models from 39 providers; V1 offered all of them (plus two ids from its
history) to the router and the UI, while pi itself reports one runnable model
(`archeus/harnesses/calls.py:161-172`, C-22). Availability was a boolean nobody computed, so the
list a user saw and the list the router could elect were the same wrong list. fable-foreman's
"signed in is not usable" and its probe ladder, OmniRoute's reasoned model lockouts and its
"idle ≠ broken", and pi's own `getAll()`/`getAvailable()` split each state the same principle: an
answer about availability needs a reason and a source.

## Alternatives

A stored `available` flag per offer (rejected: a flag without a reason cannot explain itself, and
a second store drifts from the router); computing availability in the client (rejected: P19 — no
logic in clients); filtering pi's catalogue by provider names found in `models.json` alone
(rejected: re-derives pi's auth rules and will drift from them); billable liveness pings of every
offer (rejected: spends the user's money without consent).

## Tradeoffs

A `pi --list-models` spawn per cache miss (bounded by the cache key); an offer can be AVAILABLE
yet unproven until it first serves work.

## Consequences

Amends resource-router §2 (offers from configured providers only; availability derived) and §3,
domain-model §8.3 (ModelOffer availability fields), state-machines §9 (a note: account health is
one input of offer state), ui-architecture §4.6 (Resources shows states and reasons; route
preview is where "executable" is shown). Recorded here as consequences of ADR-0031's user-override
rung, pending the user's decisions D-4/D-5: a user-declared tier and facts for a self-hosted model;
`location` refined to `this_node | self_hosted | remote`.
