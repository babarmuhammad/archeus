# ADR-0038: Four control modes for orchestration acts, all existing mechanisms; a material substitution asks

**Status:** PROPOSED (the user's directive of 2026-09-30, second orchestration pass, §8, §14; awaiting approval) · **Date:** 2026-09-30 · Implementation: the mapping is documentation now; the substitution rule in V1.x-O2 (before any cross-provider fallback can occur) · Plan: [ARCHEUS_V1_ORCHESTRATION_PLAN.md](../ARCHEUS_V1_ORCHESTRATION_PLAN.md) C4, C9, C12

## Decision

1. **Every orchestration act has exactly one of four modes, and each is an existing mechanism:**
   - *automatic* — P9 `ALLOW` / `ALLOW_WITHIN_BOUNDARY`; account `fallback: allow`;
   - *suggested* — a PROPOSED object the user accepts (the brain's principal may propose, never
     approve: mission proposal, PROPOSED plan, knowledge proposal, automation proposal);
   - *requires approval* — P9 `ASK` (plan, task, action, route Approvals); `fallback: ask`;
   - *forbidden* — P9 `DENY`, the locked floor, `forbidden_*`, data class (ADR-0035),
     `fallback: deny`.
   No fifth mode and no orchestration-specific approval object is added.
2. **The acts are mapped once** (plan C9): routing among same-provider eligible offers is
   automatic; routing-status moves are the user's (or a standing rule the user created); proposing
   an evaluation, an architecture-first plan, a rule or a pin is suggested; running an evaluation
   or a metered probe requires approval; enabling an evidence or escalation rule is the user's
   alone; a data-class violation is forbidden.
3. **A material substitution requires approval.** A fallback candidate that differs from the
   original selection in *provider*, *location* (`this_node` / `self_hosted` / `remote`) or is a
   *lower tier* is treated as `fallback: ask` even where the account says `allow`, for every
   subject including own calls; the Approval names both offers and why the first is unavailable.
   Same provider, same location, same-or-higher tier keeps `allow`.

## Why

The directive asks that the user see and control what Archeus intends, and that Archeus never
silently substitute a materially different capability. The modes already exist in P9, the
fallback modes and the proposal states; naming them per act makes the boundary inspectable
without a parallel approval system. Today's `fallback: allow` is safe only because one provider
routes; the moment a local or proxy offer can stand in for a remote one, `allow` would swap
provider, data location and capability class with a single log line.

## Alternatives

A new "orchestration approval" entity (rejected: duplicates Approval); leaving substitution to
`fallback: allow` (rejected: silent capability change); asking on every fallback (rejected: breaks
the existing same-provider rotation the user relies on).

## Tradeoffs

More approvals once several providers are configured; a standing rule can pre-approve a named
substitution pair.

## Consequences

Amends resource-router §7 (the substitution rule inside `fallback_or_block`) and reconciliation
§19 (the mode per act). The decision records the original selection's provider, location and tier
so the rule replays.
