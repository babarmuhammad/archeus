# ADR-0050: A future assistant layer (voice, desktop presence, proactive speech) is a client and a modality of the existing conversation and mission model, never a second loop, router, memory or approval path

**Status:** DECIDED (the user's answers to XR-11 and XR-10, 2026-10-03: approved with amendments A1–A5 folded into the decision text, A3 replaced by the XR-10 answer) · **Date:** proposed 2026-10-02, decided 2026-10-03 · Implementation: **post-V1**. Deciding this ADR schedules no work and changes no V1 scope. · Register, backlog and phases: [../ARCHEUS_V2_ASSISTANT_LAYER.md](../ARCHEUS_V2_ASSISTANT_LAYER.md); plan §31.5 · Research: [2026-10-external-research.md](../../research/2026-10-external-research.md) §4, §6 · Derived from ADR-0003, 0006, 0007, 0012, 0022, 0035, 0037, 0042 §6–§7, 0043, 0047 §6, 0051

## Context

The long-term direction includes a Jarvis-like assistant on Windows: voice in and out, an
always-present desktop state, spoken notifications, and control of the browser and desktop.
Every external project researched for it implements that by owning its own agent loop, model
choice, tools and memory:
- Huw Prosser's `jarvis-mlx` and `fury-sdk`;
- Browser Use;
- Windows Harness;
- OpenViking;
- AgentMemory.

Fury also executes tool-call markup found in plain model text ("tool-call healing") and compacts
history. Each of those, built into Archeus, would be a second orchestrator beside the mission
model. The decided ADRs already forbid it piecemeal. This record states the whole rule once.
**Archeus borrows useful mechanisms from those projects, not their architectural identity.**

## Decision

1. **Shape.** Archeus remains the underlying system. The assistant layer is made of:
   - clients: the SPA/PWA, the desktop shell, a tray;
   - optional local device components: audio capture, VAD, STT, TTS.

   It owns no mission, plan, task or execution state, and Core stays the single writer
   (ADR-0002).
2. **Speech in** is a user `Message` with its input modality recorded, through the same grammar,
   intent, directive and command path (ADR-0042 §7).
   - An approval or destructive confirmation is never accepted by voice alone.
   - **Activation is push-to-talk.** The microphone opens only on an explicit user act (a
     hotkey or a button), is visibly active while open, and closes when the act ends.
   - An automation or a model never opens the microphone.
   - Nothing is captured between activations.
   - A wake word is **not** part of this decision. It is PV-21, and it needs an explicit
     amendment of this clause before any implementation (XR-10).
3. **Speech out** renders text Core already returned: messages, cards and Attention items. It
   never speaks anything the screen would not show (no hidden reasoning, P16 §18.1 r8).
4. **Interrupting speech stops playback in the client.** It is not a stop verb. A spoken "stop"
   is a user message and goes through the grammar like a typed one. What else, if anything, an
   interruption cancels is XR-8 (open).
5. **Proactive speech** comes only from Attention items and decided automations (ADR-0020). The
   assistant originates no action.
6. **No assistant-side tools.**
   - Browser and desktop control exist only as harness capabilities declared through the
     descriptor (ADR-0037), routed, policy-checked and approved like any other execution
     capability (ADR-0007).
   - Model text is never parsed into a tool call or a command (ADR-0042 §6): no tool-call
     healing.
   - Narrow, typed integrations are preferred over pixel or UI Automation control.
7. **No assistant memory.** Continuity is the conversation and missions. Persistence is Core
   knowledge with provenance (ADR-0012). Archeus does not compact transcripts (ADR-0047 §6).
8. **Speech engines are device components, not routed models.**
   - A local VAD, STT or TTS makes no LLM call. It is configured and versioned, not offered
     through the catalogue (ADR-0031).
   - An engine that sends audio off the device is a provider. It is subject to the data class
     (ADR-0035) and needs its own decision (XR-4 option C).
   - An assistant component never holds a provider credential.
   - Any third-party component runs with telemetry off and verified (XR-9, open).
9. **Provenance.** A voice message records its modality together with the engine and version
   that produced its text. The modality field and its provenance land together or not at all
   (XR-7 decides when).
10. **Nothing speech-related runs in Core** (ADR-0003). Python's standard library cannot capture
    audio on Windows in any case.
11. **Security consequences, named.** The assistant layer introduces:
    - two sensors, the microphone (§2) and screen capture (V2-A5);
    - one new execution surface, desktop input injection (V2-A5).

    Each has a threat-model entry before its phase starts. P20 records them (ADR-0051 §3),
    V2-A5 additionally requires the OS-level sandbox (PV-20), and no assistant component widens
    a policy, an approval or a capability.
12. **Relationship to the phases.**
    - §1–§5 and §7–§10 govern the speech track (V2-A0…A3), and §6 the capability track (V2-A4,
      V2-A5).
    - Each production phase still needs its own decisions and the user's go-ahead (plan §31.5).
    - Research phases (A0a–A0c) add no product code.
13. **Non-goals.** This ADR does not choose:
    - a speech engine (A0a feeds XR-4);
    - a TTS engine (A0b);
    - a shell technology (A0c);
    - the speech placement (XR-4);
    - the interruption scope (XR-8);
    - a capability word (XR-2, XR-6);
    - the telemetry gate (XR-9).

    It does not schedule any phase and changes no V1 scope.

## Why

- The mission model, router, ledger, policy and knowledge lifecycle are what make Archeus
  trustworthy. None of the researched assistants has an approval step, provenance on injected
  context, or one router.
- What the Jarvis demos add is presentation plus narrow integrations, and both sit on top of
  Archeus.
- Push-to-talk keeps §2 unconditional: an always-listening microphone is a different privacy
  posture and gets its own decision (PV-21).

## Alternatives

- **An assistant runtime with its own agent loop** (the Fury / Browser Use shape): rejected. It
  would be a second orchestrator (ADR-0006, 0022, 0043).
- **An opt-in wake word now:** deferred (XR-10).
- **Leave this undecided until voice is scheduled:** rejected, because every proposal would
  re-derive the boundary.

## Consequences

- Voice, tray and desktop work after V1 is client and device work plus small Core additions:
  the message field and its provenance (§9), and capability words via ADR-0037.
- A proposal that needs a new loop, router, memory or approval path has to supersede this ADR
  explicitly.
- A wake word has to amend §2 explicitly.
