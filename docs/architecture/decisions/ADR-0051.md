# ADR-0051: V1 execution isolation is application-level and harness-provided; an Archeus-owned OS-level sandbox is post-V1

**Status:** DECIDED (the user's answer to XR-13, 2026-10-03) · **Date:** 2026-10-03 · Implementation: **P20** verifies the V1 boundary; the OS-level sandbox is **PV-20** (post-V1, required before V2-A5) · Register: [../ARCHEUS_V2_ASSISTANT_LAYER.md](../ARCHEUS_V2_ASSISTANT_LAYER.md) §4 XR-13, §5 PV-13, PV-20 · Reads ADR-0007, ADR-0049, execution-architecture §2, resource-router §3 · **Current status (2026-10-07):** the decision below is historical; PV-20 is now a **V1.x security remediation**, not implemented — see "Current status" at the end of the 2026-10-07 note · **PV-20's own ADR (Decision 5):** [ADR-0053](ADR-0053.md)

## Context

The 2026-10 research (finding F-22, from the harness-engineering corpus) recommends confining
agent executions with an OS-level filesystem and network sandbox plus a credential proxy.

Archeus already decides its execution boundary in two layers (ADR-0007 enforcement (2),
execution-architecture §2):
1. **Application-level, set by Core at spawn:**
   - push and publish credentials removed;
   - the workdir is the task worktree;
   - tool allowlists derived from action classes;
   - limits;
   - the fail-closed per-tool hook;
   - what an execution loads from its settings sources (ADR-0049).
2. **Harness-provided sandboxes:**
   - harnesses classed `sandbox` (Codex `--sandbox workspace-write`, network off unless `web` is
     ALLOW) enforce their boundary themselves;
   - tasks whose policy denies network are routed only to them (resource-router §3).

**The gap:**
- Claude Code's `Bash` network cannot be blocked by Archeus (execution-architecture §2).
- On Windows, nothing below the per-tool hook confines what a Claude Code process can read or
  reach with the user's privileges [inference from §2].
- The Windows mechanisms that could close the gap have not been studied: AppContainer, Job
  objects, Windows Sandbox.

## Decision

1. **P20 does not build an Archeus-owned OS-level sandbox.** V1's execution isolation is the
   application-level boundary plus harness-provided sandboxes, exactly as ADR-0007 and
   execution-architecture §2 specify.
2. **P20 specifies and tests that boundary as built.** At minimum:
   - **Credential removal:** an execution cannot push and finds no push credential.
   - **Workdir:** a `code_change` execution's workdir is its worktree. No `--add-dir` is passed
     today, so no extra path is granted.
   - **Tool allowlists:** execution-architecture §2 specifies Claude Code `--allowedTools` /
     `--disallowedTools` derived from action classes (a task without `exec` gets no `Bash`).
     - **This is not built.** P11's capability-removal section (p11-design-gate §18) lists only
       the environment and credential removal, and the execution `argv()` passes no tool
       allowlist and no `--add-dir` (`archeus/harnesses/claude_code/adapter.py:117-126`).
     - Today the fail-closed hook is the only per-tool gate for Claude Code executions.
     - **Decided 2026-10-03 (XR-14, ADR-0052):** P20 builds tool removal (`--tools` allow-form
       from action classes, `mcp__*` denied, never `--allowedTools`, unmapped tools excluded) and
       tests it as part of this boundary. Analysis:
       [../XR-14_TOOL_ALLOWLIST_BRIEF.md](../XR-14_TOOL_ALLOWLIST_BRIEF.md).
   - **The fail-closed hook:** it denies and halts when Core is down, on a timeout, on an
     unreadable answer and on a crash, in the deny form ADR-0049 decides (exit code 2).
   - **ADR-0049's rule:** the spawn excludes the settings sources it decides, and the execution
     records the inventory of what loaded.
   - **Network:** network-denied tasks are routed only to `sandbox` harnesses, and a Claude Code
     execution is never chosen for one.
   - **The sentinel:** it halts hook-enforced executions, and the registry kill stops sandbox
     harnesses.
3. **P20's threat model names the gap explicitly.**
   - The OS-level confinement Claude Code executions lack on Windows.
   - **Future sensors and surfaces**, none of which exist in V1:
     - the microphone (V2-A1);
     - screen capture (V2-A5);
     - desktop input injection (V2-A5).

     They are recorded so the threat model does not have to be reopened when V2 starts.
4. **The application boundary and an OS sandbox are different boundaries and stay named
   separately.**
   - The application boundary decides *what Archeus lets an execution do*: policy, action
     classes, approvals, the hook.
   - An OS sandbox would decide *what the process can physically reach* whatever the agent
     attempts.
   - Neither substitutes for the other, and no document may describe V1 as OS-sandboxed.
5. **An Archeus-owned OS sandbox is PV-20.**
   - Its design needs its own ADR, informed by the PV-13 study of the Windows mechanisms.
   - It is required before V2-A5 (desktop control) reaches production, and it is considered
     for V2-A4 (browser).
   - It may come earlier as V1.x if P24's audit finds the gap a release blocker. That would be
     a new decision, not this one.

## Note — 2026-10-07: the acknowledged V1 limitation vs. the PV-20 security property

The P20 verification pass (slice G) confirmed, with read-only probes, that the §3 OS-confinement
gap is **reachable in practice**: a Claude Code execution runs with the user's OS identity and so
keeps the user's reach into user-owned credential authorities (finding G1, Critical) and the local
Core control boundary — the privileged local token and `run/` state (finding G2, Critical). These
are **OS-boundary findings, not P11 implementation defects**: P11's environment hygiene
(`CAPABILITY_ENV`) functions exactly as designed, but the material sits in stores the OS identity
owns, which clearing an environment variable cannot remove. The separate network-egress gap
(finding G3, Medium) is **P23's**, not this ADR's.

The two boundaries this ADR names apart (Decision 4) must therefore be read as two different
statements, and this note keeps them apart on the record:

- **What V1 acknowledges as a limitation (Decision 1).** V1's isolation is the application-level
  boundary plus harness-provided sandboxes. Under it, a Claude Code execution is **not** OS-confined
  on Windows: it retains the user's identity and the reach that comes with it. ADR-0051 accepted
  this for V1 and routed the fix to PV-20. G1 and G2 are the concrete, evidenced form of that
  accepted limitation — they are **not** a regression and **not** a P11 bug.
- **What the PV-20 remediation must establish (Decision 5), and does not yet.** An execution's OS
  identity must not be the user's, and must not be able to reach any user-owned secret or
  privileged local state that would defeat an Archeus boundary — and, as a **hard requirement in
  its own right** (not merely defence in depth), Core must refuse an execution the **effects** those
  secrets would produce — every member of the closed privileged-effect set of PV-20 §3.6, which is
  the canonical list (publishing/pushing; privileged Core control; approving any pending request,
  including the execution's own; policy modification; re-arm after a halt; authoring halt, pause,
  handoff or approval state) — whatever the execution has reached. This is a
  **required security property, not a present fact**; it is claimed only when PV-20 is implemented
  and its acceptance evidence passes. No document may describe V1 as having it.

**PV-13 is the prerequisite study and is now delivered** (2026-10-07,
[../pv13-windows-os-confinement-study.md](../pv13-windows-os-confinement-study.md)): it recommends
**AppContainer as the primary identity/ACL boundary wrapped in a Job object**, with a
**separate standard user** as the escalation path, and disqualifies Windows Sandbox as a V1.x
baseline (unavailable on Windows Home, heavy per-execution startup). **PV-20's design is prepared**
([../pv20-execution-isolation-design.md](../pv20-execution-isolation-design.md)) as a **design
decision, not an implementation authorization.** P20's acceptance forbids an open Critical and
defines no accepted-Critical state. Slice G is **paused, not closed**. *(Later the same day: PV-20's
remaining architecture decisions were approved and recorded in [ADR-0053](ADR-0053.md); see
"Current status" item 8.)*

As-built corrections also recorded 2026-10-07 (the gate is the detail): Decision 2's tool-allowlist
bullet is no longer "not built" — slice F built it (ADR-0052, `--tools` allow-form, `mcp__*`
denied, `--allowedTools` never); and the fail-closed hook's deny/halt form is E/O4's (a halt is
exit 0 with `continue:false` **and** a `permissionDecision:deny`; exit code 2 is the deny and the
guarded fallback), which refines Decision 2's "exit code 2" wording.

### Current status (2026-10-07, after the user's PV-20 rulings)

This status does not rewrite the decision above; it records where it stands now.

1. **Historical V1 decision.** V1 did not have an Archeus-owned OS sandbox (Decision 1). That
   remains the record of what V1 decided.
2. **Current evidence.** That acknowledged limitation produced two Critical findings, G1
   (credential reach) and G2 (local Core control reach) — p20-design-gate §12 items 92–97. The
   acknowledgement in Decision 1 does **not** make them acceptable; both are open.
3. **PV-13 recommendation.** AppContainer as the primary isolation mechanism, wrapped in a Job
   object; separate standard user as the escalation path; Windows Sandbox not the baseline.
4. **PV-20 decisions** (PV-20 §6). The baseline is AppContainer + Job object; Core effect-bounding
   is a hard requirement; there is no silent fallback to the user's security context; PV-20 is a
   **V1.x security remediation** (this is the §5 "new decision", now taken).
5. **PV-20 is not implemented,** and no implementation is authorised.
6. **The required security property is not demonstrated.** The PV-13 capability/ACE spike was
   attempted on 2026-10-07 and **did not complete**; the capability/ACE model is **DESIGN PROPOSAL —
   UNVERIFIED**, and AppContainer is **neither proven nor disproven** (PV-20 §7.3).
7. **G remains PAUSED and NOT CLOSED,** because ADR-0051 §2 is not satisfied as built and P20's
   acceptance forbids an open Critical. G1 and G2 stay open until PV-20 is implemented and its
   acceptance evidence passes.
8. **PV-20's own ADR is written (Decision 5): [ADR-0053](ADR-0053.md).** It records the mechanism
   rulings above and the owner's six approved PV-20 decisions (R1 OS-attested execution origin,
   R3 Core-brokered provider access, R4a a separate execution repository imported as data, R4b a
   confined verification identity, R5 Core-authoritative halt state with untrusted hook reports,
   R6 Core-only Job ownership). It is an architecture decision only: **implementation is not
   started and not authorised**, and the empirical AppContainer, Claude CLI and transport evidence
   is outstanding. Items 5–7 are unchanged by it.
9. **The PV-20 blocker decisions are recorded in ADR-0053 §7 (2026-10-07).** Among them, **A4
   changes this ADR's harness-provided-sandbox posture (Context item 2, Decision 2):** every
   execution a production Core dispatches, whatever its harness, runs under the PV-20 execution
   identity inside a Core-held Job. A harness's own sandbox (Codex `--sandbox`) is an inner layer,
   never a substitute; a harness that cannot launch inside the PV-20 identity is not eligible for
   production dispatch; no harness has an exception. The network-denied routing rule of Decision 2
   becomes inner defence; egress stays P23's. Nothing is implemented, and items 5–7 are unchanged.

### Superseding decision — timing (2026-10-07, the PV-20 evidence review)

This block supersedes **timing** and nothing else. Decision 1 and Decision 5 stand verbatim as the
historical record of what was decided on 2026-10-03; history is not rewritten here.

- **What is superseded:** the timing stated in this ADR's title and status header — "an
  Archeus-owned OS-level sandbox is **post-V1**", "PV-20 (post-V1, required before V2-A5)" — and
  Decision 5's "It may come earlier as V1.x if P24's audit finds the gap a release blocker. That would
  be a new decision, not this one." **The words are kept as written**; the ruling they describe is no
  longer the ruling, and it lives here instead.
- **Ruled:** OS confinement is a **V1.x security remediation**. PV-20 is therefore a V1.x security
  remediation, not a post-V1 item, and it is not deferrable on the ground that it is larger than the
  remaining P20 work.
- **The contingency Decision 5 described is discharged:** the "new decision" it anticipated has now
  been taken (PV-20 §6.4). It does not wait on P24's audit.
- **Effect boundary, stated canonically:** Core effect-bounding is a **HARD REQUIREMENT**. It is not
  *merely* defence in depth. OS isolation and Core effect-bounding are complementary layers, neither
  substitutes for the other, and both are required (PV-20 §3.3, §3.6). Earlier, contextual uses of
  "defence in depth" elsewhere in these documents describe prior reasoning and are not withdrawn —
  no document should be read as claiming that wording has disappeared.
- **Unchanged:** G stays **PAUSED and NOT CLOSED**; G1 and G2 stay **open and Critical**; P20's
  no-open-Critical acceptance rule is unchanged and still defines no accepted-Critical state.
- **Still not claimed:** that any of this is implemented or proven. PV-20 is not implemented, and the
  boundary is not claimed to exist (PV-20 §7).

## Why

- The Windows mechanisms are unstudied, and building one in P20 would add V1 scope on
  unmeasured ground.
- The existing two layers are decided and testable.
- Recording the gap is honest; leaving it unnamed would not be.

## Alternatives

- **P20 builds an OS sandbox:** rejected for V1 scope and evidence.
- **P24 decides from evidence:** the user chose to decide now. P24 can still raise it as a new
  finding.

## Consequences

- P20's work list and acceptance gain the tests in Decision 2 and the threat-model entries in
  Decision 3 (plan §31.1 P20).
- PV-20 exists with an ADR requirement.
- V2-A5's prerequisites include PV-20.
- No V1 code changes until P20 is scheduled.
