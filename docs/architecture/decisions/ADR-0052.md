# ADR-0052: Claude Code executions get tool removal derived from action classes, beneath the per-tool hook; unmapped tools are excluded by default

**Status:** DECIDED (the user's answer to XR-14, 2026-10-03: option 1, unmapped built-in tools excluded by default) · **Date:** 2026-10-03 · Implementation: **P20**, which does not start until P19.5 is explicitly finished (plan §31.1) · Analysis: [../XR-14_TOOL_ALLOWLIST_BRIEF.md](../XR-14_TOOL_ALLOWLIST_BRIEF.md) · Register: [../ARCHEUS_V2_ASSISTANT_LAYER.md](../ARCHEUS_V2_ASSISTANT_LAYER.md) §4 XR-14, §5 PV-22 · Realises ADR-0007 enforcement (2) for Claude Code · Reads ADR-0037, ADR-0049, ADR-0051

## Context

**The requirement and the gap.**
- ADR-0007 enforcement (2) and execution-architecture §2 require tool allowlists derived from
  action classes, as the primary layer beneath the hook.
- They were never built. p11-design-gate §18 contains only environment and credential removal,
  and `archeus/harnesses/claude_code/adapter.py:117-126` passes no tool flags.
- The fail-closed hook (`archeus/harnesses/hook.py`) has therefore been the only Archeus tool
  gate.

**Facts from the Claude Code documentation [DOC, brief §1]:**
- A hook that exits non-0/non-2, times out or prints invalid JSON lets the call "proceed through
  normal permission flow".
- `--allowedTools` makes tools "execute without prompting" and does not restrict them.
- `--tools` restricts which built-in tools exist, and does not affect MCP tools.
- Hooks fire inside subagents and for MCP tools.
- Not documented: whether a hook `allow` overrides `--disallowedTools`, and whether tool names
  are stable.

## Decision

1. **Removal beneath the hook.** The Claude Code adapter derives `--tools` in **allow-form** (a
   named list) from the task's `action_classes`, which already reach it in `task_contract`
   (`archeus/core/execution/manager.py:209`). A tool absent from the list cannot be called,
   whatever any hook or permission rule says.
2. **The mapping is the adapter's**, because it is Claude Code's vocabulary. Orchestration never
   branches on a harness id (ADR-0037 §4). The initial mapping follows; P20 verifies the names
   against the installed CLI (ADR-0037 §6) before building it:

   | Action class | Tools |
   |---|---|
   | `read` | `Read`, `Glob`, `Grep`, `LS` |
   | `write_repo` | `Write`, `Edit`, `MultiEdit`, `NotebookEdit` |
   | `exec` | `Bash`, plus the PowerShell tool where the CLI offers it |
   | `web` | `WebFetch`, `WebSearch` |
   | `git_commit`, `git_push`, `deploy`, `install`, `destructive`, `external_comm`, `credential`, `spend`, `personal_data` | **no tool of their own:** they act through `Bash`, and are enforced by the hook (P9 per canonical action) and credential removal only |

3. **Unmapped built-in tools are excluded by default.**
   - Every tool not produced by the mapping is absent from `--tools`: the subagent tool,
     todo/plan tools, REPL, notebook-adjacent tools, and any tool a future CLI adds.
   - Adding one requires a mapping row: a recorded change with its argument, reviewed like any
     capability.
   - A renamed tool disappears until it is mapped. That fails safe, and the drift test (6)
     reports it.
4. **MCP.**
   - `--disallowedTools "mcp__*"` is passed, except for MCP servers opted in under ADR-0049.
   - An opted-in server's tools need an action-class mapping, or the hook judges them as
     unclassified `exec` (strictest).
   - Whether a hook `allow` can override this deny is not documented, so it is verified (7), not
     assumed.
5. **`--allowedTools` is never passed**, because it pre-approves rather than restricts. The same
   holds for any flag or setting that pre-approves tools.
6. **Tests (P20):**
   - `argv()` per class set: a `document`-shaped task gets no `Bash`, write or web tools;
     `mcp__*` is denied; `--allowedTools` is never present; the hook's `--settings` is always
     present.
   - Mapping completeness: every entry of `ACTION_CLASSES` is either mapped or listed as "no tool
     of its own", and every tool the canonicaliser names is mapped.
   - A drift test against the installed CLI's tool names.
   - Mutation checks: removing a mapping row, adding `--allowedTools`, dropping `mcp__*` and
     dropping `--settings` must each fail a test.
7. **Verification (P20, gated by ADR-0021, alongside PV-19):** one observed execution confirms
   that a removed tool is never offered or called, and shows how the `mcp__*` deny behaves
   beside an opted-in server.
8. **Execution-architecture §2's flag names are corrected** to `--tools` / `--disallowedTools` by
   a dated amendment. The intent of the row (removal) is unchanged. p11-design-gate §18 gains an
   as-built note when P20 lands.

## Security boundary

| Layer | What it bounds |
|---|---|
| Removal | which tools exist for the execution |
| The hook (exit-2 deny, ADR-0049) | judges every call to what remains, including inside subagents and for opted-in MCP tools |
| Credential removal | what a held `Bash` can achieve against remotes |
| The permission flow (Claude Code's own) | the fallback for a failed hook on held tools: prompt-requiring tools are denied in `-p` |

**None of these contains what a held tool does:** an allowed `Bash` running a program, or `Read`
outside the worktree. That is ADR-0051's recorded gap, and PV-20.

## Consequences

- **Two layers for tool selection** where a task does not hold the tool. **One layer** (the
  hook, with the permission fallback) for tools it holds and for the nine classes that ride on
  `Bash`.
- **Claude Code's tool names become a tracked contract.** They are not documented as stable, and
  the drift test is the guard.
- **Excluding the subagent tool means executions run without subagents** until a mapping row adds
  it. **Excluding todo and plan tools may change how Claude Code works on a task.** That impact is
  unmeasured, and P20 measures it on the fake and the live harness before acceptance.
- **ADR-0007's decided text remains true as written.** ADR-0051 §2's gap closes for tool
  selection when P20 lands.
- **V2-A4 and V2-A5:** their capability ADRs must each add mapping rows for their tools, or those
  tools are absent.
- **Sequencing:** no code until P20 starts, and P20 does not start until P19.5 is explicitly
  finished.
- This decision is not revisited unless implementation evidence exposes a genuine contradiction
  with it.
