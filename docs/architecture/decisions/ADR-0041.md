# ADR-0041: Account consumption policy — protected accounts, subject limits, budgets always enforced, project defaults, a readable effective policy

**Status:** PROPOSED (the user's directive of 2026-09-30, "additional architectural requirements", §E; awaiting approval) · **Date:** 2026-09-30 · Implementation: P22 (fields, router rules, Resources UI); P21 (the effective-policy read, with ADR-0043); V1.x-O1 (`limits.task_families`) · Extends ADR-0005 · Reconciliation: [ARCHEUS_V1_CONVERSATIONAL_ORCHESTRATION.md](../ARCHEUS_V1_CONVERSATIONAL_ORCHESTRATION.md) A5, B2, C1, D2

## Decision

1. **`ResourcePolicy.consumption`** ∈ `normal` (default) | `last_resort` | `explicit_only`.
   - `normal`: today's behaviour.
   - `last_resort`: the account passes through the elimination steps as usual, but the election
     considers it **only when no `normal` candidate survived**. Electing it is a fallback,
     governed by the account's `fallback` mode (default `ask`), recorded with `fallback_from`, and
     explained ("used as a last resort because …").
   - `explicit_only`: eliminated at the `restriction` step ("used only when you name it") unless
     the subject's preferences name the account, where those preferences were set by a user
     device (a mission or project preference, or a pin). A brain reading never satisfies it.
2. **`ResourcePolicy.limits`** (optional): `subjects` ⊆ {`archeus_call`, `task`, `review`},
   `max_tier`, and `task_families` (from V1.x-O1). A subject outside them eliminates the account at
   `restriction`, with the reason.
3. **Budgets are enforced whenever set**, in addition to the window ceiling, for every account;
   `concurrency` caps live executions on any account. With no budget set, behaviour is unchanged.
4. **Project default resource preferences** (the mission shape: preferred and forbidden accounts
   and harnesses, `max_cost_band`), set only by a user device, inherited by the project's missions,
   which may narrow or override them. Account priority stays one global integer; a project's
   different first choice is a preference, already an ordering key ahead of priority.
5. **The effective policy is readable**: per account, consumption class, limits, ceiling
   arithmetic, budgets, fallback mode, priority, the ordering rule, and which values are defaults.
   The default with nothing configured is deterministic and shown: registration-order priority,
   `allocation 80 / reserve 10 / brain reserve 10`, `fallback: ask`, `consumption: normal`.
6. Nothing here is a score. No evidence rule, model output or routing status can change an
   account's consumption class or limits; only a user device with the `admin` scope can.

## Why

Priority is ordering only, so an eligible lower-priority account is elected silently whenever the
higher ones are eliminated (`archeus/core/routing/router.py:284-293`); a shared account with a
small allowance is consumed "because it is technically available", which the directive forbids.
`fallback: ask|deny` applies only when no candidate survives, and `reserve_pct` is headroom for the
user, not protection. Budgets are skipped for any account whose usage window is readable
(`router.py:265-276`), so a limit the user sets on a Claude Code account would be ignored without a
word. A consumption class keeps the router ADR-0005's pure, ordered function: `last_resort` is an
election rule over the survivors and `explicit_only` and `limits` are eliminations with reasons, so
every effect replays and explains itself.

## Alternatives

A very low priority plus a low ceiling (rejected: still consumed silently when higher accounts are
eliminated); a numeric "protection weight" (rejected: a weighted score, ADR-0033 §4); per-project
priority tables (rejected: a preference already expresses a project's first choice, and a second
priority axis makes the ordering hard to explain); protecting through P9 policy rules (rejected: a
resource question, which the router already asks — ADR-0035 §4).

## Tradeoffs

More approvals when the only surviving candidate is a `last_resort` account with `fallback: ask`;
the user can set `fallback: allow` on it to make the last resort automatic but visible.

## Consequences

Amends resource-router §4 (budgets always), §5 (the `last_resort` election rule; `explicit_only`
and `limits` in `restriction`), §8 (explanation wording) and domain-model §8.4 (fields) and §4
(project `resource_preferences`). G9–G11 and G13 of the reconciliation are its gates.
