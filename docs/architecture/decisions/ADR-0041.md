# ADR-0041: Account consumption policy — protected accounts, subject limits, budgets always enforced, project defaults, a readable effective policy

**Status:** DECIDED (the user's decision pass of 2026-09-30, D-13 and D-18; proposed in the third orchestration pass, `9dc1098`) · **Date:** 2026-09-30 · Implementation: **AP-1** (§1 and §3, a standalone Core slice that must land before any harness's ADR-0021 `rotation` is permitted), P21 (§5, the effective-policy read, with ADR-0043), P22 (§2 subjects and tier, §4, the Resources UI), V1.x-O1 (§2 `task_families`) · Extends ADR-0005; builds within ADR-0021 · Reconciliation: [ARCHEUS_V1_CONVERSATIONAL_ORCHESTRATION.md](../ARCHEUS_V1_CONVERSATIONAL_ORCHESTRATION.md) A5, B2, C1, D2, H3

## Decision

**Invariant: no router consumes a user-protected account merely because it is eligible.** The
protection is applied before any ordering key — affinity, preference and priority included.

1. **`ResourcePolicy.consumption`** ∈ `normal` (default) | `last_resort` | `explicit_only`.
   - `normal`: today's behaviour.
   - `last_resort` ("don't use it unless necessary"): the account passes the elimination steps as
     usual, but the survivors are **partitioned before ordering** — a `last_resort` candidate is
     considered only when no `normal` candidate survived. Electing it is then a fallback governed
     by the account's `fallback` mode (default `ask`), recorded with `fallback_from` and explained
     ("used as a last resort because …"). Affinity never keeps work on a `last_resort` account
     once a `normal` candidate survives again: the next routing decision (a retry, a continuation,
     the next task) moves it; a running execution is not halted for this.
   - `explicit_only` ("never automatically; only if I ask"): eliminated at the `restriction` step
     with the reason "used only when you name it".
   - **Lifting a class.** A preference or pin that names the account, *set by a user device* for
     a mission (or a project, §4), lifts `last_resort` / `explicit_only` for that scope only: the
     account is then an ordinary candidate there. A brain reading never lifts a class
     (ADR-0042 §3). Every other step — policy, enforcement, provider terms, data class, `limits`,
     health, ceiling, budgets — still applies.
2. **`ResourcePolicy.limits`** (optional): `subjects` ⊆ {`archeus_call`, `task`, `review`},
   `max_tier`, and `task_families` (from V1.x-O1). A subject outside them eliminates the account at
   `restriction`, with the reason ("used only for own calls up to tier small").
3. **Budgets are enforced whenever set**, alongside the window ceiling, on every account — the
   ceiling answers "how much of the provider's window", the budget "how much Archeus may spend".
   `concurrency` caps the account's live executions on any account. A budget is accepted only on a
   measure the account's adapter actually reports (a `cost_*` budget on an account whose usage has
   no cost is refused at write time with the reason), so a budget is never evaluated against a
   missing number. With no budget set, behaviour is unchanged. **Unknown usage stays unknown**:
   `None` is never read as 0 (resource-router §4).
4. **Project default resource preferences** — the mission shape: preferred and forbidden accounts
   and harnesses, `max_cost_band` — set only by a user device, inherited by the project's missions,
   which may narrow them or override them by a user-device command. Priority stays one global
   integer per account; a project's different first choice ("reserve B for project X" =
   `project_allow` on B plus a project preference for B) is a preference, already an ordering key
   ahead of priority.
5. **The effective policy is readable**: per account, its consumption class, limits, ceiling
   arithmetic, budgets, fallback mode, priority, the ordering rule, and which values are defaults.
   The default with nothing configured is deterministic and shown: registration-order priority,
   `allocation 80 / reserve 10 / brain reserve 10`, `fallback: ask`, `consumption: normal`.
6. Nothing here is a score, and the router stays generic: no rule names a harness or provider.
   No evidence rule, model output or routing status can change an account's class or limits; only
   a user device with the `admin` scope can.

## Why

Priority is ordering only, so an eligible lower-priority account is elected silently whenever the
higher ones are eliminated (`archeus/core/routing/router.py:284-293`); a shared account with a
small allowance is consumed "because it is technically available". `fallback: ask|deny` applies
only when no candidate survives, and `reserve_pct` is headroom for the user, not protection.
Budgets are skipped for any account whose usage window is readable (`router.py:265-276`), so a
limit set on a Claude Code account would be ignored without a word. A partition before ordering
and eliminations with reasons keep the router ADR-0005's pure, ordered, replayable function.

**Why AP-1 first (D-18).** Today the only thing preventing multi-subscription routing is ADR-0021's
`rotation` answer: while it is not `permitted`, only the priority-1 subscription of a harness is
used (`router.py:198-206`). The moment the user permits rotation — a single user command on an
existing route — every eligible subscription becomes electable. §1 and §3 are therefore the
minimum that must exist before that answer can be given; the rest can wait, because until then
nothing can consume a second subscription at all.

## Alternatives

A very low priority plus a low ceiling (rejected: still consumed silently when higher accounts are
eliminated); a numeric "protection weight" (rejected: a weighted score, ADR-0033 §4); per-project
priority tables (rejected: a preference already expresses a project's first choice); protecting
through P9 policy rules (rejected: a resource question, which the router already asks —
ADR-0035 §4); moving all of this ADR before P19.5 (rejected: §2, §4 and §5 protect nothing that
§1 and §3 do not already protect, and they need the Resources UI and project settings of P22).

## Tradeoffs

More approvals when the only surviving candidate is a `last_resort` account with `fallback: ask`;
`fallback: allow` on it makes the last resort automatic but still explained.
