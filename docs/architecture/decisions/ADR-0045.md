# ADR-0045: Legacy context migration is lossless-first and read-only against its source, never touches a project file without a per-project opt-in, and cuts over only in P25.5 with the user's approval

**Status:** PROPOSED (the user's directive of 2026-09-30, "legacy Archeus context / memory / lessons migration"; the phase itself is the user's requirement, its design awaits approval) · **Date:** 2026-09-30 · Implementation: P22 (tooling, with the importer), P24 (audit of the tooling), P25.5 (dry run, import, verification, cutover) · Extends ADR-0019 and migration-plan §4–§7 · Architecture: [legacy-context-migration.md](../legacy-context-migration.md)

## Decision

1. **A final phase, P25.5 — Legacy Context and Memory Migration**, after P25 and before the P26
   release gate: a controlled migration and verification phase, not a feature phase. P26 cannot
   pass while P25.5 is unverified. P22 keeps the importer, gains the migration tooling, and loses
   the ownership cutover, which moves to P25.5.
2. **The legacy source is read only.** Extraction never writes, locks, renames, rotates or
   quarantines a legacy file, never calls a legacy writer, and records a source it cannot read
   without side effects instead of modifying it.
3. **Project files are sacrosanct.** No migration step writes, moves, renames, reformats or
   annotates a project-owned file, and no V1 metadata is injected into one. Archeus-managed blocks
   inside project files (CLAUDE.md, AGENTS.md, `.claude/rules/archeus-mem-*`) are read only until
   a **per-project opt-in** at cutover, which is explicit, attributable, reversible and separately
   approved.
4. **Lossless first.** Every run starts from an immutable, content-addressed snapshot (manifest,
   hashes, versions); verbatim **source records** are kept per file and per logical record; every
   V1 row produced is **derived** from them with `derived_from`, and the derived representation is
   never the only copy. Summaries, merges and classifications are derived again later and cite
   their sources. Redactions and reference-only items are declared, never silent.
5. **Provenance on every migrated row**: snapshot, source path and record key, hashes, extraction
   time, run and tool versions, the named transform and the field diff it applied, and the legacy
   record's own timestamp.
6. **Conflicts are relations, never a silent choice**: an imported item that conflicts with V1
   knowledge enters as CANDIDATE with a `contradicts` relation and an Attention proposal; neither
   record is superseded until the user decides.
7. **Scope is preserved**: a record keeps the scope it came from; nothing is widened to global by
   migration.
8. **Gates**: dry run on a scratch database first; 100% of source records accounted for and
   classified, 0 silent losses, 0 unexplained conflicts, 100% provenance, deterministic re-runs,
   rollback demonstrated, legacy still recoverable, and the **project compatibility gate** —
   before/after project manifests in which every difference is attributed to the user, the legacy
   app, an approved V1 mission or an approved opt-in.
9. **Rollback needs no reconstruction**: before cutover it withdraws the run's rows; after cutover
   it re-enables the legacy writers, restores opt-in files from their pre-change copies and
   re-emits legacy formats; V1-native state is kept.
10. **Cutover is the user's**, per project, after every gate and a dual-read verification; it is
    never a side effect of an update, a restart or a schedule.
11. **Security**: `admin` user-device principal; credentials never copied; sensitive logs and
    transcripts reference-only by default, with a secret scan over anything copied; project data
    class applies to everything derived.

## Why

The legacy app is in daily use, and its state is spread over some forty stores — a per-project
workdir inside every project, managed blocks inside committed project files, user- and
account-level files, harness folders — some holding credentials. The existing P22 importer maps
that state straight into V1 entities: correct for most rows, but a mapping mistake is then a loss,
nothing shows what was left behind, and the cutover it performs has no gate and no consent.
Preserving the source first makes every later step checkable and every mistake recoverable;
attributing every project-file difference is the only way to prove "untouched" rather than assert
it.

## Alternatives

Migrate in P22 as planned (rejected: before acceptance and the security audit, and without a
gate); move files into V1 (rejected: destroys coexistence and rollback); summarise legacy memory
into V1 knowledge (rejected: lossy by construction); a one-off migration script (rejected: cannot
explain what it migrated); migrate all projects at once (not the default; decision MD-4).

## Tradeoffs

A second copy of the Archeus-owned stores in `artifacts/`; one more phase before release; V1
knowledge lags legacy memory until cutover (already ADR-0019's tradeoff).
