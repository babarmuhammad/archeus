# ADR-0045: Legacy context migration is per project, lossless-first and read-only against its source; existing projects keep working on the legacy system until their own approved cutover

**Status:** DECIDED (the user's migration decision pass of 2026-10-01, MD-1…MD-6; proposed 2026-09-30 in `e9d5681`; §10, §11 and §13 amended by the validation pass of 2026-10-01 — legacy-context-migration.md §25) · **Date:** 2026-10-01 · Implementation: P22 (tooling, with the importer, against fixtures only), P24 (audit of the tooling), P25.5 (dry run, import, verification, and cutover of the projects the user chooses) · Extends ADR-0019 and migration-plan §4–§7; the write boundary is ADR-0046 · Architecture: [legacy-context-migration.md](../legacy-context-migration.md)

## Decision

1. **Existing project safety during V1 development (hard invariant).** V1 development, migration
   and project cutover are **three separate concerns**. No project ever has to be migrated,
   rewritten, restructured or converted to keep working, and migration is never a prerequisite
   for normal work on a project. Until *that project's* approved cutover: its files are untouched
   by migration; its legacy context, memory, CLAUDE.md / AGENTS.md / rules and harness
   configuration remain usable and recoverable; its git state is not altered by migration; its
   workflow on the legacy system keeps working; V1 may coexist without forcing conversion. After
   its cutover: every change is attributable and has provenance, project-owned files pass the
   compatibility gate, rollback has been demonstrated, and legacy recovery stays available for the
   retention period (§10).
2. **A final phase, P25.5 — Legacy Context and Memory Migration**, after P25 and before P26: a
   controlled migration and verification phase. P22 builds the tooling (fixtures only) and loses
   the ownership cutover to P25.5.
3. **The legacy source is read only.** Extraction never writes, locks, renames, rotates or
   quarantines a legacy file and never calls a legacy writer or a loader with side effects; a
   source that cannot be read without side effects is recorded and excluded, never modified.
4. **No data loss: additive before cutover.** The only order is read → snapshot → preserve the
   source → derive V1 → verify → the user approves → cutover. No destructive source operation
   happens because a migration started; nothing is ever read, transformed and then deleted or
   replaced.
5. **Lossless first.** An immutable, content-addressed snapshot (manifest, hashes, versions);
   verbatim source records per file and per logical record; every V1 row **derived** from them and
   never the only copy; redactions and reference-only items declared.
6. **Provenance on every migrated row**: snapshot, path and record key, hashes, extraction time,
   run and tool versions, the named transform and its field diff, the record's own timestamp.
7. **Conflicts are relations, never a silent choice** (CANDIDATE + `contradicts` + Attention
   proposal); **scope is preserved** (nothing widened to global).
8. **Gates**: dry run on a scratch database first; 100% source accounting, 0 silent losses, 0
   unexplained conflicts, 100% provenance, deterministic re-runs, dual-read, rollback demonstrated,
   legacy recoverable, and the **project compatibility gate** — before/after manifests in which
   every difference is attributed to one of ADR-0046's permitted writes, the user, or the legacy
   app. **A run is keyed to explicit project identities** (V1 project id + its root paths + the
   legacy workdirs and harness folders that resolve to them) and **fails closed** if any source
   cannot be assigned to exactly one project in scope.
9. **Sensitive sources (MD-2)** fall in four categories, by source, before any content is read
   into a record:
   - **A — usable V1 knowledge**: the memory graph (entities, relations, lessons), user-pinned
     `ARCHEUS:KEEP` blocks, the workspace manifest, the legacy plan text, non-secret settings,
     loops, libraries, session labels;
   - **B — preserved source record, never ordinary context**: snapshots of earlier managed
     blocks and graphs, the dirty and session logs, worklog (as history), generated prompts —
     copied, hashed, readable by the migration report and provenance views, never injected into a
     context package;
   - **C — excluded entirely**: credentials (the legacy account-credential store,
     `.credentials.json`) and every secret value inside a copied file (API keys, tokens), recorded
     only as "redacted at field path P" — **no hash of a secret is stored**;
   - **D — hash, manifest and provenance only (reference-only, the default for sensitive
     operational records)**: injected context, bash logs, denials, transcripts and archived
     transcripts, events and proxy logs, caches, quarantined files — the original stays in place,
     unmodified; Archeus keeps its path, size, mtime and hash.
   **Exceptions** move a D source to B (never to A, and never a C source anywhere): only per
   source and per project, by a user-device `admin` command, after a secret scan whose hits become
   declared redactions, under the project's data class (ADR-0035), recorded on the run. Promoting
   B material to knowledge is an ordinary V1 knowledge proposal later, citing it.
10. **Rollback and retention (MD-6).** Before cutover, rollback withdraws the run's rows (legacy was
    never touched). After a project's cutover its **rollback window** opens: the immutable
    snapshot is the exact recovery material, and a **legacy-format export** — the memory graph
    with lessons, the worklog and the managed-block renderings, regenerated deterministically from
    V1 state at a recorded event sequence by a versioned exporter — covers what changed in V1 since
    cutover. Both live in `ARCHEUS_HOME/artifacts/` (never written into the project until a
    rollback is executed), each verified by hash and by a read of its parsed form in a scratch
    directory. The window is **configurable per project, at or above ADR-0019's 90 days** (a floor
    the architecture already had, not a new number), and **does not expire automatically**: it
    closes only when the user explicitly closes it for that project, which Archeus refuses while
    the project still depends on legacy tooling (a legacy reader or writer has not stood down, or a
    legacy-only workflow is still in use). Recovery material is deleted only by an explicit user
    command after the window closes; the export **capability** is removed only by an explicit
    release decision. Rollback never overwrites a newer user change (a file is restored only if it
    still has the hash V1 wrote), and what it cannot fully restore is listed in a
    **non-rollbackable register** the user accepts before cutover (legacy-context-migration §25.7).
11. **Legacy sessions and plans (MD-3).** **No legacy session becomes an Execution**: an Execution
    is work Archeus drove under P9/P10 (P12 D2), and a legacy session was not. A historical session
    stays **preserved source material** — a manifest entry with its identity (harness, account
    config dir, provider session id), path and hash, its transcript in place (category D) — and
    becomes a **Session** row (mode `manual`, P12's registration path, a deterministic id from its
    identity) only by the user's own action (resume, hand-off, register) or by an explicit
    per-run rule the user sets (`sessions: none | listed | window`, default `none`). No session
    becomes a V1 record because of its date. Incomplete or unreadable sessions are report entries —
    never omitted. A legacy plan that was never launched becomes a mission in
    CREATED with origin `legacy_import`, awaiting the user's confirmation; a launched one becomes a
    REFERENCE item with its verbatim text. No mission is imported as COMPLETED, because V1 reaches
    COMPLETED only through verification and review (conflict LM-C3).
12. **Cutover is per project (MD-4) and the user's.** Lifecycle, per project:
    `legacy → dry run → snapshot → validation → dual-read → compatibility gate → explicit user
    approval → V1 cutover → monitored coexistence (the rollback window) → retirement of legacy for
    that project`. There is **no global migration flag or mode**: projects on V1, on legacy,
    pending, and in a rollback window are all valid at once, and migrating project A cannot change
    project B. Cutover writes a per-project marker, `<project>/.archeus/v1-cutover.json` (ADR-0046),
    and nothing else outside the approved opt-ins: legacy writers and hooks **stand down only for a
    project carrying the marker**, and V1's hooks act **only** for such a project — a legacy seam
    built with the tooling in P22 (conflict LM-C2). Cutover is never a side effect of an update,
    restart or schedule.
13. **Retirement (MD-5)** is a separate, explicit decision with two levels: *per project* — when its
    rollback window is closed by the user (§10); *of the legacy app* — only by the user's explicit
    **release decision after P25.5**, when migration-plan §6's retirement checklist passes and every
    project the user names as required has independently passed migration, demonstrated rollback,
    had its dual-read differences explained, passed its compatibility gate and had its legacy
    export verified, and every other project is cut over too or declared by the user as no longer
    needing Archeus (its legacy state preserved in place and in a snapshot). No date is set. While
    any project still works through the legacy app, it does not retire.
14. **Security**: `admin` user-device principal; the P9/P10/P11/P13/P15 controls unchanged; the
    tooling audited in P24.

## Why

The legacy app is in daily use across many projects, and its state is spread over about forty
stores — a workdir inside every project, managed blocks inside committed project files, user- and
account-level files, harness folders — some holding credentials. A global cutover, a converted
session history, or a lossy import would each break a project that never asked to move. Preserving
the source first makes every step checkable and every mistake recoverable; a per-project marker is
the smallest mechanism that lets two applications own different projects without two writers of
one file (ADR-0019's lesson).

## Alternatives

Migrate in P22 (rejected: before acceptance and audit); one global cutover (rejected by the user);
legacy sessions as Executions (rejected: P12 D2; would fabricate driven work); a fixed session age
window (rejected: an arbitrary heuristic — the references cost nothing); a retention period that
expires by itself (rejected: recovery material must not vanish while rollback is possible); a
global cutover setting read by the legacy app (rejected: a global mode).

## Tradeoffs

A second copy of the Archeus-owned stores in `artifacts/`; one more phase before release; a small
legacy seam (the marker check); V1 knowledge lags legacy memory per project until that project's
cutover.
