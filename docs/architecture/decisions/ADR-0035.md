# ADR-0035: A project's data class limits which providers and locations may receive its work

**Status:** DECIDED (direction set by the user's directive of 2026-09-30, §13 and clause H; this record resolves O-10 of the orchestration reconciliation) · **Date:** 2026-09-30 · Implementation: V1.x-O4 (until then the existing account `project_deny` and mission `forbidden_*` restrictions are the boundary) · Reconciliation: [ARCHEUS_V1_ORCHESTRATION_RECONCILIATION.md](../ARCHEUS_V1_ORCHESTRATION_RECONCILIATION.md) §20

## Decision

1. A project (and, narrower, a mission) carries `data_class` — `public | internal | confidential
   | local_only` — set only by a user device through a command; default `internal`.
2. A **provider rule** (ResourcePolicy-scoped, versioned) maps each data class to the providers
   and locations allowed (e.g. `local_only` → `location: local`; `confidential` → an explicit
   provider allowlist). Provider and location come from the catalogue (ADR-0031).
3. The rule is applied **in Core, at the router's `restriction` step**, for every subject that
   sends project content (task, review, own calls about the project), eliminating an offer with
   the reason; `route why` explains it. An offer whose provider is unknown (an opaque router
   without a guaranteed SERVED record) fails every class except `public`.
4. The P9 policy engine keeps its action-level role and gains no provider input; the provider
   question is a resource question, which the router already asks for `project_allow/deny`
   (resource-router §9). A client is never the boundary; there is no development bypass.
5. Context assembly never adds content from a project with a stricter class than the one the
   decision was checked for.

## Why

Once more than one provider can receive work (the Codex adapter is a V1 release requirement;
proxies and local models follow), capability must not decide where a project's code goes. Keeping
it in the restriction step reuses the existing, replayable resource path and leaves P9's
action/boundary semantics untouched.

## Alternatives

A `provider` match key in P9 policy rules (rejected for now: mixes resource and action questions;
reconsider if a rule needs action context); a client-side warning (rejected: not a boundary).

## Tradeoffs

A new setting on projects; misclassification is the user's to correct.

## Consequences

Amends resource-router §3 (restriction inputs) and domain-model §8.4 (provider rules). P24 adds
the cross-phase question "can a catalogue update, an evidence rule or an opaque router route a
project's content to a provider its data class forbids?" — the answer must be no by construction.
