# ADR-0047: Context capacity is a governed execution resource — measured with its basis, never assumed; the only continuation is the existing checkpoint hand-off

**Status:** DECIDED (the user approved D-26 on 2026-10-01, as resolved in `0067369`; proposed in `52f0a0f` by the context-capacity audit of 2026-10-01 and revised the same day by the resolution pass — see "Revision"; built in the P21 D-26 slice — see "As built") · **Date:** 2026-10-01 · Implementation: **P21** (the recorded basis, the `live_work` context field, the explanation, the no-progress guard; see clause 12) · Extends p12-design-gate §10.1 and §13.1 (FROZEN, as built), execution-architecture §6, ADR-0043 §2, ADR-0034 §4; reads ADR-0031 §1, ADR-0041 · Gates: testing-strategy §10 (CX-1…CX-18)

## Context — what already exists

The audit found that most of the requirement is already designed **and built** in P12. This ADR
does not restate a second mechanism; it names the existing one and closes five gaps.

| Concern | Already covered by | State |
|---|---|---|
| Model capacity (context window per model/revision) | `ModelInfo(id, tier, context_window)` offers (`archeus/harnesses/base.py`); `Model`/`ModelOffer` facts with per-field source and `observed_at` (ADR-0031 §1–§2, P22) | offers built; catalogue P22 |
| Window unknown | `context_window: None`; the router counts an unknown window as the smallest, so a stated minimum excludes it (resource-router §3); the manager uses the smallest window the harness declares, and **none** when it declares none (p12-design-gate §13.1) | built |
| Session consumption | `pressure = (input + cache_read + cache_creation tokens) / window` on every usage the stream reports; stored on `Execution.pressure` via `record_progress` (`archeus/core/execution/manager.py:330-340`) | built |
| When to stop | pressure ≥ 0.75 hands off; the PreCompact hook counts as 0.9 (p12 D20, `PRESSURE_HANDOFF`, `PRESSURE_PRECOMPACT`) | built |
| Halting safely | `HANDOFF` flag; the hook halts at the next tool call; no boundary within `pause_timeout` → killed (p12 §10.1 step 2) | built |
| Checkpoint | Core-derived, not asked of the full agent: objective, constraints, completed steps, files changed, verification, decisions, open problems, next action, context refs (execution-architecture §6) | built |
| Continuation | one transaction: checkpoint, `ENDED_HANDOFF` (uncharged), P9 `check_dispatch`, P10 `route`, new Execution with `handoff_from`, `attempt + 1`, same plan binding; mission and task states unchanged; refused → task READY uncharged (p12 §10.1) | built |
| Provenance of the hand-off | `stop_reason: pressure`, reason text, `handoff_from`, `task_contract.continuation`, the checkpoint row, events | built |
| Task requirement | `min_context_window` in the router's model step | **seam only**: tasks pass none (p13-design-gate §26.8) |
| Own calls (planner, extraction, review) | one-shot; the context package's budget follows the chosen offer's window (ADR-0034 §4) | built/decided |
| Live visibility | `live_work` (ADR-0043 §2), P21 | decided, no context field |
| User sessions (`interactive_attached`, `manual`) | resume and hand-off (ADR-0023, P12) | no measurement |

**Gaps found:**

1. **No measurement quality.** `pressure` is a bare float. A value computed against the smallest
   declared window (the model was unknown) is an *estimate* and is stored exactly like a reported
   one; a harness that reports no usage leaves `pressure: None` with nothing saying why; nothing
   marks a reading that later output has overtaken.
2. **Unbounded hand-off loop.** A pressure hand-off is uncharged, so a continuation whose starting
   load (task contract + checkpoint rendering + package) is itself at or past the threshold hands
   off again on its first usage report, and so on. No attempt budget stops it.
3. **Compaction has no stated position.** Claude Code's own compaction goes ahead (`hook.py`
   PreCompact: "compaction itself goes ahead"); Archeus triggers none. Neither fact is an
   architectural decision anywhere.
4. **Not visible and not explainable with its basis.** `live_work` has no context field; a hand-off's
   reason says `context pressure 0.80 reached 0.75` with no window, no source, no quality.
5. **Routing interaction is implicit.** Nothing states that context capacity is a constraint and never
   an ordering key, or how a pressure hand-off meets AP-1.

## Decision

1. **Five quantities, never one number.**
   - *Model capacity* — the window a model/revision supports: an ADR-0031 fact with its source rung
     and `observed_at`. Factual capability, not permission: a catalogued model stays unroutable
     until APPROVED (ADR-0031 §4) whatever its window.
   - *Harness behaviour* — what the adapter declares: whether it reports usage, whether it compacts
     on its own and whether Archeus can observe it (a PreCompact-style hook, a `compact_boundary`
     event), and whether it has a tool boundary to halt at. Declared by the adapter's capabilities
     today; by ADR-0037's descriptor if that is decided (it would add `usage_reporting` and
     `compaction: none | harness_auto_observed | harness_auto_unobserved`).
   - *Session state* — what one execution has consumed: `pressure` with its **basis** (clause 2).
   - *Task requirement* — `min_context_window` on the requirement: a hard minimum on the *model's
     window*, set only when a user, a pin or a verified source states it. It is never guessed by
     the planner or derived from a transcript; until stated it is absent, and absent means "no
     minimum", not "fits".
   - *Continuation safety* — a derived answer (clause 4), never stored as a score.
2. **Every pressure value carries its basis.** Recorded on the execution by the same
   `record_progress` write that records `pressure`:
   `context {used_tokens, window, window_source: offer | harness_smallest | none, usage_source:
   harness_reported | none, at_seq, signal: none | precompact, signal_seq}` where `at_seq` is the
   stream offset the usage was read at and `signal_seq` the offset at which a PreCompact record was
   observed. `offer` means the offer of the execution's **own account** (domain-model §8.3, C-22);
   as built the manager asks the adapter for its default offers (`manager._window` →
   `capabilities(None)`), which P21 corrects — no effect today, since the only harness whose
   offers differ by account (pi) has no execution adapter (C-23).
   *Quality* is derived at read time, never stored, first match wins: **signalled** (`signal:
   precompact` — the harness reported that it is about to compact its own context; the `pressure`
   of 0.9 is p12 D20's policy stand-in for that signal, **not** a measured ratio, so `used_tokens`
   and `window` keep only what a real usage report said, or stay `None`, and `remaining` is
   `null`), **unavailable** (no window or no usage report: `pressure` stays `None`, never 0, and
   the item says "context not measured by this harness"), **stale** (output was recorded after
   `at_seq` with no newer usage report — a comparison of offsets, so it needs no clock and no
   threshold), **estimated** (`window_source: harness_smallest`), **reported** (offer window and a
   harness usage report). The manager's `(pressure or 0.0)` comparisons are threshold checks inside
   one tick and are never stored or shown; nothing recorded or rendered turns `None` into 0.
   Only token counts are recorded;
   no prompt, transcript or context content is kept for this beyond the execution stream P11
   already writes. Output tokens are recorded but not added: the occupancy that matters is the
   next turn's input, which already contains them. Harness overhead (system prompt, tool schemas)
   is inside the reported input; what a harness reserves and does not report is covered by the
   margin (clause 3), not estimated.
3. **The threshold stays the approved one.** 0.75, with PreCompact counted as 0.9, is p12 D20
   (FROZEN). It is **session policy**: one Core constant, not model metadata and not a routing
   input. This ADR adds no number. Making it per harness or per model needs evidence and its own
   recorded decision.
4. **Where continuation safety is evaluated.** (a) At every route, including every continuation and
   retry: the window meets the task requirement when one is stated (built). (b) At every usage
   report (built). (c) On PreCompact (built). (d) At the next tool boundary, where a requested
   hand-off halts (built). (e) **New:** when a continuation would be created (the guard, clause 5).
   Not evaluable in V1: *before a large tool operation* or *before adding large context* — Core adds no
   context mid-execution and a tool's output size is unknown until it returns; that belongs to a
   harness, and is deferred. **Unknown is never safe**: with quality *unavailable* the execution
   runs on the harness's own behaviour (and, for Claude Code, the PreCompact backstop), its item
   says so, and P13 verification judges the result as it judges every result.
5. **No-progress guard — the one behaviour change.**
   - *When.* In `record_handoff`, before the end is written (it needs no checkpoint, so the
     checkpoint of the same transaction can record its outcome), for an execution that is a
     continuation (`handoff_from` set) and whose own hand-off is for `pressure` (a usage report or
     the PreCompact signal). A user's hand-off and an account change (`limit`, `ceiling`) are never
     guarded: the first is the user's choice, the second is not a context problem.
   - *What counts as progress — read from records, never from a checkpoint.* A checkpoint is
     history and is never read to decide a state (p12-design-gate §8.3, FROZEN); the guard keeps
     that rule. It reads two facts: (i) the **end state** of the execution's workdir — the HEAD
     revision plus a digest of the tracked and untracked diff — measured by the node in the same
     read that already produces `files_changed` (`git diff --stat HEAD`, `node/local.py`) — read-only
     git calls that never write the index or a ref (`--no-optional-locks`), so the read is not a
     project change (ADR-0046, MG-6) — and recorded on the Execution (`end_state_digest`) beside
     `exit_code`; (ii) the artifacts the execution recorded (ADR-0030 §4
     producer record, P21). The execution made progress when (ii) is non-empty, or when (i)
     differs from the recorded end state of **every** earlier execution of the same continuation
     chain (the `handoff_from` ancestry) — so a chain that returns to an earlier state (A → B → A)
     is no progress, not two steps of it. Never counted: `DECISION:` lines or any other agent
     statement, verification rows (none is written while the task is RUNNING), and other tasks'
     movement. An end state that cannot be measured (no git workdir, the read failed) is **no
     progress**: an unknown fact refuses, never passes (guards fail closed, state-machines §2).
   - *The transition.* `HANDING_OFF → ENDED_HANDOFF` by the existing `checkpoint_written` edge,
     with `exit_reason handoff`, `stop_reason pressure` and **`charged True`**, and no continuation.
     It is the only exit of HANDING_OFF whose meaning is true: the process halted at a boundary
     on Core's request and the checkpoint was written (CX-4); `exited_error` → ENDED_ERROR would
     record a process error that did not happen, STOPPING → ENDED_KILLED needs a live process, and
     a new state would be a second name for ENDED_HANDOFF. `charged` is a field, not a state:
     `charged_attempts` already counts every execution whose `charged` is not False, whatever its
     state. This is the one amendment to p12-design-gate §10.1 step 3 (`charged False`), which
     stays FROZEN and unedited. A charged ENDED_HANDOFF exists only through this guard, so the
     guarded end is identifiable from the record alone; the checkpoint derived in the same
     transaction lists `context insufficient` in `open_problems` with both readings' bases.
   - *The task and the mission.* The existing charged rule (P11 D9, `charged_failure`):
     `execution_failed_retry` while charged attempts remain, else `execution_failed_final` with
     `failure_class: context_insufficient`; the reasons carry both readings' bases. A retry is an
     ordinary new execution — no `handoff_from`, no checkpoint suffix — dispatched through P9 and
     P10 like every retry; its own pressure hand-offs start a new chain. `context_insufficient` is
     **not** added to `NOT_RETRYABLE`: that list holds the classes a replan cannot fix (`policy`,
     `credential`, `human`), and a task larger than every eligible window is exactly what a replan
     fixes, by splitting it — the planner sees why through the checkpoint's `open_problems` (p12
     §8.4, a planner input, not a state decision). So the mission takes the existing
     `task_failed_retryable` edge to REPLANNING while `replan_budget_exhausted` allows
     (`max_replans`), and the existing exhausted path after that.
   - *Why this ends.* Every guarded end spends one charged attempt and a retry draws only on
     charged attempts, so a task has at most `max_attempts` guarded ends per plan version and a
     mission at most `max_replans` + 1 plan versions: hand-off → retry → hand-off is finite with no
     new number. No new state, no new edge, no number.
5a. **A chain that keeps making progress has no count cap — its bound is the resources.** V1 adds
   no continuation-count limit. A chain whose every link makes measured progress (clause 5) is
   work being done, not a loop, and a count would fail a long task that is progressing while
   adding a number with no evidence behind it (the reason clause 3 adds none). It is bounded by
   what already bounds all work: (1) each link is a real execution with its harness's own
   per-execution limit (Claude Code's `--max-turns` by estimate) and P12's `pause_timeout`; (2)
   each link is re-authorised by P9 (`check_dispatch`: the plan in force, the binding, policy) and
   re-routed by P10 (provider terms, usage windows and limits, allocation and reserve ceilings,
   budgets, concurrency, and AP-1's partition once built) — any refusal ends the chain
   **uncharged** with the task READY, where the ordinary dispatch asks, blocks or waits (built);
   (3) the e-stop (nothing starts while disarmed and every live execution stops), a user stop and
   a pause; (4) every link is a live `live_work` item carrying its hand-off count
   (`task_contract.continuation`, built) and its recorded reason, so the chain is visible and
   explainable while it runs. Core holds no loop that creates executions: a continuation is
   created only inside the transaction that ends a real process (`record_handoff`), at most once
   per end, and nothing retries a hand-off on a timer. One dependency is stated rather than
   hidden: a budget set on an account that reports a usage window is enforced only from AP-1 (G10,
   C-35); until AP-1 lands, such an account's own windows, limits and ceilings are the resource
   bound — and no real harness is routable at all today (eliminated at `provider_terms`).
6. **Compaction.** Archeus-initiated compaction or summarisation is **not a V1 capability**. Recorded
   as unavailable, not simulated. Continuity is the checkpoint, derived by Core from its records
   and the execution's recorded output rather than from what the agent's context retained, so a
   hand-off loses nothing Core holds. Its provenance (p12-design-gate §8.2): **authoritative** —
   identity, trigger, `as_of_seq`; **copies of rows, the rows win** — objective, constraints,
   success criteria, completed steps, verification; **measured by the node** — `files_changed`;
   **recorded by Core** — `open_problems` (hook denials and halts, the failure, the exit code),
   `usage`; **the harness's output** — the last error line; **the agent's own statements** —
   `decisions` from `DECISION:` lines, beside the mission's CONFIRMED DECISION knowledge items.
   Each is kept twice: verbatim in the execution stream P11 already writes, and clipped and
   redacted in the checkpoint (§8.2 caps). A `DECISION:` line is a claim: it is never read to decide
   a state, never counts as progress (clause 5), and where it contradicts a row — a check it says
   passed that a Verification row records failed — the row is the truth; neither is edited to
   agree, and P21's rendering and Why view name the agent as the source of that section. A
   harness's own compaction is harness behaviour: observed, not governed — PreCompact → pressure 0.9 → hand-off at
   the next tool boundary, `compact_boundary` recorded. Work the agent does on compacted context
   before that boundary is verified by P13 like any other work. A governed compaction would need
   its own ADR (who triggers it, which checkpoint fields may never be dropped, how its output is
   verified against them); none is proposed.
7. **Routing.** A continuation is an ordinary Execution routed through P9 and P10 (built). Context
   capacity is a **constraint that eliminates**, never an ordering key: there is no "larger window is
   better", the model step still takes the smallest tier meeting the requirement, and a
   continuation inherits the task's requirement unchanged — the ended execution's pressure does not
   raise it. Pressure is not an account problem: affinity is kept (as built) and no fallback is
   triggered by it. Every other elimination — authorisation, policy, data class (ADR-0035), provider
   terms (ADR-0021), budgets, ceilings, concurrency, e-stop, verification and independent review,
   explicit user directives — is untouched and runs before and after it exactly as now.
8. **Accounts (AP-1).** Protection applies at a continuation's route like any other route. A hand-off
   never lifts protection and never counts as a user-device preference naming an account; a
   protected account is not elected because it "has capacity". If only a protected candidate
   survives, AP-1 and the fallback policy decide (ask or block). No session, account or harness is
   preferred because it started the mission, is mounted, or is connected: a continuation is always a
   new session and affinity is the only carry-over. A pressure hand-off rotates nothing. AP-1 is
   **specified and not built** (ADR-0041 §1, §3; testing-strategy AP-1, G9, G10): until it lands, no
   route — first dispatch or continuation — has protection classes, and every real harness is
   eliminated at `provider_terms`. A continuation needs nothing of its own for it: it calls the
   same `router.route` as a first dispatch (`execution/handoff.py`), so AP-1's partition reaches it
   the day AP-1 lands, and CX-7 is the gate that proves it then.
9. **Visibility and explanation.** `live_work` (ADR-0043 §2) gains `context` per execution item: the
   clause 2 basis, its derived quality, and `remaining = window − used` only when both are known
   and the quality is not *signalled* (otherwise `null`, shown as unknown). A hand-off's reason
   names its basis ("the harness reported 150,000 of 200,000 tokens; window from the offer" /
   "…window estimated: the smallest this harness declares" / "the harness signalled it was about
   to compact its context (PreCompact), counted as 0.9 by policy; last reported usage: none").
   Each item carries its chain's hand-off count. The checkpoint row is what was retained, with
   `relevant_context_refs` as the provenance of the retained context. The `status` and `why` verbs answer "how much context
   is left", "why did you stop using this session", "what did you preserve" from these records only,
   never from a model's account of itself (ADR-0042, ADR-0043). Surfaces: the mission thread and Now
   (a continuation shown as "continuing in a fresh session", spec §17 — numbers on demand), the Work
   live view and the inspector (per execution), Why (the hand-off reason and checkpoint). Not
   Control → Resources: context is per execution, not per account. No new dashboard. Nothing is
   computed without a live execution's stream: no polling, and motion only for real `execution.*`
   frames (ADR-0024).
10. **User sessions** (`interactive_attached`, `manual`) are **not measured** in V1: quality
    *unavailable*. A measurement would come through the session adapter's `turns` read; deferred.
11. **Security, legacy, project files.** Counts only, `observe` scope, redaction unchanged; no
    authority is widened (P9 re-checks every continuation, built). Legacy sessions and stats carry
    **no** V1 context measurement: a migration never fabricates a `context` basis or a `pressure`
    (legacy token totals are session totals, not occupancy) and creates no Execution (MG-19). Nothing
    is written into a project by pressure, a checkpoint or a continuation: a headless continuation
    gets the checkpoint as a prompt suffix, and a user-session hand-off's delivery copy stays in
    ADR-0046's namespace (MG-12).
12. **Owner.** P21, beside the provenance fields it already owns (ADR-0031 §6) and `live_work`
    (ADR-0043). P21's "no routing behaviour changes" holds: clause 5 changes whether a continuation
    is created, not how anything is routed. No new phase or slice.

## Why

The requirement is real — a session must not be discovered full only when the harness fails — and
P12 already meets its core: it measures, halts at a boundary, derives the checkpoint from Core and
routes the continuation through the governed pipeline. What it lacks is honesty about the
measurement (an estimate reads as a fact), a bound on its own loop, and a readable reason. Adding
those to the existing records is smaller and safer than a context subsystem.

## Alternatives

A per-session context budget entity with its own states (rejected: a second lifecycle beside
Execution, the reason ADR-0043 rejected an Agent entity); a universal percentage per model
(rejected: no evidence, and p12 D20 already decided the margin); Archeus-driven summarisation
(rejected for V1: a lossy step whose loss nothing could verify, while the checkpoint loses nothing
Core holds); preferring larger-window models at a continuation (rejected: a hidden ranking,
ADR-0033).

## Tradeoffs

A continuation that makes no measured progress ends charged instead of handing off again; the
retry and then the replan are the recovery, each within its existing budget, and the user sees
why. The guard does **not** bound a chain that keeps making progress: that chain is legitimate
work, bounded by the resources it consumes, the per-execution limits, P9 and P10 at every link,
the e-stop and the user (clause 5a) — a long task on a generous account can run many links, and
that is visible on every link rather than capped. Read-only work — a link that only reads and
changes nothing — counts as no progress, so investigation that needs more than two windows of
context fails charged and is replanned smaller. An unmeasurable workdir counts as no progress, so
a task with no git workdir gets at most one pressure continuation per attempt. Harnesses that
report no usage get no pressure hand-off, only their own behaviour and verification — stated,
not hidden.

## Revision

*2026-10-01, resolution pass (still PROPOSED; nothing here is built).* The consistency audit of
the first draft found six gaps, closed above without a new state, edge or number:

1. **The loop was bounded only for an exact repeat.** The guard compared a continuation with its
   immediate predecessor, so a chain that changed something trivially on every link, or
   oscillated (A → B → A), was capped by nothing — hand-offs are uncharged and no count exists.
   Clause 5 now compares against every earlier link of the chain and counts an unmeasurable end
   state as no progress; clause 5a states that a chain which keeps making progress is bounded by
   resources and stops, not by a count, and the Tradeoffs say so instead of implying the guard
   closes every chain.
2. **The guard read checkpoints to decide a state,** which p12-design-gate §8.3 (FROZEN) forbids.
   It now reads the recorded end state and artifacts (clause 5).
3. **The terminal transition was unnamed.** It is `checkpoint_written` to ENDED_HANDOFF with
   `charged True` (clause 5; the Failure semantics table).
4. **Retry semantics were implicit.** `context_insufficient` is retryable within `max_attempts` and
   replannable within `max_replans`, and stays out of `NOT_RETRYABLE` (clause 5).
5. **A PreCompact reading had no basis.** It is the *signalled* quality, never a usage report
   (clause 2).
6. **The checkpoint's provenance was overstated** as wholly Core-derived; `decisions` are the
   agent's statements (clause 6). Also stated: AP-1 is not built (clause 8), and the window is the
   execution's own account's offer (clause 2).

## As built

*P21, the D-26 slice (2026-10-01).* Nothing above changed; this records where it lives.

- **Basis and quality** — `archeus/core/execution/pressure.py`: `reported`, `signalled`,
  `quality`, `view`, `reason`, `progressed`, and the p12 D20 constants (the manager re-exports
  them). `Execution.context` holds the basis and is written by `record_progress` with
  `pressure`; quality, `remaining` and the summary are derived by `pressure.view` in every read
  (`executions.view`, `of_task`, `live_work`). `at_seq` is the offset of the read that carried
  the report. A report with no input figure measures nothing; a report with no known window
  records the tokens and no ratio.
- **PreCompact** — the manager records `signal: precompact` with the offset it was observed at
  and sets `pressure` to at least 0.9; the basis keeps only what real reports said.
- **Window** — `manager._window` asks the adapter for the offers of the execution's own account
  (`AccountRef(account_id or harness_id, home_ref)`), as C-22's router does; the fix of clause 2.
- **End state** — `LocalNode.end_state(workdir)`: `git --no-optional-locks` `rev-parse HEAD`,
  `diff --binary HEAD`, `ls-files --others --exclude-standard` and `hash-object --stdin-paths`
  (no `-w`), hashed together; None when the workdir is not a repository, has no commit or a
  read failed. Measured at every end with the other checkpoint facts and recorded as
  `Execution.end_state_digest`. Ceiling: git output is decoded with undecodable bytes dropped,
  so two text diffs differing only in such bytes digest alike — which reads as no progress,
  the fail-closed side.
- **Guard** — `executions.no_progress`, called by `record_handoff` before the end is written;
  the guarded end takes `checkpoint_written` with `charged True`, its checkpoint lists the
  reason in `open_problems`, and the task goes through `charged_failure` with
  `context_insufficient`. Clause 5 (ii), the execution's recorded artifacts, is passed empty:
  no execution records an artifact until the producer record exists (V1-3, P21, not in this
  slice), so progress is the end state alone until then.
- **Live work, why, status** — `archeus/core/application/live.py`: `live_work(conn)` (the
