# ADR-0034: Artifact-first hand-off between the steps of a mission

**Status:** DECIDED (direction set by the user's directive of 2026-09-30, clauses T–V; this record resolves O-6's hand-off half and O-15 of the orchestration reconciliation) · **Date:** 2026-09-30 · Implementation: P21 (artifact producer, already assigned by ADR-0030 §4), V1.x-O3 (declared outputs, input rules, critic step) · Reconciliation: [ARCHEUS_V1_ORCHESTRATION_RECONCILIATION.md](../ARCHEUS_V1_ORCHESTRATION_RECONCILIATION.md) §14, §15, §16

## Decision

1. **Steps exchange artifacts, never conversation.** A step's output that another step consumes is
   an Artifact with a producer: `Artifact` gains `produced_by {kind: execution, id}`, `task_id`,
   `kind` (architecture | plan | patch | report | test_result | review | checkpoint |
   transcript_excerpt) and `label` (domain-model §7.9 already specifies `produced_by`/`label`).
   No provider session, transcript or hidden model-to-model channel crosses a step boundary.
2. **A downstream task names its inputs** in the existing contract field `inputs[]` as artifact
   references, and starts only from a **verified** upstream artifact at a recorded revision; an
   unverified artifact is never an input.
3. **Roles are not entities.** They follow from the task's `kind` and `task_family` (ADR-0032)
   and the routing subject (`task`, `review`, `archeus_call` purpose). There is no fixed
   architect → implementer → reviewer → verifier chain; the plan's DAG is the composition, the
   planner proposes it, Core validates it, the router chooses each resource.
4. **Context is explicit and bounded** by subject: the package's budget follows the chosen
   offer's context window; an implementer gets the task contract, its input artifacts and budgeted
   repository context; a reviewer gets the user's verbatim request, requirements, constraints, the
   relevant artifacts, the diff and verification evidence — never the implementer's transcript or
   summary. What was included is recorded in the ContextPackage as today.
5. **Terminal states are the hand-off acts**: done = VERIFIED (+ review); refused = FAILED with
   `failure_class` or BLOCKED with a reason; needs human = an Approval or a clarification. An
   optional **critic** is a second independent Review requested by the mission's
   `review_strategy` or by the user; reviewer disagreement goes to the human, never to a vote.
6. **An architecture stage is a task**, not a new mechanism: a `document`-kind task with
   `task_family: architecture`, `min_model_tier: large`, an `architecture` artifact as its
   expected output, verified by DocumentVerifier plus review (plus human acceptance where the
   autonomy profile puts an approval point there). A replan after it is optional and counts as
   an ordinary replan.

## Why

Checkpoints already hand off by a Core-derived artifact, never provider state
(execution-architecture §6); artifacts make each step reproducible, auditable, provider-
independent and resumable (R5: queues are what exists on disk). superpowers' brief/report files
and fable-foreman's blind verifier are the same discipline as prompt conventions; Archeus holds it
as Core state.

## Alternatives

Agent-to-agent messaging (rejected: hidden state, unauditable); passing transcripts (rejected:
breaks independence and budgets); a dedicated pipeline entity (rejected: the plan's DAG already is
one).

## Tradeoffs

A step must declare its output; a free-form "carry on from what the last model said" is not
possible, by design.

## Consequences

Amends domain-model §7.9 (producer fields), §7.3 (`inputs[]` may reference artifacts),
execution-architecture §6 (declared outputs beside checkpoints). New event `artifact.recorded`
(P21, with the producer record). No new state machine.
