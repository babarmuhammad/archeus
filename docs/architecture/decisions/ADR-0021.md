# ADR-0021: Provider-terms gate before the first real headless model call

**Status:** OPEN · **Date:** 2026-09-23

## Decision

The user confirms whether automated headless use of subscription accounts, and rotation across several subscriptions, is permitted by each provider's terms **immediately before the first real headless model call** (the first tool-less structured call in P6 or P7, whichever is switched on first; P4 ships no model pass — p4-design-gate D2). It is not a P0 gate: P0.5–P3.5 make no real model call. Fake and scripted harnesses/brains are unrestricted for architecture and acceptance testing. Tool-less structured calls are allowed only through the controlled `llmcall` runner once this gate is passed. Real tool-using agent execution additionally stays hard-gated until the P9 policy engine exists. Nothing assumes subscription automation is permitted. (Moved from P0 on 2026-09-23 with the user's explicit approval.)

## Mechanism (P6, as built — the question itself is still open)

The answer is a Core record per harness (`ProviderTerms`: `headless` and `rotation`, each
`unknown | permitted | refused`; no record is `unknown`). `unknown` blocks exactly as `refused`
does. Only the user gives it — `archeus terms <harness> permit|refuse [--rotation …]` or the
admin route `POST /v1/provider-terms/{harness}` — and `provider_terms.decided` records it. Every
real adapter's `call()` is checked twice: in the pre-router election, and again in a fresh read
immediately before the spawn. Scripted adapters (`FakeCaller`, by class identity) are exempt;
nothing else is. Rotation across subscriptions runs only when `rotation` is `permitted`. A pass
the gate stopped is recorded as `gated`, never fails its project, and runs again once headless
use is permitted (p6-design-gate §3).

## Why

The migration kit's feasibility doctrine: a fully sketched plan may still end in "don't". The router and multi-account features depend on this answer.

## Alternatives

Assume permitted; restrict V1 to API keys.

## Tradeoffs

Uncertainty until answered.

## Consequences

If not permitted: the architecture stays intact; real headless calls and executions use supported API-key/provider accounts, and subscription accounts remain available for the user's own interactive and manual sessions.
