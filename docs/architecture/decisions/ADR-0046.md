# ADR-0046: The V1 write boundary — `ARCHEUS_HOME`, an Archeus-owned project-local namespace with per-entry ownership, and project-owned files only through named approved capabilities

**Status:** DECIDED (the user's migration decision pass of 2026-10-01; resolves LM-C1) · **Date:** 2026-10-01 · Implementation: holds for every phase from now; its static gate (MG-12) is built in P22 · Amends target-architecture §5.1 and migration-plan §5; extends ADR-0019 · Architecture: [legacy-context-migration.md](../legacy-context-migration.md) §3, §24

## Decision

**V1 never silently writes an arbitrary project-owned file.** Everything V1 writes falls in exactly
one of four places, and nothing else is permitted:

1. **`ARCHEUS_HOME`** — its V1-owned entries (target-architecture §5.1). All migration output lives
   here.
2. **The Archeus-owned project-local namespace `<project>/.archeus/`** — gitignored by its own
   `.gitignore` (`*`), never project-owned. Ownership is **per entry**, as in `ARCHEUS_HOME`:

   | Entry | Owner | V1 may |
   |---|---|---|
   | the directory and its `.gitignore` | legacy (created by `store.workdir`) | have it created through that legacy function, if absent |
   | `sessions/<session-id>.md` | **V1** (P12 D15) | write one per session, never overwrite, never read back |
   | `connections-cache.json` | **shared** (ADR-0019) | write only through `connections.build_hierarchy` |
   | `v1-cutover.json` | **V1** (ADR-0045 §12) | write only at a user-approved cutover of that project; remove at its rollback |
   | every other entry (`memory/`, `snapshots/`, `plan-latest.md`, `bash-log.txt`, …) | legacy | never write, move or delete |

   The mirror under a harness project folder (`<config_dir>/projects/<enc>/.archeus/`) is legacy's;
   V1 never writes it.
3. **Project-owned files and git state — only through a named, approved capability**, each
   attributable to a record, observable in the compatibility manifest (ADR-0045 §8), reversible
   where stated, and covered by a test:

   | Capability | What changes | Authority | Record | Reversal |
   |---|---|---|---|---|
   | task worktree | `git worktree add` registers under `<repo>/.git/worktrees/` and creates a task branch; removed after the task | an authorised execution (P9, P11) | Execution | `git worktree remove`, branch deleted by the same lifecycle |
   | verified merge | the mission's verified change enters the user's working tree | an approved mission, verified and reviewed (P11, P13) | Execution + merge record | the user's git history |
   | cutover opt-in | Archeus-managed blocks in `CLAUDE.md` / `AGENTS.md`, `.claude/rules/archeus-mem-*` | the user's per-project cutover approval (ADR-0045 §12) | migration run + opt-in list | restore from the pre-change copy (ADR-0045 §10) |

4. **User-level harness configuration** — only the ADR-0019 shared latch
   (`~/.claude/archeus-limits.json`, through `quota.note_limit`) and, at a user-approved cutover,
   V1's hook entries in an account's `settings.json`, through the existing atomic
   read-modify-write helper, removed at rollback. Per-execution hook settings live in
   `ARCHEUS_HOME/run/`.

A new write site anywhere else is a decision that amends this record first.

## Why

target-architecture §5.1 said V1 writes only `ARCHEUS_HOME` plus two shared files, while P12 D15
decided — and V1 builds (`archeus/core/sessions/service.py:34-39`) — per-session delivery copies in
`<project>/.archeus/sessions/`, and P11 already changes a repository's git state for task
worktrees. The sentence was stale, not the code. Removing the P12 capability to match the words
would have lost a decided feature; the fix is to name the boundary precisely. `<project>/.archeus/`
has been Archeus's own space inside other people's projects since before V1 (gitignored by
construction because it holds command logs and transcripts), so it is the right place for V1's
project-local files and the wrong place to treat as project content.

## Alternatives

Move the delivery copies into `ARCHEUS_HOME` (rejected: P12 D15 needs a path the target session can
read inside its own project); treat `.archeus/` as V1-owned wholesale (rejected: two writers of the
legacy memory, ADR-0019); a V1 subfolder with no ownership table (rejected: invites the next write
site without a decision).

## Tradeoffs

One more marker file per cut-over project; one static gate to maintain.

## Consequences

target-architecture §5.1 gains the boundary table; migration-plan §5 lists `sessions/` and
`v1-cutover.json`; testing-strategy §9 MG-12 walks `archeus/` for write sites outside these four
places, and MG-6 attributes every observed difference to one of them.
