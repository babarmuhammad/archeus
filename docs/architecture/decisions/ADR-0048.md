# ADR-0048: D-25 — account identity, usage measures, own calls as consumers, and the legacy boundary of AP-1

**Status:** DECIDED (resolved 2026-10-01 under the user's D-25 directive of that day; every rule below is derived from the decided records it cites plus the coexistence invariant the directive states — none is a new preference; two derivations are flagged for the user's confirmation under "Confirmation points") · **Date:** 2026-10-01 · Implementation: **AP-1** (the whole of "AP-1 scope" below), P21 (own calls as `live_work` items), P22 (the legacy-seam tooling and the account import), P25.5 / P26 (ownership transfer and legacy retirement) · Resolves the D-25 finding in ADR-0041 ("Why AP-1 first"); amends ADR-0041 §3 (one word, see "Conflicts"); enforces ADR-0022's "until P10"; reads ADR-0019, ADR-0021 (OPEN), ADR-0023, ADR-0037 (PROPOSED), ADR-0043, ADR-0045, ADR-0046, ADR-0047 · Gates: testing-strategy §8 (AP-1, AP-ID, AP-UK, AP-CC, AP-RT, AP-LG, AP-WB, AP-RB)

## Context

The AP-1 readiness audit (2026-10-01, at `a22d926`) found that ADR-0041's protection, once built,
would still not reach five paths, and recorded the scope question as D-25:

- Claude Code's own-call account, when no Claude Code account is registered, is chosen **before**
  the router by legacy `rotate.elect()` once rotation is permitted (`archeus/harnesses/calls.py:70-76`).
  `rotate.elect()` reads an unpolled account as 0% and knows no V1 policy.
- One home has two identities: a task's unregistered account is `claude_code:default` with no home
  (`archeus/core/application/resources.py:357`; the process inherits Core's environment), an own
  call's is `claude_code:<config dir>` (`archeus/harnesses/calls.py:76`). A review's
  "not the account that did the work" exclusion (`archeus/core/verification/reviewer.py:81-96`)
  therefore never matches it.
- No adapter declares which usage measures it reports (`archeus/harnesses/base.py:57-68`), and
  missing figures become 0 in three places: `_usage` (`archeus/harnesses/calls.py:30`),
  `ledger_totals` (`resources.py:171`), and an execution that reports nothing writes no ledger row
  at all (`archeus/core/application/executions.py:282-288`). An execution that ends without the
  harness's own total (no `result` event) is ledgered with its last per-turn figure.
- Own calls are not executions; their in-flight state (a RouteDecision with no `outcome`,
  ADR-0043 §1) is counted by nothing, and four own-call threads run with no limit.
- The legacy application makes about sixteen own calls (memory, lessons, review, CLAUDE.md,
  brief, hooks/agents/skills generation, MCP analysis, system prompt, plan, council, loops) on the
  active or thread account, with `quota.preflight` able to switch silently to an account with
  headroom (`headless_quota: auto`). No V1 policy reaches them and V1 calls none of them.

The directive adds a binding operational invariant: **the current Archeus stays fully usable while
V1 is built**, and before P25.5/P26 V1 may observe, snapshot, validate and prepare, but must not
rewrite or migrate memory, replace project instructions, take ownership of project files, disable
legacy rotation or legacy own-call consumers, change a project's working behaviour, silently
redirect current Archeus calls through V1, or retire legacy stores. AP-1 must not become a
migration or cutover mechanism.

## Decision

**Provenance between the two systems (D-25.5).** A V1 consumption is a RouteDecision (and, for a
task, an Execution) plus its UsageLedger row in `ARCHEUS_HOME/archeus.db`, with the account key of
§2. A legacy consumption is recorded only in legacy stores and never enters the V1 ledger. The two
meet in exactly one place, which is shared on purpose and unchanged: the rate-limit latch
(`quota.note_limit` / `quota.reason`, migration-plan §5). Consequences, stated rather than
hidden: a **window ceiling** sees legacy use (the provider's window includes it); a **budget** and
**concurrency** count V1 Core's consumption only — "how much Archeus V1 may spend", not the
account's total — until legacy retirement.

### 2. Account identity model

| Case | Account key | Home | Notes |
|---|---|---|---|
| Claude Code account A, registered | `acc_…A` (its `Account.id`) | `C:\Users\<u>\.claude` | the key for policy, ledger, RouteDecision, Execution, review exclusion |
| Claude Code account B, registered | `acc_…B` | `C:\Users\<u>\.claude-work` | a second `register_account` on `…\.claude` is refused: one home, one account |
| pi account A, registered | `acc_…P` | `C:\Users\<u>\.pi\agent` | pi's offers are this home's (C-22) |
| another harness's account (Codex) | `acc_…X` | its `CODEX_HOME` | keys never cross harness ids: a Claude home and a pi home are two accounts even if both reach one provider account — that identity is not knowable from Core and is not claimed |
| default, unnamed (no Claude Code account registered) | `claude_code:c:\users\<u>\.claude` | whatever `default_account()` resolves (today `config.resolve_config_dir(None)`: the environment, then the user's setting, then the default) | offered only while the harness has no registered account; never rotated |
| an own call on A | RouteDecision `account_id = acc_…A`; ledger row the same | — | in flight until its `outcome` |
| a task execution on A | Execution `account_id = acc_…A` | spawned with `account_env(home of A)` | unregistered: `account_ref = claude_code:c:\users\<u>\.claude` and the same home in its environment |
| a continuation of that execution | a new Execution with its own RouteDecision; affinity `(claude_code, acc_…A)` | — | re-routed through P9 and P10; affinity is an ordering key, so AP-1's partition and protection apply first (ADR-0047 §8) |
| a retry | a new Execution, routed afresh | — | no carry-over but affinity |
| a user session (ADR-0023) | the account key it was launched on | — | not counted in `concurrency` (D-25.4 counts Archeus's live work; a user session is the user's own use) |

**Recognising one real account everywhere.** Within V1 a real account has exactly one key: either
it is registered (one `Account.id`, unique per canonical home) or it is the unregistered default
(one adapter-produced key), and the two never coexist in one snapshot because the default
disappears once the harness has a registered account. History compares keys only. A legacy
account becomes a V1 account only through the P25.5 import, which matches it by canonical home.
**Ceiling:** an account with no home (an API key held elsewhere) is identified by its
`Account.id` alone; registering the same key twice is a user action visible in the account list,
not a silent consumption.

### 3. Usage and budget model

| Term | Meaning | Stored as |
|---|---|---|
| **reported** (`basis: reported_total`) | the harness's own total for that consumer (Claude Code's `result` event; an own call's JSON envelope) | the figure |
| **partial** (`basis: partial`) | a figure the harness reported that is known not to be the total — an end without the harness's total (killed, lost, halted for a hand-off): a lower bound | the figure, marked partial |
| **unavailable** (`basis: none`) | the consumer ran and the adapter reported nothing for this measure, or does not declare it | `None` |
| **unknown** | any value that is not reported: partial or unavailable. Never filled, never defaulted | `None` or a marked lower bound |
| **estimated** | **no consumption is ever estimated.** The only estimates in the system are ADR-0047's window estimate (labelled `estimated`) and the router's `projected` bump, which is a policy margin on a window, not usage | — |
| **token usage** | measure `tokens` = `tokens_in + tokens_out` (cache figures recorded, not budgeted) | per figure |
| **cost** | measure `cost` only where the adapter declares that its figure is what the account is charged. AP-1 declares `cost` for **no** current adapter (Claude Code reports a cost figure whose meaning differs by auth kind; declaring it is evidence for a later change, not an AP-1 assumption), so a `cost_per_day` budget is refused at write on every current real adapter | per figure |
| **concurrency** | live work on the account key: live executions plus own calls in flight (D-25.4). Computed by Core from its own rows, so it is never unknown | a count |
| **ceiling** | `allocation − reserve` (− brain reserve for tasks) over the provider's **window** (resource-router §4), unchanged | from UsageSnapshot |
| **reserve** | headroom of the provider's window kept for the user (`reserve_pct`) and for the brain (`brain_reserve_pct`), unchanged | policy |

**Order inside `allocation`, every account (ADR-0041 §3):** window ceiling when a window is known
(as built) → then budgets whenever set (new: also on windowed accounts) → an account with no
window and no budget stays fallback-only (as built). Each budget: refused at write if its measure
is not declared; at route time `consumed ≥ budget` → reached; `complete = False` and the lower
bound below the budget → unevaluable → eliminated with "budget tokens_per_day cannot be evaluated:
usage partly unreported", fallbackable. `concurrency` is always evaluable.

**Why missing usage can never become zero.** (1) Adapters return `None` for an absent figure —
there is no `or 0` between a harness and the ledger. (2) Ledger figures are nullable and carry a
`basis`; a row is written on **every** end of a consumer that ran, so "no row" cannot hide a
consumption. (3) `ledger_totals` sums a measure only when every row in the period reports it as
`reported_total`, and otherwise returns the lower bound with `complete = False`. (4) The router
reads `complete = False` as unevaluable and eliminates; there is no branch where an incomplete
total passes. (5) A budget on a measure nobody reports cannot exist (refused at write). (6)
Readers render `None` as unknown (ADR-0043 §3, G12). Each step has a mutation gate (§8); removing
any one of them fails a test.

**Governs:** every registered account of every auth kind and harness, and each harness's
unregistered default account (which can only be `normal`: it has no policy); every V1 Core
consumer — first dispatch, retry, continuation, resume, and the planner, brain, knowledge
extraction, lesson and review own calls.

**Does not govern yet:** the legacy application (D-25.5); a user's own sessions (ADR-0023:
recorded on their account key, not counted); `limits` by subject, tier or task family and project
default preferences (P22, V1.x-O1); the effective-policy read (P21); own calls as `live_work`
items and account consumers in `/v1/accounts` (P21); per-preference provenance (`set_by`,
`message_id`), which P19 must add before the conversation may write a preference (ADR-0042 §3) —
until then every stored preference is user-device-set by construction (`resources._user`);
pins (P22 / V1.x-O2: AP-1's lift is by preference only); any ADR-0021 answer.

**Leaves untouched:** every file under `claude_sessions/`, legacy settings, legacy rotation and
`quota.preflight`, legacy memory and stores, every project file, CLAUDE.md / AGENTS.md / rules,
the shared rate-limit latch. AP-1 writes only `ARCHEUS_HOME/archeus.db` (and its pre-migration
copy in `ARCHEUS_HOME/backups/`, both V1-owned).

**Deferred to:** P21 (own-call `live_work` items, consumers per account, the effective policy);
P22 (Resources UI for every field, limits, project defaults, the legacy seam and import tooling);
P25.5 (account import with the user's class for each account, per-project cutover); P26 /
retirement (legacy rotation and preflight end).

### 8. Gates (testing-strategy §8)

Every gate is mutation-verified: a mutant that removes or inverts the rule must fail it, and the
run is recorded with the slice (`tools/mutate_ap1.py`).

| Gate | Asserts | Mutants that must fail it |
|---|---|---|
| **AP-1** protection invariant (amended) | over generated snapshots no `last_resort` account is elected while a `normal` candidate survives, whatever its affinity, preference or priority; no `explicit_only` account is elected unless a user-device preference names it, and the lift is scoped to that mission (G9); a shared account marked `last_resort` with `fallback: ask` is reached only through `ask`; every elimination and the partition carry a reason | partition removed; partition after ordering; `last_resort` treated as `normal`; `explicit_only` automatic; lift unscoped; reason dropped |
| **G10** budgets always | a budget on a windowed account is enforced; none set → behaviour unchanged; a budget on an undeclared measure is refused at write | budget check skipped when a window is known; write validation removed |
| **AP-UK** unknown usage | an adapter's absent figure is `None`; every end of a consumer that ran writes a row; a period with a `partial` or `none` row makes the budget unevaluable and eliminates; the lower bound reaching the budget reads "reached" | `or 0` reintroduced in `_usage` or `ledger_totals`; the row skipped when usage is empty; `complete` ignored; unevaluable passed |
| **AP-CC** concurrency | live executions and in-flight own calls on one key both count; at the cap a task and an own call are both refused; an own call past its bound no longer counts | own calls not counted; own calls exempted; the bound removed |

## Conflicts found, and the smallest corrections

1. **ADR-0022 vs code.** ADR-0022 limits the `rotate.elect()` account source to "until P10"; P10 is
   built and `archeus/harnesses/calls.py:75` still calls it. Not a decision conflict: code that
   outlived its ADR. AP-1 removes the call (D-25.1); ADR-0022 gains a pointer.
2. **ADR-0041 §3 "concurrency caps the account's live executions".** Under ADR-0043 §1 an own
   call in flight is live work too, and the user's own requirement for this budget (E-4, "do not
   consume all concurrent slots on account A") cannot hold if own calls sit outside the count. The
   smallest correction is one word, recorded as an amendment note and leaving the decision text as
   it was: *live executions* reads *live work (ADR-0043 §1)*. (Confirmation point 1.)
3. **ADR-0041 §3 "a budget is accepted only on a measure the adapter reports"** had no mechanism:
   no adapter declares its measures. Not a contradiction; resolved by D-25.3 inside the existing
   adapter capabilities (ADR-0047 §1's own precedent), not by deciding ADR-0037.
4. **domain-model §8.5 `UsageLedger`** lists `tokens_in`… as plain integers (the code defaults them
   to 0). Corrected to nullable with `basis` (D-25.3).
5. **The decision register** had no D-25 row (it went D-24 → D-26). Added.

No frozen design gate is edited: the router's behaviour is amended through this ADR and ADR-0041,
as ADR-0047 amended p12 §10.1.

## Confirmation points

Both follow from the records and are what AP-1 will build; they are named because each has a
visible cost the user may prefer to trade differently.

1. **Own calls are blocked at the concurrency cap** (D-25.4). Cost: while an account's slots are
   full and no other account is free, the brain, planner, extraction and review wait. The
   deterministic verbs still work. The alternative — own calls counted but never blocked — would
   need a "brain reserve" for concurrency that no record defines.
2. **A budget with partly unreported usage fails closed** (D-25.3). Cost: one execution that ends
   without its harness's total (a kill, a lost process, a hand-off with no `result` event) makes a
   `tokens_per_day` budget unevaluable for the rest of that day, so the account is reached only by
   its fallback mode. The alternative — counting known figures only — is the "missing usage as
   zero" the invariant forbids.

## Alternatives

Implicit V1 policy for every legacy account (rejected: that is the P25.5 account import, done early
and without the user's per-account answer); routing legacy own calls through Core before AP-1
completes (rejected: a silent redirect of the current application, forbidden before cutover);
making ADR-0037 a prerequisite (rejected: ADR-0047 §1 already places harness declarations in the
adapter capabilities until ADR-0037 is decided); counting known usage only (rejected: unknown
becomes zero); own calls as Executions (rejected: ADR-0022, ADR-0043 §1).
