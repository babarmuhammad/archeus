# ADR-0053: Executions run under an isolated OS identity inside a Core-held Job, and Core bounds every privileged effect by attested origin (PV-20, a V1.x security remediation)

**Status:** DECIDED — architecture approved; **implementation authorised for slice S0 only** (the Gap A three-state sentinel determination, built 2026-10-08 — p20-design-gate §12 item 101); the isolation mechanism is not started and not authorised (the owner's PV-20 rulings §6.1–§6.11, the six §7.2 decisions, and the blocker decisions A1–A6 with the A7 correction of §7 below, 2026-10-07) · **Date:** 2026-10-07 · Required by **ADR-0051 Decision 5** ("its design needs its own ADR") · Design: [../pv20-execution-isolation-design.md](../pv20-execution-isolation-design.md) · Study: [../pv13-windows-os-confinement-study.md](../pv13-windows-os-confinement-study.md) · Remediates findings **G1** and **G2** (Critical, open — [../p20-design-gate.md](../p20-design-gate.md) §12 items 92–97) · Reads ADR-0007, ADR-0049, ADR-0051, ADR-0052; p11, p13 and p15 design gates; execution-architecture §2, §3.1, §4, §7, §8, §10

> **Evidence status.** Design approved; implementation limited to slice S0; empirical AppContainer, Claude
> CLI and transport evidence not yet established. Nothing in this ADR claims that AppContainer
> works, that the boundary exists, or that any acceptance row passes. Every statement about exact
> grants, capabilities, Windows behaviour or CLI behaviour is **DESIGN PROPOSAL — UNVERIFIED**
> (PV-20 §7.1, §7.3).

## Context

**Why the user-identity execution model is insufficient.** ADR-0051 Decision 1 accepted, for V1,
that a Claude Code execution runs with the user's OS identity, bounded only by the application
layer (policy, action classes, tool removal, the fail-closed hook, environment hygiene). P20 slice
G's read-only verification showed what that identity reaches in practice, at the boundary level:

- **G1 (Critical):** user-owned credential authorities whose secrets would authorise pushing,
  publishing or registry/SSH access. P11's `CAPABILITY_ENV` works as designed; the secrets live in
  stores the OS identity owns, which clearing an environment variable cannot remove.
- **G2 (Critical):** the local Core control boundary — the privileged local token and `run/`
  control state — which to Core's loopback API is the full-scope local principal past step-up.

These are OS-boundary findings, not P11 defects. The 2026-10-07 decision-matrix review added a
third path to the same material that confining the agent process alone would not close: **Core
itself runs execution-influenced code under the user's identity.** Verification runs a task's
test and build commands in its workspace as the user (`node.run_check`, called from
`core/verification/evidence.py`), and those commands are execution-written content. Core's own git
operations on execution-produced repository state are a second such path.

**Two independent layers, both required.** Neither is "merely defence in depth"; neither
substitutes for the other:

1. **OS confinement — the execution identity boundary (read-bounding).** An execution, and every
   process running code an execution influenced, runs under an identity that is not the user's and
   cannot reach user-owned secrets or Core-private state.
2. **The Core effect boundary (effect-bounding).** Core independently refuses every privileged
   effect to an execution-originated request, whatever the execution has managed to reach (PV-20
   §3.6). This is a **hard requirement** (ADR-0051 superseding decision; PV-20 §6.2).

**Prerequisites.** The PV-13 study (delivered 2026-10-07) recommends AppContainer as the primary
identity/ACL boundary wrapped in a Job object. Its empirical capability/ACE spike was attempted on
2026-10-07 and **did not complete** (PV-20 §7.3): AppContainer is neither proven nor disproven.
ADR-0051's superseding decision made OS confinement a **V1.x security remediation**.

## Decision

### 1. Mechanism and isolation establishment (PV-20 §6.1, §6.3, §6.11)

- **AppContainer + Job object** is the confirmed mechanism direction: AppContainer is the
  execution identity/ACL boundary; the Job is the process-tree envelope and the authority for
  execution lifetime. A Job is not an ACL boundary and never substitutes for the identity
  boundary.
- **A separate standard user** is an escalation path, used only if AppContainer evidence later
  proves insufficient (for example a credential authority it does not govern). Escalating is a
  **new owner decision**; nothing escalates automatically.
- **Windows Sandbox / a disposable VM** is an optional maximum-isolation tier, not the V1.x
  baseline.
- **No silent fallback.** If isolation cannot be established, the untrusted execution does not
  start. There is no fallback to the user's security context, and P11 §17's in-place mode is not
  a PV-20 fallback.
- **Isolation establishment is an all-or-nothing pre-spawn invariant** (PV-20 §3.4: identity
  exists; required grants established; prohibited broad grants absent; Job exists; the Core/mailbox
  boundary exists; the isolated spawn path is selected). No configuration setting disables it.
- **Failure to establish isolation means no spawn.** How such a failure is charged and whether it
  re-dispatches is P11's O7 (§5 below); whatever O7 decides, it never bypasses isolation.

### 2. The effect boundary (PV-20 §6.2, §3.6)

Core refuses to an execution origin every member of the **closed** privileged-effect set of PV-20
§3.6, which is the canonical list: publishing/pushing; privileged Core control; approving any
pending request, including the execution's own; policy modification; re-arm after a halt;
authoring halt, pause, handoff or approval state. Possessing an execution-context credential grants
none of them. Adding an effect to the set is a design change.

### 3. The six approved decisions (the owner, 2026-10-07)

Recorded in the order they were decided; each depends on those before it.

1. **R4b — verification authority: a confined verification identity (Option 2).**
   - Core-run verification of execution-influenced code (a check's test and build commands) runs
     under a confined verification identity, distinct from both the user's and the execution's
     identity, with no access to Core state, credentials or the local token, in its own Job, on a
     checkout at the recorded revision with no live writer.
   - Core holds the process handles and records the exit code and output itself, so the command
     observation keeps P13's "authoritative" meaning: *Core observed the outcome of a command at the
     recorded revision.* It never meant *trusted code*.
   - **Option 3 is the fail-closed degraded mode:** if the confined verification identity cannot be
     established, no execution-influenced code runs and the check is missing evidence, which P13
     resolves to ERROR or AWAITING_HUMAN, never PASSED.
   - **Option 1 is rejected:** execution-influenced code never runs under the user's identity.
   - **Completed by A6 (§7):** one fresh verifier principal per verification, never reused, whose
     authority is a subset of the execution's runtime/tool grants plus its own checkout and scratch,
     with network only if P23 permits it.
2. **R4a — repository topology: a separate execution repository, imported as data (R4a-B).**
   - An execution works in an execution repository separate from the user's repository.
   - Core brings results into the user's repository by an import that treats them as data and never
     honours the execution repository's configuration, hooks or refs.
   - The user's `.git` (config, hooks, refs, objects) is **not** exposed to an execution through a
     linked worktree.
   - P13 D12's rule (a task starts from the mission branch when it exists) is kept; its mechanism,
     and P11's workspace seam, change.
   - **Completed by A1 and A5 (§7):** every isolated execution of every task kind gets such a
     workspace; seeding is a copy of the base revision only (no linked worktree, shared objects,
     alternates or hardlinks); the import copies the working tree as data into a Core-owned
     repository, whose import commit is the canonical revision.
3. **R1 — execution origin: OS-attested origin at the connecting peer (R1-A).**
   - A peer attested as inside an execution boundary, or whose origin cannot be determined,
     receives no `user_device` authority and is refused every §3.6 effect, whatever credential it
     presents.
   - R1-A is sound only together with R4a and R4b closing every path by which execution-influenced
     code runs under the user's identity (to attestation, such code *is* the user).
   - **Scope (A3, §7):** R1-A is an allowlist, not a denylist. User identity alone is not
     sufficient; a forwarded request is never direct local origin; the verifier, forwarding hops,
     proxies and execution-influenced user-identity deputies receive no §3.6 authority.
   - **No silent substitution.** If attestation cannot be established on Core's local transport,
     nothing is substituted: a transport change, or step-up/presence for the whole closed set
     (R1-B) with any change it implies to P9 D16, P15 §6.6, D10 or V2-3, is a **new owner
     decision**.
4. **R3 — provider access: Core-brokered (R3-B), as the target.**
   - The execution holds no provider credential. Core brokers provider access through an endpoint
     that authenticates the execution as an execution principal with zero Core scopes, never accepts
     the local token, shares no authentication domain with `user_device`, and exposes no Core route.
     The broker must never become an R1 path.
   - This is conditional on evidence that the production Claude CLI can work through such a broker.
     If it cannot, scoped per-execution credentials (R3-A) require a **separate, explicit owner
     security decision**.
   - **Until one of the two is viable, isolated Claude Code executions do not run (fail closed).**
   - Network egress remains P23's.
   - **The account home stays outside the boundary (A2, §7):** an isolated execution's
     `CLAUDE_CONFIG_DIR` is a fresh per-execution directory holding no provider login.
5. **R5 — halt state: H2.**
   - Only Core authors halt, pause, handoff and approval state, and Core holds it in Core-owned
     durable state; Core's classification is authoritative.
   - The hook's halt and PreCompact records are untrusted reports carried on the execution's request
     input. A report can move an execution's classification only toward a non-advancing state; it
     can never manufacture success, an approval or any Core-authored state. A PreCompact report can
     only raise context pressure; Core decides any handoff.
   - An execution that ends while PAUSING or HANDING_OFF and that Core cannot classify from its own
     state resolves to halted at the boundary — **never ENDED_OK**. This changes `record_end`'s
     current classification.
   - After a Core restart, reports found are read as claims.
6. **R6 — Job ownership: Core-only (R6-A).**
   - Core is the sole holder of each isolated execution's Job, and the Job is configured so that
     Core's death terminates the isolated process tree.
   - No non-Core component holds lifetime authority, and no reference that could recover the Job
     exists outside Core's process.
   - On a Core restart there is no live isolated process to adopt: Core reconciles its records and
     resolves every remaining non-terminal execution through terminate/reap/fail, and reclaims
     stale profiles and grants. **A live isolated process is never re-adopted.**

### 4. Implementation constraints (not owner decisions)

- **R2 — resource layout.** The authority model is ruled (PV-20 §6.6). The implementation keeps
  seven resource classes on separate boundaries (PV-20 §7.5): (1) request input; (2) Core response;
  (3) STOP/PAUSE/HANDOFF sentinel state; (4) lifecycle/control state; (5) halt state; (6)
  local-token / Core-private state; (7) private execution state. Classes 4, 5 and 6 are Core-only;
  no lifecycle or classification decision reads an execution-writable file as authority. Exact
  access rules, directories and filenames are implementation work. Core-authored spawn
  configuration carries class 2's authority — Core writes, the execution reads (A2, §7); the
  execution's stream is execution-authored content even though Core holds its handle; an isolated
  execution's workspace and `CLAUDE_CONFIG_DIR` are class 7 (A1, A2).
- **R7 — profile granularity.** One execution-specific identity/principal, created before spawn and
  torn down after the execution; other executions' state is inaccessible; grants on shared runtime
  material are read/execute only, and that material holds no user secrets; Core-owned state is
  never granted. Whether the principal is a per-execution profile or a per-execution capability is
  a mechanism choice. It returns to the owner only if evidence shows a per-execution principal
  cannot be established.
- **Sentinel ordering.** The explicit three-state sentinel determination (present / absent /
  indeterminate → fail closed; PV-20 §6.10, Gap A) lands **no later than** the change that
  separates the sentinel from the mailbox. Before slice S0 (2026-10-08) an inaccessible sentinel
  read as absent and the observed fail-closed result came from the mailbox write failing next to
  it; separating the two without the determination would have failed open. S0 built the
  determination, so the ordering is met; row 7 is not thereby verified (PV-20 §7.4).

### 5. External dependencies

- **R8 — O7 (P11).** Charging and re-dispatch of an isolation-establishment failure is P11's
  `SpawnFailed` question (p20-design-gate §4.2 O7, §12 item 72), deferred to P11 by the owner and
  not redesigned here. PV-20 §3.4 requires P11's decision before implementation.
- **P23** owns network egress (G3), the baseline network capability, and network for verification.

### 6. Rulings carried unchanged (PV-20 §6.4–§6.10)

V1.x timing; G kept PAUSED / NOT CLOSED with G1 and G2 Critical and open; the split-authority
mailbox; the four repository categories; the Job as lifetime authority with restart as
reconciliation; harness scope (claims only on the real Claude Code path), **amended by A4 (§7):**
every production-dispatched execution, whatever its harness, runs under the PV-20 identity; the
three-state sentinel.

### 7. Blocker decisions (the owner, 2026-10-07, after the PV-20 architecture audit)

The final read-only architecture audit (2026-10-07) found seven blockers, A1–A7, in the documented
architecture. The owner approved A1–A6 in the direction the PV-20 blocker decision matrix
recommended; A7 is a documentation correction of contracts R5 and R6-A already fixed. **None
authorises implementation.** Recorded in the order the matrix recommended deciding them.

1. **A4 — harness identity: H-1.**
   - Every execution dispatched by a production Core, whatever its harness, runs under the PV-20
     execution identity and inside its Core-held Job.
   - A harness's own sandbox (for example Codex `--sandbox`) is an additional inner layer, never a
     substitute for PV-20. No harness has an exception.
   - A harness that cannot launch inside the PV-20 identity is **not eligible for production
     dispatch** (fail closed).
   - Fake and test harnesses are not production-dispatchable, and their results are never
     AppContainer confinement evidence.
   - A PV-20 property is claimed for a harness path only on evidence from that path.
2. **A1 — workspace: A1-1.**
   - Every isolated execution, of every task kind, runs in a Core-established workspace distinct
     from the user's project root, the user's `.git`, and resource classes 1–6.
   - A project whose first root is a git repository: a separate execution repository seeded from
     the recorded base revision (P13 D12: the mission branch when it exists, otherwise HEAD). A
     detached HEAD is seeded from the recorded commit.
   - No project: an empty execution-private workspace in class 7 — never the bare `run/exec/<id>/`.
   - A project root that is not a git repository is **structurally refused**.
   - `workspace_mode: in_place` is **withdrawn for isolated executions**. No case falls back to the
     user's project root.
   - A structural workspace impossibility is rejected **before dispatch** and never enters a
     spawn/retry loop. A transient workspace or isolation failure is an isolation-establishment
     failure: no spawn, charged and re-dispatched as P11's O7 decides.
   - Repository changes of every task kind reach the user's repository only through the A5 import
     and P13's merge-back.
3. **A5 — repository and git boundary: G-4.**
   - Core never runs git, or any program that reads git configuration, against an execution
     repository under the user's identity. The execution repository is untrusted data: its
     `.git/config`, hooks, refs, objects and index, and the attribute and configuration files that
     affect git behaviour (in-tree `.gitattributes`, `.gitmodules`, `.lfsconfig`), are never honoured
     by a Core git operation.
   - Seeding is a **copy of the base revision only** — never a linked worktree, shared objects,
     alternates, hardlinks, or any other mechanism that exposes the user's `.git`.
   - After the execution, Core copies its working tree **as data** into a Core-owned import
     repository. **Core's pinned import commit is the canonical revision**, recorded in Core state;
     the execution's own commits and HEAD are claims. Core's snapshot is that import commit, taken
     after the copy.
   - Every Core git operation over execution-derived content — the import commit, diffs and other
     git facts, the merge into the mission branch, materialising a verification checkout, push —
     runs under a **Core-pinned configuration** that prevents execution-controlled hooks, drivers and
     configuration from running.
   - R4b verifies a **fresh checkout of the Core-recorded revision**, materialised by Core, and binds
     the outcome to that revision.
   - **Confirmed by the owner (2026-10-07; PV-20 §3.2 category 4):** no repository-controlled or
     execution-derived git extension executes during a Core git operation on execution-derived
     content — repository-controlled hooks (the user's own included), filters, fsmonitor, diff and
     merge drivers, submodules, LFS transfer mechanisms, and any other execution-derived git
     extension. The Core-pinned configuration prevents their execution. Core cannot tell whether a
     user's own hook runs repository content, and R4b forbids running execution-influenced code
     under the user's identity.
   - **Core does not push content whose publication requires executing any of those mechanisms**
     (for example LFS-dependent content). That capability needs a separate owner decision.
4. **A6 — verifier: V-1.**
   - Every verification gets a **fresh verifier principal**: distinct from the user and from every
     execution, created for one verification, never reused, destroyed after Core records the
     result.
   - It has its own Job (held only by Core, so it dies with Core, and recorded in the process
     registry the item-83 stop uses), its own workspace (the A5 checkout), and its own scratch, home
     and temporary state.
   - It has **no** user credential, provider credential, broker credential, local token, hook token,
     mailbox, Core database or state, Core listener or loopback route, execution repository, or
     import repository.
   - It receives only the minimum runtime/toolchain grants the verification needs, plus its own
     checkout and scratch state. **No persistent or shared verifier cache.**
   - **Maximum authority:** a subset of the execution runtime/tool grants plus its own checkout and
     scratch, with network only if P23 explicitly permits it.
   - One verification can never influence another verification's state, credentials, authority or
     result. A check that needs anything outside these grants yields missing evidence — ERROR or
     AWAITING_HUMAN — never PASSED.
5. **A2 — account home and Claude configuration: A2-1.**
   - An isolated execution never receives the account home, a copy of it, or implicit access to
     account-home configuration. No legacy account-home behaviour is silently preserved.
   - Its `CLAUDE_CONFIG_DIR` is a fresh, Core-created, per-execution directory in execution-private
     state (class 7), holding no provider login, torn down with the execution.
   - Provider access remains R3-B, Core-brokered (or whatever a separate R3-A decision approves).
   - Core-authored spawn configuration (Archeus's hook settings, the MCP configuration, any
     materialised opt-in) is Core-write / execution-read only, outside that directory.
   - ADR-0049 opt-ins enter the boundary only as Core-materialised data, and only when they carry no
     credential authority.
   - **No MCP opt-in is admitted to an isolated execution** (confirmed by the owner, 2026-10-07).
     The rule is not limited to credential-bearing servers: Core cannot establish from a server
     definition that it carries no credential, and admitting servers on a structural check plus
     owner attestation (matrix option A2-2) was not approved. Changing it needs a new owner
     decision.
   - The account-level CLAUDE.md loads into an isolated execution only if opted in.
6. **A3 — R1 origin scope: allowlist + hop rule + deputy rule.**
   - **A trusted local §3.6 request requires both:** (1) the OS-attested connection origin
     satisfies the approved user-origin condition, **and** (2) the request arrived through an
     approved trusted path that is not an execution-influenced deputy or a forwarding hop. User
     identity alone is not sufficient.
   - Direct approved user-origin requests may receive §3.6 authority. Approved paired-device
     requests receive only what P15 and D10 permit.
   - **No §3.6 authority:** execution-originated requests; verifier-originated requests; forwarding
     hops; proxies; undetermined origins; execution-influenced user-identity deputies.
   - A forwarded request is never treated as direct local origin merely because the forwarding
     process runs as the user.
   - **Hop rule:** a hop that does not carry its originator's origin is permitted only if no
     execution or verification identity can reach it, or if it has no route to Core.
   - **Deputy rule:** no Archeus-owned process running as the user executes, or loads as
     configuration, execution-influenced content; Archeus's own model calls take such content only as
     prompt data. Clients render it only as data.
   - The verifier has no Core route and cannot become a privileged deputy.
   - The attestation mechanism is **not** chosen here; it belongs to the empirical phase.
   - R1-A's soundness precondition therefore names every path: verification (R4b, A6), the import and
     Core's repository operations (R4a, A5), every harness (A4), Archeus's own calls and clients
     (A3), and forwarding hops (P23).
7. **A7 — lifecycle authority: a documentation correction, not a new owner decision.**
   - `ENDED_OK` is an execution-level fact, not success. Core records it only from its own observed
     exit 0, under R5's conditions.
   - An execution-authored stream result is never treated as a process exit.
   - PAUSING and HANDING_OFF never reach ENDED_OK because an execution reports success: ENDED_OK
     from them needs a cause Core can classify from its own state, and no execution report is one.
     Otherwise PAUSING resolves to PAUSED (halted at the boundary) and HANDING_OFF to ENDED_HANDOFF,
     or either to ENDED_ERROR on a non-zero exit.
   - Ambiguous termination is non-advancing.
   - After a Core restart, isolated executions are not adopted (R6-A).
   - An `ended` tombstone Core wrote itself (class 4) remains an authoritative Core observation.
   - PASSED requires authoritative verification evidence; a missing verifier can never produce
     PASSED.
   - **Non-security policy details, still open:** ERROR versus AWAITING_HUMAN for a missing verifier;
     PAUSED versus failed for an execution PAUSING at a Core restart.

## Why

- **Effect-bounding needs an origin Core can identify** (PV-20 §8 row 4 was design-open for that
  reason). R1-A ties authority to the property PV-20 creates — the execution's identity is not the
  user's — and reopens no established decision; R1-B would reopen P9 D16, P15 §6.6, D10 and V2-3.
- **R1-A is unsound while Core runs execution-influenced code as the user**, which is why R4b and
  R4a come first. Option 1 of R4b is impossible under the PV-13 mechanism set: a Job is not an ACL
  boundary and a restricted token alone is too leaky, so any real boundary changes the identity.
- **A linked worktree shares refs, packed refs, objects, config and hooks at directory level**, so
  "no general authority over repository metadata" (PV-20 §6.7) probably cannot be expressed by ACLs;
  R4a-B makes "execution-produced state is untrusted input" a matter of structure.
- **PV-20 §3.1 bars any user-owned credential authority inside the boundary**; R3-A would place one
  there, which is why it needs its own security acceptance. ADR-0051's Context already cites the
  research recommending a credential proxy (F-22).
- **Everything the hook writes is execution-authored**, so no hook-originated halt record can be
  authoritative under any option; only Core's classification can be. Without a rule, separating the
  mailbox would turn every pause or handoff that exits 0 into ENDED_OK.
- **A Job that survives Core needs a second holder or a durable reference** outside Core's process,
  and a Core-down Job stop would be the parallel mechanism item 83 forbids. While Core is down the
  hook halts every execution within its wait anyway, so re-adoption would preserve little.
- **The blocker decisions (§7) close the paths R1-A's soundness depends on.** A harness running as
  the user (A4), a workspace in the user's project root (A1), Core running git inside an execution
  repository (A5), a shared or unbounded verifier (A6), the account home inside the boundary (A2),
  and a forwarding hop or user-identity deputy presenting execution-influenced requests (A3) are
  each a way for execution-influenced code or requests to reach Core as the user. A1–A6 apply the
  already-approved R4a, R4b, R3 and R1 to every such path instead of the code-change path alone.

## Alternatives (not chosen)

- **R1-B (step-up/presence) as primary:** reopens P9 D16, P15 §6.6, D10 and V2-3. Available only as
  a future owner decision if attestation fails.
- **R3-A (scoped credential) as target:** a user-owned credential inside the boundary, exfiltrable
  while G3 is open. Available only by a separate owner security decision.
- **R4a-A (linked worktree + ACL split):** cannot express per-ref authority unless proven; every
  Core git call would have to ignore execution-writable metadata.
- **R4b Option 1:** not possible as framed. **Option 3 as the design:** removes P13's command
  evidence for every code task; kept as the fail-closed mode only.
- **H1 (Core state only):** loses the halts the hook reports without contacting Core.
- **R6-B (Job survives, Core reacquires):** a durable reference or second holder, and a second
  Core-down stop path.
- **Windows Sandbox as baseline; restricted token alone:** PV-13 §5.
- **Blocker alternatives (the PV-20 blocker decision matrix):** A4 — a sandbox harness under the
  user's identity as an R4b exception (H-4). A1 — a read-only ACE view of the live project root
  (A1-2); refusing every non-worktree execution (A1-3); `in_place` for "read-only" kinds (A1-4, the
  silent fallback). A5 — Core git in the execution repository with hardening (G-1); a bundle
  produced inside the boundary (G-2, acceptable but not chosen); Core parsing git objects itself
  (G-3). A6 — one verifier per mission (V-2); a shared verifier with reset (V-3); checks in the
  execution's own identity (V-4). A2 — admitting MCP servers by structural check plus owner
  attestation (A2-2, a possible later decision); the account home with deny ACEs (A2-3); a copy of
  it (A2-4); an MCP credential broker (A2-5, a new mechanism).

## Consequences

- **Core-run verification can no longer execute execution-influenced code under the user's
  identity.** p13-design-gate §8.1 and D3, and execution-architecture §8, are amended (2026-10-07).
  As built, verification still runs as the user; that is the open remediation, not a closed one.
- **P11's workspace semantics must accommodate the separate execution repository** (p11-design-gate
  §17 and §28; P13 D12 keeps its rule, not its mechanism).
- **P11's live-process re-attachment is withdrawn for isolated executions** (p11-design-gate §15.3;
  execution-architecture §3.1, §4). Restart tests that adopt a live process become
  restart-and-fail tests for isolated executions when PV-20 is built.
- **P13 recognises a missing or unavailable confined verifier as missing evidence:** ERROR or
  AWAITING_HUMAN, never PASSED.
- **R3 remains conditional** on production Claude CLI feasibility; until it or a separately approved
  alternative is viable, isolated Claude Code executions do not run.
- **P23 continues to own network egress.**
- **The mailbox/resource layout must implement the seven resource classes** (R2).
- **The tri-state sentinel determination lands no later than the mailbox/sentinel split.**
- **The item-83 STOP file + process registry remains the only Core-down stop mechanism.** The Job is
  the execution lifetime boundary, not a second, independent stop authority (execution-architecture
  §10; PV-20 §3.7).
- **PV-20 acceptance rows 1, 4 and 5 stay design-open** — rows 4 and 5 until R1's attestation
  exists and is evidenced, row 1 until the production CLI is shown to work through R3-B's broker
  (its failure needs a separate R3-A decision); rows depending on R4a, R4b, R5 and R6 are
  design-complete and implementation- or evidence-blocked (PV-20 §8).
- **From the blocker decisions (§7; none implemented):**
  - *A4:* router eligibility gains a condition — a harness that cannot launch inside the PV-20
    identity is not eligible for production dispatch (PV-20 §3.8; ADR-0051 Current status).
  - *A1:* `workspace_mode: in_place` is withdrawn for isolated executions, so the planner's
    `in_place` default for non-`code_change` kinds, P11 §16's `in_place` admission rule and
    `integration_state = NULL` for in-place tasks no longer apply to them (p11-design-gate §16–§17,
    domain-model §7.3, p8-design-gate §7.1); non-git project roots are refused before dispatch.
  - *A5:* Core's as-built git operations in the execution workspace — `git_head`, `git_dirty`,
    `git_snapshot`, `git_merge_base`, the HEAD/branch read on every hook request (p11-design-gate
    §10.4 step 4), seeding by `git worktree add`, and merge or push that runs the user's hooks over
    execution-derived content — are boundary violations PV-20 removes (p13-design-gate §8.1, §8.3,
    §12.1, §12.2; execution-architecture §7).
  - *A6:* PV-20 §3.9's "wider than an execution's" is replaced by the A6 ceiling.
  - *A2:* the adapter's `CLAUDE_CONFIG_DIR` = account home and `config.account_env(home)` are
    replaced for isolated executions; `run/exec/<id>/mcp.json` is not written for them; ADR-0049's
    opt-ins are materialised as data (ADR-0049 "PV-20 consequence"; p20-design-gate §1.5, items 50 and 65;
    p11-design-gate §18; execution-architecture §2).
  - *A3:* "local" for a §3.6 effect means a direct, attested user-origin request through an approved
    path; P15 §6.6's credential locality and P9 D16's local step-up are necessary, no longer
    sufficient (p15-design-gate §6.6; p9-design-gate D16; api-and-realtime §5.1). Archeus's own model
    calls (planner, review, knowledge passes) fall under the deputy rule.
  - *A7:* state-machines §4, p11-design-gate §15.3–§15.4 and execution-architecture §5 are
    corrected.
- **G stays PAUSED and NOT CLOSED; G1 and G2 stay Critical and open** until PV-20 is implemented and
  its acceptance evidence passes. No document may describe V1 or V1.x as OS-confined before then.
