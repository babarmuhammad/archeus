# ADR-0043: Live work is executions and in-flight own calls, derived once; there is no Agent entity

**Status:** DECIDED (the user's decision pass of 2026-09-30, D-13; proposed in the third orchestration pass, `9dc1098`) · **Date:** 2026-09-30 · Implementation: P21 (reads, the `status` verb over them); P19.5 and later surfaces consume them where they exist · Reconciliation: [ARCHEUS_V1_CONVERSATIONAL_ORCHESTRATION.md](../ARCHEUS_V1_CONVERSATIONAL_ORCHESTRATION.md) A3, B3, C3, D5

## Decision

1. **No Agent entity.** An agent at work is an `Execution` in a live state, or an own call whose
   RouteDecision has no `outcome` yet. The mission stays the control room's unit; harness,
   account and model are execution metadata. Harness-internal subagents stay invisible to Core
   unless an adapter records them; nothing is invented to fill the gap.
2. **One pure derivation, `live_work(conn)`**, gives per item: kind (execution, or own call with
   its purpose); mission, task and project; repository and worktree/branch; harness, account,
   model (with `model_revision` and `served_model` once P21 records them), effort; task and
   execution states; plan step; what it has produced so far (checkpoints; recorded artifacts once
   P21's producer record exists); what it waits on (approval, a limit's reset, human acceptance, a
   dependency); and the resource constraint affecting it (the reason recorded by the decision that
   blocked or redirected it); and, for an execution, its context state (`context`: the recorded
   basis of its latest pressure, the derived quality and `remaining` only when window and usage are
   both known — ADR-0047 §9, PROPOSED; absent until that ADR is decided). It is served as a `live` section of `/v1/status`, not a new route,
   and it is the only source for the `status` verb, the operations strip, Happening now, the
   operations map and Control → Resources.
3. **Account consumption** joins `account_view` in `/v1/accounts`: its live consumers (from
   `live_work`), ledger totals by period, mission and subject kind, the window utilisation with
   `observed_at` and `resets_at`, and **unknown shown as unknown** — no number is derived from a
   missing reading.
4. **The effective policy** (ADR-0041 §5) is part of the same view.
5. **Visual DNA holds** (ADR-0024…0028): an item exists only while its row does; motion only for a
   real `execution.*` frame; own calls emit no frames and never animate; a model, provider, harness
   or role is never a colour.

## Why

"Which agents are working, on what, with which account" has no answer today: there is no
fleet-wide read of executions (only per id and per task), `/v1/status` returns world status
(`archeus/api/routes.py:283-285`), an own call that is consuming an account is visible nowhere, and
the ledger is read only inside one route decision (`archeus/core/application/queries.py:199-205`).
The specification and the visual rulebook already decided that the mission, not the agent, is the
user's unit (System Specification line 1114; rulebook §6 O-1), so the answer is a derived read over
the records Core already keeps, not a new entity. One derivation behind every reader is the same
pattern as ADR-0036's `offer_state`: the conversation, the strip and Resources can never disagree.

## Alternatives

An Agent entity with its own states (rejected: a second lifecycle that must be kept in step with
Execution and would invite decorative state); a new `/v1/live` route (rejected: `/v1/status`
already exists, is unused by the SPA, and is what the `status` verb answers from); composing live
work in the client from per-mission reads (rejected: P19 — no logic in clients).

## Tradeoffs

`/v1/status` grows; readers that need only world status ignore the section.
