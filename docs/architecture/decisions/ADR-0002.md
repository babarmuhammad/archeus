# ADR-0002: SQLite with a single writer and a transactional outbox

**Status:** DECIDED · **Date:** 2026-09-23

## Decision

SQLite (WAL) is the relational source of truth. One writer thread executes all commands; each command writes entity rows and appends domain events in the same transaction. Side effects run in outbox consumers after commit, each with a cursor and an idempotent-effects table. State tables are the truth; events are audit, trigger and realtime feed. Not full event sourcing.

## Why

Transactions make current state trustworthy; same-transaction events make history complete and let automation and realtime rely on it. One writer removes lock contention and makes claim-and-advance scheduling trivially atomic. Event sourcing would force every read model to be rebuilt from events, which is more machinery than a single-user system needs.

## Alternatives

JSON files (today); Postgres; full event sourcing; git as the event store (Munder Difflin — rejected because of repository bloat and lock contention the authors already work around).

## Tradeoffs

A single writer caps write throughput (hundreds of commands per second is ample). SQLite file locking across processes is avoided by making Core the only writer.

## Consequences

Hooks and the CLI must go through HTTP. Migrations use `PRAGMA user_version` with backups. Events have retention and a 410 resync path.
