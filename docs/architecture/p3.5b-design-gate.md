## 2. P3.5b scope

**P3.5b is the rest of plan §31.1 P3.5:** make the accepted skeleton reachable from outside the
Core process.

**In scope:**
- the HTTP API (a minimal route table, §5.1);
- the SSE stream with replay (§6);
- local authentication and coarse route scopes (§4);
- a Host allowlist, a fetch-metadata allowlist and security headers including the CSP;

- the generated API doc and TypeScript client;

- the `v1-client` CI job.

**Also in scope (added by §18.1):** a **boot reconciliation sweep**. At startup it reconciles every execution the database holds in a non-terminal state, whatever state its mission is in. It reads the database plus the per-execution files, and uses neither the process registry nor stream tailing.

- the `execution.progress` event (P11);

**Explicitly excluded:**
- P4 (world, `CoreClient.status()`);
- P9 (trigger authorization, approvals, PolicyDecision rows);
- P10 (routing, accounts, allocation);
- P11 (live process control, adoption, e-stop, pause/stop of executions);
- P15 (pairing, remote access, the device management UI);
- P16 (the full information architecture, the inspector, `/v1/now`);

## 3. D1–D7 decisions

### D1 — SPA libraries

**Decision:** the P3.5b SPA uses React 19 + Vite (ADR-0011, DECIDED) and the browser's own APIs.

- **No TanStack Query and no React Router in P3.5b.**
- The native APIs used are `fetch` with a streaming body, IndexedDB, the Web Locks API, `BroadcastChannel` and `history.replaceState`.
- Q4 (plan §33, PROPOSED, "needed by P3.5") is re-targeted to P16. **USER** confirms.

**Why:**
- P3.5b has two read-only lists fed by one query each (`GET /v1/missions`) and one event stream.
- The re-query rule of ADR-0009 ("on an event whose subject is on screen, re-query it") is one small hook here: refetch the list when a `mission.*` event arrives.
- Two views are one piece of state, not a router.
- Adopting either library now would fix Q4 while the only thing using it is two lists. That ties P16's decision to a skeleton that exists to be thrown away (plan §31: "a disposable end-to-end run").

**Role each would have had:**
- TanStack Query: a cache keyed by resource path and invalidated by event subject (ui-architecture §2 `data/`).
- React Router: URL routes for the surfaces of ADR-0014.

Both earn their place when P16 has many surfaces sharing one cache.

**Alternatives considered:**

| Alternative | Rejected because |
|---|---|
| Adopt both now | Premature coupling, larger bundle, Q4 decided by default |
| Vanilla TS without React | Contradicts ADR-0011 |
| Only TanStack Query | Still decides Q4; not needed for one query per view |

**Kept from ADR-0009 even though P3.5b is small:** one stream per browser, by electing a leader tab with Web Locks and sharing events over `BroadcastChannel`. These are platform APIs, not dependencies. Without them a second tab on the same device uses up the two-streams-per-device limit.

### D2 — Authentication versus authorization

The authoritative text is plan §27. "Authorization: principal scopes …; **the route table declares the
required scope per route**" is part of the P3.5 design (`api/auth.py` in plan §31.1 P3.5).
"Which principal may fire which trigger" is P9 (accepted P3/P3.5a invariant). The line between
them:

| Question | P3.5b answer |
|---|---|
| What proves the client is authenticated? | a device token (`dev_` + 256-bit `secrets.token_urlsafe(32)`) sent as `Authorization: Bearer <token>`. Verified by `sha256(token)` lookup in `tokens` plus `hmac.compare_digest` on bytes, `kind = 'device'`, `revoked_at IS NULL`, `expires_at` NULL or in the future, and the device `ACTIVE` |
| Where does a client get a token? | **the CLI and TUI:** the local token, read from `<home>/run/local-token`. It is minted by Core on first start, for a `user_device` principal with a `Device(name='local', platform='tui')`. **The SPA:** a launch-code redemption (D7) mints a token for a new `Device(platform='web' or 'desktop')`. Pairing is P15 |
| How is it stored? | Core stores only `sha256(token)` (P2 rule). The local token is stored in `run/local-token` (D5). The SPA keeps its token in IndexedDB. A token is **never** put in a URL, a log line, an event payload or an idempotency record |
| How is it revoked? | `POST /v1/devices/{id}/revoke` (scope `admin`) runs one writer command: `Device` ACTIVE → REVOKED (`revoke` edge) plus `tokens.revoked_at`. After commit, and before the HTTP response, the handler closes that device's live streams (state-machines §12, "in the same request"). A revoked local token is re-minted at the next `archeus core` start |
| What is a scope? | a coarse capability of the **credential**: the `tokens.scopes` of the presented token, which must be a subset of the principal's `PRINCIPAL_SCOPES` when minted. Each route declares one required scope; a token without it gets `403 scope_required {scope}` **before** any command is submitted or any query runs |
| What does each scope permit at this layer? | `observe`: every GET and the event stream. `control`: the mission commands `create`, `pause` and `resume`. `approve`: **no P3.5b route**; it is reserved for P9 approval decisions. `admin`: minting launch codes and revoking devices |
| Which scopes each credential gets | local token: `observe control approve admin`. Launch-code device: **`observe` only (USER D-scope)**, because the P3.5b SPA is read-only |
| What P3.5b must NOT decide | whether a principal may fire a given trigger on a given subject. Also: any per-mission, per-project or per-workspace permission; approval semantics and step-up; binding a decision to an action hash; storing PolicyDecision rows; policy profiles. The HTTP layer never branches on `actor.kind` and never evaluates the Policy port; it only passes `actor=Ref('user_device', principal_id)` into the command |
| How P9 connects | P9 authorizes **inside the application layer**, where commands already receive `actor`. It uses the authenticated principal that P3.5b hands over, together with the Policy port, and records decisions. P9 adds no HTTP middleware. A P9 refusal is a typed error that the §5.5 table maps to an HTTP status (`403` or `423`). P9 may make the route scopes finer; it never replaces authentication |

### D3 — `PolicyDenied` and HTTP 423

**The conflict:** api-and-realtime §1 says `423 policy_denied (includes PolicyDecision id)`, but P9 defers durable PolicyDecision rows. `PolicyDenied.decision.id` exists only in memory; a `GET /v1/policy-decisions/{id}` would 404.

**Decision:** the P3.5b contract is

```json
423 {"error": "policy_denied",
     "detail": {"task": "<task key>", "action_class": "<class>", "decision": "DENY",
                "reason": "<the policy's reason>"}}
```

- There is **no `policy_decision_id` field** until P9 persists decisions. P9 adds it as a new field, which does not break the API version.
- The field is left out entirely, not sent as `null`, so no client code grows around an id that does not exist.
- api-and-realtime §1 is amended when this is implemented.

**No P3.5b route can raise `PolicyDenied`.** Only `Work.propose_plan` and `Work.dispatch_task` raise it, and only the engine calls them. So in P3.5b:
- the 423 mapping is tested at the error-translator level;
- over HTTP, a DENY stays what P3.5a accepted: the mission remains in its state with nothing written, and there is no durable explanation until P9 (plan §31.1, deferral 5);
- the engine does not retry it in a loop (parking, §5.3).

### D4 — Who drives the engine in an HTTP Core

**Composition, in start order:**
1. Acquire the lock (§7).
2. `Database.open` starts the writer thread.
3. Ensure the local token (§4).
4. Start the engine thread.
5. Bind the HTTP server.
6. Write `core.json`.

Stopping runs in the reverse order (§5.4).

- **One engine instance per Core.** It is built once by the Core runtime and only there (a structural test lists who may construct `Engine`). It runs on one thread named `archeus-engine`. **It is never restarted inside the same process.** A new `Engine` instance treats every execution the old one started as not its own and kills it. That is the adoption boundary, and it belongs to P11.
- **Coexisting with the single writer.** The engine thread and the HTTP threads all submit commands to the one writer queue. The writer runs them one at a time, which is the only ordering there is. Engine steps and HTTP handlers never hold a transaction. Spawning a process and waiting for it happen on the engine thread **between** commands, exactly as in P3.5a.
- **The loop and parking.** One pass steps every mission that is not in `engine.SETTLED`, unless it is parked. A step that changed nothing parks the mission at its current `version`. A parked mission is stepped again only once its version changes, that is, when some command moved it. When a pass makes no progress, the thread waits on the writer's commit notification (§6.3) with a timeout (`idle_s`, 1 s by default). This keeps a mission refused by DENY in REASONING, a mission waiting in REVIEWING after a rejected review, and a blocked task from turning into a hot loop.
  - Ceiling: a change that does not bump the mission's version cannot wake it. No P3.5b command makes such a change. P11 revisits this when it adds task-level control.
- **Races with HTTP commands.** A user command can move a mission between the engine reading it and firing a trigger; for example, a cancel between reading CREATED and firing `start`. The engine then gets `IllegalTrigger`, `GuardFailed` or `VersionConflict`. The loop treats these three as **a lost race**: log one line, skip the mission, and re-read it on the next pass. The accepted guards already refuse the stale move, so nothing is bypassed. Any other exception is an engine failure.
- **When the engine thread dies,** Core fails and stops: it logs to `<home>/logs/core.log` and runs the §5.4 shutdown with exit code 3. It does not restart the engine in-process (see the adoption boundary above). The next `archeus core` reconciles.
- **Blocking ceiling (from P3.5a):** `Engine._finish` waits for the child process on the engine thread, so other missions wait meanwhile. Commands and streams are unaffected because they run on their own threads. This is accepted for the skeleton; the P11 execution manager removes it.
- **When Core is killed:**
  - the OS releases the lock;
  - `core.json` goes stale;
  - detached fake children keep running;
  - any in-flight writer transaction was not committed.
  
  On the next start, the engine's first pass reconciles each unfinished execution (kill by pid + create_time, attempt ended, task retried with a **new** execution after the old one has ended). This is P3.5a behaviour and is not changed.
- **Reconcile, never adopt.** Deliberate and accepted. ADR-0008 describes the V1 target, where Core adopts live processes; the plan schedules adoption in P11.
- **No second competing engine.** This follows from the lock (§7) plus the rule that nothing but the Core runtime and `InProcessClient` hosts an engine. Both take the same lock (§7).

### D5 — Windows local security (the minimum V1 guarantee)

**What is secret:**
- only `run/local-token` (plaintext at rest);
- launch codes, which live in memory only;
- device tokens, of which Core stores only hashes.

The other files are not secret: `core.lock` (empty), `core.json` (`{pid, create_time, port, started_at, version, schema}`) and the per-execution files. `core.json` still matters for integrity.

**Guarantee, POSIX:**
- the home and `run/` are `0700`;
- `local-token` is created with `os.open(O_CREAT|O_EXCL|O_WRONLY, 0o600)`;
- Core checks the mode at every start, and the CLI at every read. Core **refuses to start** when group or other permission bits are set, with a message saying how to fix it.

**Guarantee, Windows:**
- The default home `%LOCALAPPDATA%\Archeus` inherits the user-profile DACL (the user, SYSTEM, Administrators), so the token can be read only by accounts that can already read the user's profile. That is the whole P3.5b guarantee.
- When `ARCHEUS_HOME` points outside `%USERPROFILE%`, Core starts, and both `archeus status` and `core.log` warn that the token is protected only by that directory's ACL.
- **Not in P3.5b:** writing custom DACLs (security descriptors through `ctypes`) and DPAPI encryption of the token. DPAPI is already sanctioned for API keys (plan §27) and is the documented upgrade path if the user wants the token protected against same-machine administrators. **USER** accepts the minimum.

**Threats and answers:**
- **Loopback is not a user boundary.** Another local user can connect to the port, but cannot read the token, so the token is the boundary.
- **Port squatting.** While Core is down, another user could listen on the stale port. The CLI therefore sends the token **only** when `core.lock` is held and `core.json`'s pid + create_time is alive (§7).
- **Logging.** The request log records the method, the route *template*, the status, the duration and the device id. It never records the `Authorization` header, a query string, or the body of any `/v1/devices/launch/*` request.
- **Crash leftovers.**
  - `core.lock` stays on disk but its OS lock is gone, which is harmless.
  - `core.json` stays but is stale, and is validated by the lock (§7).
  - `local-token` persists on purpose.

### D6 — Legacy CLI verbs

`claude_sessions/cli.py` sends the reserved verbs to `archeus.cli.main` with a lazy import, placed **after** the statusline fast path (migration-plan §3). No verb is currently registered under these names; today they fall through to `main.run`.

| Verb | Treatment | Why |
|---|---|---|
| `core` | **implemented** | starts Core in the foreground (Ctrl+C stops it cleanly). `--port N` overrides the port. `--open` asks the running Core, or the one just started, for a launch code and opens `http://127.0.0.1:<port>/#launch=<code>` |
| `status` | **implemented** | Core liveness only, from the lock, `core.json` and `/v1/health`. It is **not** `CoreClient.status()`, which is the cross-project status of S13 (P4) |
| `pause` | **explicitly deferred (P11)** | a mission-level pause already exists over HTTP, but it does not stop a running execution. A CLI verb named `pause` promises that it does, which only P11 delivers |
| `approve` | explicitly deferred (P9) | approvals |
| `route` | explicitly deferred (P10) | `route why` |
| `estop` | explicitly deferred (P11, and P20 for the Core-less form) | live process control |
| `pair` | explicitly deferred (P15) | pairing and remote access |

A deferred verb prints `archeus <verb> is not available yet (arrives with P<n>); nothing was done` to stderr and exits `2`. It imports nothing beyond the standard library. Reserving the names now means scripts never see a verb whose behaviour later changes from "opened the TUI" to something else.

### D7 — Launch codes

| Aspect | Decision |
|---|---|
| Storage | **in memory only**, in the Core process: `{sha256(code): (expires_at_monotonic, minted_by_device_id)}` behind a lock. Never persisted and never in the database |
| Code | `secrets.token_urlsafe(32)`, placed in the URL **fragment** (`#launch=`), which the browser never sends to the server |
| TTL | 60 s (api-and-realtime §5.1), measured on an injectable monotonic clock |
| Minting | `POST /v1/devices/launch/code`: requires the `admin` scope, a loopback peer and a loopback `Host`. In practice only the local token holds `admin` |
| Redemption | `POST /v1/devices/launch/redeem {code, platform}`: loopback peer, loopback `Host`, fetch-metadata allowlist, and **no bearer token**. The HTTP thread pops the hash atomically under the lock, so only one of two concurrent redemptions finds it. It then generates the token on the HTTP thread and submits **one** writer command that receives only the token's *hash*: principal + Device (PAIRING → ACTIVE via `code_redeemed`) + `tokens` row + its events. The response is `{device_id, token}` |
| Single use and replay | the pop is the use. A reused, expired, unknown or malformed code all get the same `401 invalid_launch_code`, so the answer reveals nothing |
| Idempotency | **exempt.** The response contains a secret, and the writer would store it in plaintext in `idempotency_keys` for 24 h. The command is submitted without a key. If the command fails after the pop, the code is spent and the user opens the SPA again |
| Restart | all outstanding codes are gone (they live 60 s anyway) |
| Logging | neither the code nor the token is ever logged (D5) |
| Reuse by the SPA | the SPA first tries the token it already has (`GET /v1/version`). It redeems a launch code only when it has no token or its token is refused, then removes the fragment with `history.replaceState` |

## 4. Authentication and authorization boundary

The request pipeline is below. The order matters, and each step fails closed.

1. **Host allowlist:** exactly `127.0.0.1:<port>`, which is the one documented origin `http://127.0.0.1:7337` by default (D10, §18.3). `localhost` is **not** accepted: a second origin would mean a second IndexedDB token and a second leader lock. Anything else gets `403 host_not_allowed`. This runs for every path, static files included. It is the DNS-rebinding defense.
2. **Fetch metadata:** if `Sec-Fetch-Site` is present it must be `same-origin` or `none`, and if `Origin` is present it must be an allowed origin; otherwise `403 cross_site`. A request with neither header (the CLI) passes.
3. **No credentials in URLs:** a query parameter named `token` or `access_token` gets `401 token_in_url`, even when a valid header is also present.
4. **Size limit:** a body over 1 MiB gets `413`. A command body that is not JSON gets `400 invalid_request`.
5. **Routing:** an unknown path gets `404 not_found`, and a known path with the wrong method gets `405 method_not_allowed`. Routing comes before authentication so that the static files and `launch/redeem` can be public.
6. **Authentication** for routes that need it: `401 unauthenticated` when the token is missing, malformed, unknown, revoked or expired. It is one code with no reason given, so the answer is not an oracle.
7. **Scope:** `403 scope_required {"scope": "<name>"}`.
8. **Idempotency key** on every command route except `launch/*`: a missing key gets `400 invalid_request {field: idempotency_key}`.
9. **Handler:** body shape validated against the route's schema, then **one** `writer.execute(command, {..., actor})` or one `Database.read()` query.

Every response carries these headers:

```
Content-Security-Policy: default-src 'self'; script-src 'self'; connect-src 'self'; img-src 'self' data:; frame-ancestors 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Cache-Control: no-store        (API and SSE responses; the SPA's hashed assets are cacheable)
```

The P9 boundary is §3 D2's table. The application layer sees only
`actor=Ref('user_device', <principal id>)`, exactly what `InProcessClient` passes today.

## 5. HTTP / Core lifecycle design

### 5.1 The P3.5b route table (the whole of it)

`api/routes.py` is the only route table (api-and-realtime §1). Each row is
`(method, path, handler, scope, idempotent, request_schema, response_schema)`.
- The two schema columns are an addition (§13 A11): the generated TS client needs types, and the route boundary validates body shape against the same schema.
- Schemas are plain dicts in one stdlib module.
- Domain validation stays in the entities.

| Method | Path | Scope | Key | Calls |
|---|---|---|---|---|
| GET | `/`, `/assets/*` | none | – | the built SPA from `archeus/api/static/`, or a plain "SPA not built" page (not an error) |
| GET | `/v1/health` | observe | – | `{core: {pid, started_at, version, schema, ports: "stub"}, engine: {state: running\|idle\|failed, observed_seq, parked: n}}` |
| GET | `/v1/version` | observe | – | `{version, api: "v1"}` |
| GET | `/v1/missions?state=` | observe | – | `queries.list_missions`, filtered by state |
| GET | `/v1/missions/{id}` | observe | – | `queries.get_mission` |
| POST | `/v1/missions` | control | required | `commands.create_mission` |
| POST | `/v1/missions/{id}/pause` | control | required | `Missions.pause` |
| POST | `/v1/missions/{id}/resume` | control | required | `Missions.resume` |
| GET | `/v1/events?after=&limit=` | observe | – | `queries.events` (full envelopes, api-and-realtime §3.4) |
| GET | `/v1/events/stream` | observe | – | SSE (§6) |
| POST | `/v1/devices/launch/code` | admin + loopback | exempt | in-memory mint (D7) |
| POST | `/v1/devices/launch/redeem` | none + loopback | exempt | D7 |
| POST | `/v1/devices/{id}/revoke` | admin | required | a new `revoke_device` writer command, then close that device's streams |

**Routes deliberately absent:**
- cancel, accept and request-changes;
- approvals (P9);
- executions and routing (P10, P11);
- `/v1/now` (P16);
- pairing (P15);
- a device list (P15);
- `/v1/status` (S13, P4);
- the hook routes (P11).

A test pins the table to exactly these rows.

### 5.2 Threads and pools

`api/server.py` uses `ThreadingHTTPServer` bound to `127.0.0.1` with two bounded pools, acquired without blocking:
- **Requests:** 32 slots. When full the response is `503 busy` with `Retry-After: 1`.
- **Streams:** 8 slots, at most 2 per device. When full the response is `429 too_many_streams`.

A stream holds only a stream slot. A request handler waits on its command's `Future` for at most 30 s. On timeout it answers `503 busy`; the command may still commit, and a retry with the same key replays it.

### 5.3 The engine loop

Described in §3 D4. What it records is operational state that `/v1/health` reports:
- `idle`: the last pass made no progress and `observed_seq` equals the head it read;
- `failed`: the engine thread died.

`HttpClient._idle()` counts Core as idle only when `engine.state == 'idle'` and `observed_seq` equals the current head of `GET /v1/events`. This is the HTTP counterpart of `InProcessClient._idle()`, which lets a judge scenario waiting for a state that cannot arrive fail at once instead of after 30 s (§13 A7).

### 5.4 Shutdown (Ctrl+C / SIGTERM / CTRL_BREAK, or engine failure)

1. Set `stopping`. New requests get `503 core_stopping`.
2. Close every SSE stream with an `event: shutdown` frame.
3. Stop the HTTP server.
4. Signal the engine thread and **do not wait** for a running child. The child is detached and gets reconciled at the next start. While stopping, a `WriterClosed` raised in the engine thread is expected, not a failure.
5. `writer.close(drain=True)`: queued commands commit, and handlers already waiting get their answers.
6. Delete `core.json`.
7. Release the lock.

The exit code is 0, or 3 after an engine failure.

**Accepted ceiling:** an execution that finishes during shutdown has its `ended` tombstone but no committed `record_exit`. The next Core reconciles it as LOST and the task runs again. That repeats work, but no two executions of the task ever run at once. P11's collect-on-boot removes it.

## 6. SSE design

### 6.1 Contract

- **Request:** `GET /v1/events/stream`, `Authorization: Bearer`, and a cursor from `Last-Event-ID` or `?after=` (a cursor is not a secret). When both are present, the header wins, because that is how a reconnect carries it.
- **No cursor at all** means start at the current head: live events only, no replay. This is what a client does after a resync.
- **Cursor validated before the `200`:** a malformed cursor is `400`, and one that is `pruned` or `ahead` is `410`, all sent as normal HTTP responses before any stream bytes.
- **Frames:** `id: <seq>\nevent: <type>\ndata: {"subject": {"kind", "id"}, "scope": {"workspace", "project"}}\n\n`. That is **identities only**: no payload, no entity fields. The client re-queries (ADR-0009).
- **Replay:** exactly the events with `seq > cursor`, in `seq` order, read in pages of ≤ 1000 from one short `query_only` snapshot per page (`outbox.events_after`). No transaction is held while waiting.
- **Heartbeat:** `: hb\n\n` every `heartbeat_s` (15 s by default, injectable for tests). A failed write means the client has gone; the thread exits and its slot is released.
- **Retention expiring during a live stream:** a page read that raises `CursorExpired` sends `event: cursor_expired\ndata: {"reason", "floor", "head"}` and closes. The client re-queries its screens and reconnects with no cursor (§13 A10).
- **Visibility:** no filtering in P3.5b. `observe` sees every event, as the in-process binding does, so the two bindings return the same `events()`. `visibility` is a display hint the SPA applies itself (§13 A16).
- **Revocation:** after the revoke commits, the handler closes that device's registered streams before it responds. A stream thread also re-checks its token each time it wakes, so a revocation made any other way closes the stream within one wake.
- **Deferred to P15:** `device.stream_opened` / `device.stream_closed` (presence). Writing an event per connection would also wake every stream once for each connection.

### 6.2 Backpressure

- Each stream writes to its own socket from its own thread, so a slow client blocks only that thread.
- The writer never waits on a reader: it only notifies.
- The stream pool bounds how many such threads can exist (§5.2).

### 6.3 Commit notification (the one addition to P2 infrastructure)

`Writer` gains a `threading.Condition` and a commit counter. It notifies **after** `COMMIT` and
never on a rollback or on an idempotent replay, which rolls back. Stream threads and the engine
thread wait on it with a timeout. This is what api-and-realtime §4 already specifies ("block on an
in-process condition variable that the writer notifies after each commit"). It adds an ability and
changes no existing behaviour. Polling was rejected: it would re-read the head in every stream for
nothing.

## 7. Core lock / discovery design

| File | Content | Written | Protection |
|---|---|---|---|
| `run/core.lock` | empty | opened and locked (`msvcrt.locking` on Windows, `fcntl.flock` on POSIX, both stdlib) **before** `Database.open` | held for the life of the process; the OS releases it when the process dies |
| `run/core.json` | `{pid, create_time, port, started_at, version, schema}` | after the server binds; written atomically (temp file + `os.replace`) | not secret; integrity is checked through the lock |
| `run/local-token` | `dev_…` | first start, or when its hash is missing or revoked | D5 |

- **A second Core is refused.** Lock acquisition is retried for up to 2 s (covering a CLI probe, below). If it still fails, `archeus core` prints `Core is already running (pid, port)` and exits 1, without opening the database.
- **A stale lock recovers itself.** It is an OS lock, not a pid file, so there is never a stale lock to clean up.
- **Discovery (the CLI):**
  1. Try to take the lock without blocking.
     - If the CLI gets it, Core is not running. It releases the lock at once and reports `not running`, sending nothing anywhere.
     - If the lock is held, continue.
  2. Parse `core.json`. If it is missing or malformed while the lock is held, report `running, discovery file unreadable` and send nothing.
  3. Check that the pid is alive with the recorded create_time.
  4. Only now send the local token to `127.0.0.1:<port>`.
  
  This closes the port-squatting case (§13 A5). The probe races with a Core that is starting, which is why Core retries the lock.
- **Port:** a fixed default, overridable with `--port` or `ARCHEUS_PORT`.
  - It must be fixed because the browser origin includes the port. With an ephemeral port the SPA would lose its IndexedDB token and its leader election on every restart, and mint a new device each time (§13 A8).
  - The port is **7337** (D10, accepted). The legacy GUI and gateway use an ephemeral port (`make_server(port=0)`) and failover profiles start at 20129, so nothing collides.
  - If the port is in use, the message names the port and the override, the process exits 2, and no `core.json` is written.
- **Who takes the lock:** the Core runtime **and `InProcessClient._core()`**, through one shared function. Two hosts on one home, for example a judge test mixing bindings, therefore fail loudly instead of running two engines. A structural test lists the callers of `Database.open` and of the `Engine(` constructor.

## 8. CLI boundary

`archeus core` and `archeus status` are the only working V1 verbs (D6). `status` prints:
- whether Core is running (from the lock), with pid, port, uptime and version;
- the schema version and the engine state from `/v1/health`;
- the ports label `stub` (§13 A12);
- the ACL warning when it applies (D5).

It exits 0 when Core is running, 1 when it is not, 2 when discovery fails, and 3 when the engine has failed.

**Statusline fast path:** `cli.py` keeps the statusline dispatch first. The V1 dispatch is a lazy import after it, and a test asserts that no `archeus` module is in `sys.modules` after the statusline path runs. That is a structural check, not a timing one, so it is deterministic on CI.

The CLI talks HTTP only (ADR-0002). It never calls `Database.open`.

## 9. SPA boundary

- **Location:** `clients/app/`, built by Vite into `archeus/api/static/`, which is git-ignored (see §16 on `.gitignore`).
- **Pages:** exactly two lists, **Now** (missions not settled) and **Work** (all missions), both from `GET /v1/missions`.
- **Live updates:** one SSE stream, owned by the leader tab. Any `mission.*` event re-fetches the list.
- **State shown:** the state field as Core returns it, with no state computed on the client.
- **Banner:** "walking skeleton: fake harness, stub policy" whenever `/v1/health` says `ports: stub`.
- **Read-only.** There are no commands, because the launch device is `observe`-only.
- **No inline script and no inline handlers,** so the CSP needs no `'unsafe-inline'`.
- **Not the P16 information architecture:** no `nav/destinations.ts` table, no inspector, no design-token pipeline. Those arrive with P16. The P3.5b SPA is disposable.
- **Generated client:** `clients/app/src/api/generated.ts` and `docs/architecture/api-reference.md` are generated from `routes.py` by a Python tool. Their freshness is checked in the **Python** job (no Node needed). Output is deterministic: sorted, with no timestamps.
- **CI:** a new `v1-client` job runs `npm ci`, `npm run build` and `npm audit` (plan §27), then the Playwright skeleton test. The test must report that at least one test ran, since a suite that collects nothing reports success. The Python job stays Node-free.
- **Packaging:** the wheel ships only built static files, never `node_modules`, sources or maps. `package-data` needs a nested glob, because this repo has already shipped an empty directory from a glob that did not recurse.

## 11. Invariants (P3.5b)

These are the P3.5b invariants. The accepted P3/P3.5a invariants are listed separately in §1 and all still hold.

1. **One writer per home.** The OS lock is taken before the database opens. No process without the lock opens the database for writing.
2. **One engine per home.** It is built only by the lock holder and never re-created within a process.
3. **The API cannot mutate the domain directly.** Its only mutation path is `writer.execute(<application command>)`, so the single `Missions._fire` path, the guards, plan-in-force protection, the verification and review rules and DENY-before-writes are reached only through the commands that already enforce them.
4. **The API makes no domain decisions.** It never evaluates the Policy port, never branches on `actor.kind`, and never decides whether a trigger may fire. That stays P9's.
5. **Authentication is required** on every route except the static SPA files and `launch/redeem`, which authenticates by its code.
6. **Scope checks come first.** The Host check, fetch-metadata check and scope check complete before any command is submitted or any query runs. A refused request writes nothing.
7. **Secrets never land in a URL, a log line, an event, `idempotency_keys` or `core.json`.** The database stores only hashes. The one plaintext secret at rest is `run/local-token` (D5).
8. **The event stream carries identities only.** Replay is exact (`seq > cursor`, in order, no gaps, no duplicates). `seq` increases monotonically across restarts.
9. **A cursor that cannot be honoured is refused.** Before a stream starts it gets 410 or 400; during a stream it gets an explicit `cursor_expired` frame. The stream never skips events silently.
10. **Commands are idempotent by key.** A repeated key replays the stored response. A different request under the same key is refused. Concurrent duplicates run once, because the writer serializes them.
11. **A restart reconciles and never adopts.** An execution's attempt ends before the task gets a new one. No two executions of a task are live at once.
12. **Nothing with a side effect runs inside a transaction.** No spawn, engine step, brain call or network write happens inside a writer command, and no transaction is held while a stream or the engine waits.
13. **Streams cannot starve commands.** They use a separate bounded pool. The writer never waits on a reader.
14. **Both bindings keep one contract.** `HttpClient` and `InProcessClient` implement the same operations with the same results and the same `(status, code)` errors.
15. **No real model, provider or network call.** Only the fake harness runs. The adapter registry's stub gate is unchanged.

Refinement of an existing invariant:

"`resume` reads `held_from`, and the engine is the only thing advancing a mission" becomes "the engine is the only automatic stepper. A user command may move a mission between an engine read and an engine fire, and the guards refuse the engine's stale move (§3 D4)."

This is a clarification, not a change. P3.5a already fired every move through a version-checked, guarded primitive; only now does a second thread exist to race with.

## 18. Decision pass (2026-09-24)

### 18.1 D8: Core ownership vs process registry vs adoption vs output observability

**Four different things that the earlier text ran together:**

| Concept | What it is | Artifact / state | Phase |
|---|---|---|---|
| **Core ownership** | which process is *the* Core for a home: the only writer and the only engine | `run/core.lock` (OS lock), `run/core.json` (discovery) | **P3.5b** |
| **Execution process registry** | a database-free list of every process Archeus spawned, so that tools **without the database or without Core** can find and kill them | `run/processes.jsonl` `{execution_id, pid, create_time, argv0, started_at}`, tombstoned on exit (execution-architecture §4) | **P11** (its consumers: `archeus estop` with Core down, P11/P20) |
| **Live-process adoption** | a restarted Core re-attaches to a still-running child (pid + create_time match, `stream.jsonl` still growing) and resumes tailing from a recorded offset, instead of killing it | an offset per execution plus the adopt branch of boot reconciliation | **P11** (ADR-0008's target; the plan schedules it in P11) |
| **Output / stream observability** | (a) the **read primitive**: `base.read_stream(path, offset)` and `adapter.inspect()`; (b) **live tailing**: incremental reads while running, a stored offset, `execution.progress` events, pressure from usage; (c) the **client route** `/v1/executions/{id}/stream?from=` | (a) exists since P1/P3.5a; (b) execution-manager state; (c) an API row | (a) **exists**; (b) **P11**; (c) **P16** |

**What each P3.5b activity needs:**

| Activity | Core lock / discovery | Process registry | Live tailing | Stream route |
|---|---|---|---|---|
| Core startup | **yes** | no | no | no |
| Core shutdown | **yes** (release) | no | no | no |
| Core crash recovery | **yes** (the OS releases the lock) | no | no | no |
| Execution reconciliation | yes: it guarantees no other engine owns the children | **no** | **no** | no |
| HTTP observability (missions, events) | no | no | no | no |
| SSE (domain events) | no | no | no | no |
| SPA (Now/Work lists) | no | no | no | no |

**Q5 — can P3.5b reconcile without the registry?** Yes.
- The database is a complete list of every execution that may have a process, because of an accepted P3.5a invariant: **an Execution row is committed in INTENT before any process exists** (`dispatch_task` commits, then the engine spawns).
- So, for a Core that has its database, the non-terminal `executions` rows are a superset of what the registry would list.
- The registry adds value only where the database is unavailable or Core is down, which is exactly P11/P20's e-stop.

**Q6 — can it reconcile without stream tailing?** Yes.
- Reconciliation *ends* the attempt (ABANDONED, or LOST → ENDED_KILLED) and retries the task with a new execution.
- It never reads the output.
- Only adoption needs to know whether `stream.jsonl` is growing and where to resume.

**Q9 — the exact state P3.5b inspects** to reconcile a dead Core's execution (P3.5a's `Engine._reconcile`, unchanged but for the recycled-PID fix in 6):
1. the `executions` row: `state` (not in `states.terminal('execution')`), `harness_id`;
2. `run/exec/<id>/spawning`: whether a spawn was attempted;
3. `run/exec/<id>/pid.json`: `{pid, create_time}`;
4. `run/exec/<id>/ended`: the tombstone;
5. the live process check: `proc.process_create_time(pid) == create_time`;
6. the kill: `adapter.stop(handle)`, which is `proc.kill_pid_tree(pid, create_time)` and refuses a recycled pid. A recycled PID is treated as the process having exited; nothing is killed. (`_reconcile` catches `StopRefused` and continues to LOST → ENDED_KILLED, `exit_reason: lost`.)

It never reads `processes.jsonl` and never reads `stream.jsonl`.

**Q7 — a P3.5b acceptance scenario that needs either abstraction?** None.
- H1/H2 (kill mid-execution, restart, reconcile, no duplicate) need only the state above.
- G1–G6 need only the lock and discovery file.
- The SK judge asserts `execution.started` with a pid, which is a domain event.
- No P3.5b route exposes execution output.

**The review found one real P3.5b gap, and it is neither abstraction (A35):**
- P3.5a reconciles lazily, inside `Engine._execute`, and the engine only steps missions not in `SETTLED`.
- A mission paused over HTTP while its execution runs (`pause` is a P3.5b route, and pausing a mission does not stop its execution) is PAUSED, which is settled.
- If Core is killed then, the restarted engine never steps that mission, so the orphan child is **never reconciled until the user resumes**. The execution row stays STARTING/RUNNING and the process runs on.
- The minimum seam is a **boot reconciliation sweep**: before the engine loop starts, the Core runtime calls `Engine.reconcile_orphans()`. That reads every non-terminal `executions` row and applies the existing `_reconcile` to each one this engine did not start. At boot that is all of them. It is the same kill-and-retry semantics, applied to every mission instead of only stepped ones. (A task reconciled under a PAUSED mission becomes READY and is dispatched after `resume`; the mission itself is not moved.)
- Until the sweep finishes, `/v1/health.engine.state` reads `reconciling`.
- This is reported here and is **not** fixed in P3.5a.

**Q8 — dependency inversion if "stream tailing" moved to P16?** Yes, if the *mechanism* moved.
- P11 adoption resumes from a recorded offset.
- P12 hand-off reads pressure and usage from the live stream.
- Both precede P16, so a P16-owned tailer would make P11 and P12 depend on a later UI phase.

**Final D8 split, with no inversion:**
- **P3.5b** keeps the read primitive as it is (`base.read_stream`, `adapter.inspect`, used at exit by `record_exit`).
- **P11** owns the registry, live tailing with a stored offset, `execution.progress`, and adoption. The P3.5b boot sweep becomes P11's "adopt or reconcile" by adding the adopt branch.
- **P16** owns only the client route `/v1/executions/{id}/stream?from=`. It must read **through** `adapter.inspect` / `base.read_stream` (P11 by then), never parse `stream.jsonl` itself.

Arrows then run P1/P3.5a → P11 → P16 only.

**Interfaces fixed at the boundary:**

| Seam | Owner | Consumers |
|---|---|---|
| `Engine.reconcile_orphans() -> list[execution_id]` | P3.5b (additive over P3.5a) | Core runtime at boot; P11 adds the adopt branch behind the same call |
| `base.read_stream(path, offset) -> (events, new_offset)`, `adapter.inspect(handle) -> Snapshot(events, offset)` | P1/P3.5a | `record_exit` (P3.5a); P11 tailer; P16 route |
| `paths.processes_registry()` | P1 (path only; nothing writes it) | P11 supervisor writes, P11/P20 `estop` reads |

**A36, a documentation contradiction reported, not fixed:**
- execution-architecture §3.1, the process I/O contract "frozen in P1", says of `pid.json`: "also appended to `run/processes.jsonl`".
- `base.spawn` (P1/P3.5a) has never appended it, and no test asserts it.
- The contract text is ahead of the code.
- By D8 the append belongs to P11's supervisor. §3.1 is amended at implementation to say so; the code is not changed.

**The plan's "minimal local node"** (P3.5: "supervisor + process registry + stream tailing") is, for P3.5b:
- the Core-hosted engine thread;
- the existing adapter registry and process I/O files;
- the boot sweep.

The plan P3.5 text is amended to match (§15).

### 18.2 Static assets and `.gitignore`

1. **Why `archeus/api/static/` exists.** Core serves the built SPA from its own package (ADR-0011: "web serves it from Core"; ui-architecture §2: Vite `outDir` is `archeus/api/static`), and the wheel must carry it because Node is never a runtime dependency (ADR-0003).
2. **Source-controlled or generated?** Generated. The source is `clients/app/` (tracked). The output is produced by `npm ci && npm run build` and is never committed (ui-architecture §2).
3. **Exactly which files are generated** (Vite, with `outDir: ../../archeus/api/static`, `emptyOutDir: true`, `sourcemap: false`, `assetsDir: 'assets'`):
   - `archeus/api/static/index.html`;
   - `archeus/api/static/assets/*.js` and `*.css` (content-hashed);
   - anything in `clients/app/public/`, copied to the root of `static/`.
   
   Separately, `clients/app/node_modules/`.
4. **Exactly which files are ignored.**
   - `archeus/api/.gitignore` containing `/static/`, and `clients/app/.gitignore` containing `/node_modules/`.
   - Both are **scoped to their own directory**, like the existing `www/.gitignore`, rather than a broad root rule.
   - A nested `.gitignore` inside `static/` itself is rejected, because `emptyOutDir` deletes it on every build.
   - `archeus/api/.gitignore` does not ship: package-data names only the static globs.
5. **Is the existing three-line root `.gitignore` change correct?** Correct for its own purpose and unrelated to P3.5b.
   - It ignores `docs/architecture/reference` (a slash in the middle makes the pattern anchored), which holds the three untracked source documents the user chose to keep out of git.
   - One defect: the file has **no trailing newline**. Any tool that appends a rule without a leading newline would produce `docs/architecture/reference<next rule>` and silently break both.
   - P3.5b needs no root change, so it stays the user's to finish and commit. It stays untouched.
6. **Does package-data need the files in the source tree?** Yes. setuptools copies package-data files that exist at build time, and **a glob that matches nothing is silent**: the wheel simply lacks the SPA (the repo's skills-templates lesson). So the SPA must be built before `python -m build`.
7. **How the wheel test proves the assets are present:**
   - The CI `package` job and `release.yml` each gain `setup-node`, then `npm ci`, then `npm run build` in `clients/app/`, **before** `python -m build`.
   - The existing installed-wheel step then reads `archeus/api/static/index.html` out of site-packages. It parses every `/assets/…` reference and fails when any referenced file is missing.
   - It also fails if the wheel contains a `.map`, a `.ts`/`.tsx` source or anything from `node_modules`.
   - The Node-free `test` job keeps `test_every_declared_glob_matches_at_least_one_file`, with a **scoped exemption** `GENERATED_GLOBS = {'archeus.api': ('static/*', 'static/assets/*')}`, bounded by two assertions:
     - every exempt path is ignored by git (`git check-ignore`);
     - the exemption lists nothing else.
   
   A generated glob can therefore never hide a hand-written file that failed to match.
8. **A staging step instead of an in-tree ignore?** Considered and rejected for P3.5b:
   - Mapping a data package onto `clients/app/dist` with `package-dir` gives an installed layout different from a source checkout. Core would need two ways to find its static files (one for dev, one for installed), which is the tested-tree ≠ shipped-tree hazard this repo keeps paying for.
   - It would also fail `test_the_declared_packages_are_exactly_the_packages_on_disk`.
   - A copy step (`dist` → `archeus/api/static` before the build) still puts files in the package tree, so it still needs the same scoped ignore, and adds a step.
   - In-tree output with a scoped ignore is the smallest correct design.
   - A dev checkout without a build serves the "SPA not built" page (§5.1), not an error.
