## Findings

1. **Low (non-blocking; suggested).** tests/v1/integration/test_p20_secrets_runtime.py:10-18 and the rig fixture :116-134. The rig execution writes no core.log, so the execution lifecycle's logging is not at rest anywhere the gate reads.

   - In a real Core, ExecutionManager runs in-process and anything logged on `archeus.core` lands in logs/core.log (runtime.py:522-528).
   - Reproduced (X3): `logging.getLogger('archeus.core').info('hook %s', token)` after the draw in `_spawn` survives both gates (static 7 passed, runtime 2 passed). With the module's own `log.info('hook %s', token)`, the census catches it (X3b), so only the inline-logger form slips through. That form has no call site today.
   - Change: in the rig fixture, attach a `logging.FileHandler(<home>/logs/core.log)` on `archeus.core` (what `Core._open_log` does), and remove it on teardown. Or say in the docstring that the execution's log lines are the census's to see.

3. **Low (non-blocking; recommended, from T-107).** test_p20_secrets_runtime.py:93 and :104. The PIN sent at pairing (`'482913'`) is not in `found`, so a plaintext PIN at rest is invisible to both gates.

4. **Low (non-blocking; suggested).** test_p20_secrets_runtime.py:80-81. `except OSError: continue` ("a file that went while walking") also skips a file that exists and cannot be read, so the scan fails open on it.
