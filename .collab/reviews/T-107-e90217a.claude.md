Findings:
1. Medium, required. A replayed re-arm says `{"armed": true}` while Core is disarmed. A busy retry of a re-arm that has committed now leaves Core disarmed.
   - On a replay, `rearm` returns the stored answer as it is (routes.py:645-646). The stored answer is `{'armed': True}` (executions.py:578). J04 asserts exactly that body next to `_armed(remote) is False` (test_presence.py, J04), so the test locks in an answer that is false.
   - The same path breaks a legitimate retry. Probe P1: a paired client e-stops, and its re-arm (right PIN, key K) gets `503 busy` because `command_timeout` fires (TimeoutError maps to busy, server.py:163). The command commits afterwards. The client retries with K, which the SPA does by itself (`retryable` covers busy and core_starting; `keyAfter` keeps the key after a network outcome).
     - d6877a2: retry `200 {"armed":true}`, Core armed, one core.rearmed.
     - e90217a: retry `200 {"armed":true}`, **Core still disarmed**, one core.rearmed.
     - So the event log says re-armed, the sentinel says disarmed, and the client is told armed. A Core restart between the commit and `clear_estop` ends in the same state.
   - Every outcome leaves Core disarmed, so this fails safe, but the false answer is on the safety control. `estopSaid` (clients/app/src/state/present.ts) shows "Re-armed: Core accepts new work again." with `when: true`. Its own "Core answered, but it is still disarmed." branch, the one made for this state, never fires.
   - Fix (one line, same pattern as the e-stop route's `dict(out, armed=False)`): on a replay, return `dict(out, armed=not LocalNode.disarmed())`, and J04 asserts `{'armed': False}`. The client then gets a true answer, and its next press uses a new key and asks for the PIN again.
   - Getting back the busy-retry behaviour as well (clear the sentinel on a replay only when no `core.estopped` committed after the stored re-arm) is optional and the owner's call. It is not needed for (4) as accepted.
2. Low, required (test gap). Nothing tests that a replayed re-arm leaves the strike count alone, and that is the property that keeps leaving the PIN out of the hash safe.

It is an unbounded PIN search for whoever holds the device token and one used key. As built, the 5th wrong PIN revokes the device (the 6th request gets 401). The code is right; only the test is missing.

3. Low, doc (audit accuracy; nothing to change in code for T-107).

     - What actually guards them is `_launch`'s `launched_seq >= launch_seq` (sessions/service.py:177). It holds for sequential replays, so the card's conclusion stands there.
     - It is check-then-act, though. An original and a same-key duplicate in flight at the same time can both pass it before either records `launched`, which would open two terminals. Not probed. This is older code that T-107 did not change.
   - (b) A replayed e-stop is a full stop in effect, not just the sentinel.
     - The manager stops live executions on its next tick (execution/manager.py:510), and the engine dispatches nothing while disarmed (engine.py:184, 255).
     - It records no second `core.estopped`, blocks no mission, and its `stopped` list is the original's. `armed: false` is still true because the route overrides it.

On the questions asked:
- **Is the replay signal reliable?** Yes, on every path checked:
  - Writer: it is serial, so a same-key duplicate in flight always sees the committed row. Probe P2: 4 concurrent same-key re-arms gave 4x 200, one core.rearmed, armed.
  - Core restart: the row is in SQLite, so a replay is still recognised.
  - `fut.replayed` is assigned before `set_result`, and server.py reads it only after `result()` returns, so never after an exception.
  - Bindings: the only product request object is `server.Handler`. `InProcessClient` is the judge's test binding. It calls `writer.execute` directly, has no re-arm op, sends the e-stop unkeyed, and has no strike counter, so there are no route effects to diverge.
  - Two small points about `Handler.replayed`: it is never initialised, and it survives across keep-alive requests. No route reads it before `run` sets it in the same request, so neither matters.
  - The weak point is not the signal. It is the assumption that the original's route effects ran, which is finding 1.
- **Is the route audit complete?** Every `req.run` route and the session service were read.
  - The ones with effects outside the writer are estop, rearm, post_message (decision), decide_approval, revoke_device (`close_device`), `_step_up_failed` (unkeyed), register_account, set_account_state and set_resource_policy (the probe is a read), import_meeting (a content-addressed `artifacts.put`), and create/resume/handoff session (`_launch`).
  - No route repeats a side effect on a replay that the card missed. Finding 3 corrects two of the stated reasons.
- **Should a replayed e-stop re-engage the sentinel?** Yes. It fails safe, and as 3(b) shows it is effectively a full stop.
- **Should a replayed decision leave the strike count alone?** Yes, and that change is required by (5), not just tidy. Once the PIN is out of the hash, a replay checks no PIN, so a reset on a replay would let anyone holding the device token and a used key reset the breaker between guesses (see finding 2 for re-arm).
- **Which fields are kept out of the hash?** `PROOF_ARGS = {'step_up'}` only, and that is complete. It is the only proof that reaches a keyed command. Pairing and launch codes, the PIN at pairing, and new tokens all go through `keyed=False` commands, and only as a pbkdf2 record or a sha256 of a 256-bit token. No other route argument is secret.
- **Can a used key with a different PIN unlock anything?** No. It returns the stored answer, but only to the same principal: the actor `Ref` (one principal per device, commands.py:136) is in the hashed arguments. Probe P3: another paired device reusing the key gets `400 invalid_request` (conflict), and Core stays disarmed. The replay runs nothing, checks no PIN, and neither counts nor resets a strike. Its answer is one that device already received, so it authorises nothing and leaks nothing, apart from the stale `armed` in finding 1. It also closes the old oracle, where a wrong PIN got 409 and the right one 200. The key is client-random, and it is bound to the device through the hash, not through the key column.

- **Is the 10^6 test real?** Yes. It is an exhaustive search over all 10^6 six-digit PINs, and it catches R2.
  - Its positive control shows the template is string-identical to the old blob for the real PIN. That is enough to show a hit would have matched, though it never runs one.
  - A cheaper and stricter assertion would be `stored == request_hash(name, args without step_up)`. Optional.
