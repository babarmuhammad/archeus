Review of T-101 at f357434 (detached checkout D:/archeus-p20-mcp, on top of b2dbf4c). Read-only on product code. The bug is real and the fix works. On b2dbf4c a user's stop, stop_mission or e-stop on a halted execution that has run raises NotPermitted; on f357434 it succeeds, and `core.estopped` is recorded in the same transaction. A user actor cannot exploit the change today: it chooses only which execution ends, and the session's content is all fields Core recorded, identical to what Core writes when it ends the same execution itself.

The elevation is not scoped to the stop, though. It sits in `_finish`, which every end path shares, and it removes a fail-closed that the other end commands relied on. The tests also do not pin who is recorded as the actor.

The questions asked:
- Can a user actor make Core write something on its behalf beyond the session? Not through any route. The user-reachable commands that reach `_finish` are stop_execution, stop_mission and estop (`_user` / `estop`'s own check; brain and system are refused by E23). They reach it only through `refuse` → `discarded`, so only for a PAUSED or AWAITING_APPROVAL execution with process_seq >= 1 and no session. The user supplies only the id. The four system-attributed writes are:
  - the Session insert,
  - `session.created`,
  - the close transition,
  - `Execution.session_id`.
  Their content is all Core-recorded fields: the mission's workspace and project, the workdir, account, model and effort, and `adapter_state['session']` from Core's own `record_end` at the halt. The session is closed in the same transaction, and `resume` refuses a headless session (sessions.py:246). If no system principal exists, `Ref('system', None)` makes `writer.insert` raise (`ids.is_id`), so it fails closed.
- Is it scoped to exactly the stop/e-stop of an AWAITING_APPROVAL execution? No, on both counts:
  - In code, every non-Core `_finish` writes as system (finding 1).
  - In reach, it covers a stop, stop_mission or e-stop of a PAUSED or AWAITING_APPROVAL execution. That is wider than the card names, but it is the same bug, so correct (finding 2 asks for tests).
- Would not creating a session on a stop be narrower? Not in effect, and I would not take it:
  - It breaks D5 (p12-design-gate §6): every end of an execution that ran leaves its headless session and checkpoint.
  - The record would depend on who ended the execution. Core's own `_awaiting`/`_paused` refuse writes the session as system; a user stop would not.
  - It drops process 1's provider session ref, which is Core's only record of it.
  The narrower fix is the scoped substitution in finding 1.
- Does the audit trail still name the user? Yes, by reading and by probe:
  - `refuse` fires `discarded` with the user, and `execution.ended`, `_respond` and `_block` also carry the user.
  - `core.estopped` is `Ref('principal', actor.id)` with the user as actor (probe: kind user_device, id == x.user.id).
  - Only the four session writes are system.
  Nothing pins this yet (finding 2).
- `core.estopped` in the same transaction: yes. It is appended after the stops in `estop()`, in the one writer transaction, and the test asserts `killed == [e.id]`.
- Claude adapter: read, not run. adapter.py:241 returns `adapter_state={'session': session}`, and `Execution.session_id` is set only by sessions.py:135, so the adapter takes the same path. Confirmed.
