## Q1 — Atomic claim; one terminal for concurrent resume/hand-off/new launch; replay opens nothing; fresh key still launches

Atomic. `_launch` reads `s.launch_seq` outside the writer (`self._session`), but the decision
itself is made inside `claim_launch`, a single writer command (`archeus/core/application/sessions.py:213`):
it reloads the Session fresh from `tx` and checks
`launch_seq != s.launch_seq or max(s.launched_seq, s.launch_claimed_seq) >= launch_seq`. The
writer runs one command at a time (stated in the module docstring and consistent with every
other command in this file), so two concurrent `claim_launch` calls for the same `launch_seq`
serialize: the first sets `launch_claimed_seq = launch_seq` and wins, the second reloads the
now-updated row and loses (`max(... , launch_claimed_seq) >= launch_seq` is now true). This is
the right fix for the root cause the T-113 probe found: the old guard
(`s.launched_seq >= s.launch_seq`) was a stale read-outside-the-writer, check-then-act race;
moving the check-and-set into one writer transaction removes the window entirely, regardless of
how the two callers got into `_launch` (writer-level idempotency-key replay returning the same
`duplicate: False` payload to both racers, two distinct resume calls, or two hand-off calls each
creating their own session and separately winning their own claim).

Traced `register→launch`, `resume`, and `handoff` — all three route through the same `_launch`,
so "new launch" is covered by the same mechanism, not a special case.

A replay (T36): `S.resume`'s own idempotency (`s.last_request == request_id` → `duplicate: True`)
already short-circuits before `_launch` is reached for a true replay after the first command
committed; verified by test and by reading `resume()` (`archeus/core/application/sessions.py:248-281`).
A fresh key/request_id (T36's `r2`/`k2`) bumps `launch_seq` again and launches normally — the
claim only ever blocks a *second claimant of the same launch_seq*, never a new one.

Ran `test_T35_two_concurrent_requests_with_one_key_open_one_terminal` for both `resume` and
`handoff` params, 3 total runs (27-test file run once, then the T35/T36/T37 slice run twice
more) — all green, no flakes. The test uses a real `threading.Thread` pair plus a
`SlowTerminal` that sleeps 0.2s inside `open_terminal` to widen the window the old code raced
in, which is the right way to make this race observable.

**Judgement: sound.**

## Q2 — Crash between claim and terminal; any session claimed forever and unlaunchable

Not possible. `expire_launches` (`archeus/core/application/sessions.py:231`) keys off
`s.launch_seq > s.launched_seq` only — it does not look at `launch_claimed_seq` at all, so a
claimed-but-never-launched row is caught by exactly the same boot sweep that already handled an
*unclaimed* unsettled launch: it sets `launched_seq = launch_seq` and `launch_error =
'launch_expired'`. Since `launched_seq` moves forward, the next `claim_launch` for a *new*
`launch_seq` (from the next resume) sees `s.launched_seq < new launch_seq` and wins cleanly —
nothing about `launch_claimed_seq` staying behind at the old value matters, because the
`launch_seq != s.launch_seq` term in `claim_launch` and the `max(...)` term are both evaluated
against the *current* `launch_seq`, which has moved on.

T37 exercises exactly this: claim without a terminal, construct a fresh `SessionService` (crash
simulation), `sweep()`, assert `expired == [session]` and `launch_error == 'launch_expired'`,
then resume again and assert a terminal opens. Ran green, repeatably.

**Judgement: no stuck-forever state. Sound.**

## Q4 — Authority (who may claim) consistent with resume/hand-off

`claim_launch` calls `_core(actor)`, the same system-only guard used by `launched`, `observe`,
and `expire_launches` — all of which, like `claim_launch`, are called with `self.system` from
`SessionService`, never with the end-user actor. `resume`/`handoff` themselves still gate on
`_user(actor)` as before; the claim is an internal step `_launch` takes on the system's behalf
after a user-authorized command already succeeded, not a new entry point a user calls directly.
No authority surface was added or changed.

**Judgement: consistent. Sound.**
