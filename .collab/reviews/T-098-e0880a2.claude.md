## Q2. Is the e2e a real gate for Control's use of the rule? Does forwarding without the PIN mask anything?
It is a real gate for Control.
- The stub changes one field of Core's own `/v1/sync` answer. That is the same path Estop reads (`useRead<Sync>(paths.sync())`, Control.tsx:917). The test's positive control is the PIN field appearing, and that field renders only when `stepUp === 'pin'`. So the stubbed value demonstrably reaches Estop.
- From there, a Control that dropped or weakened the rule fails one of these checks:
  - Empty field: Re-arm must be disabled and the section must show "Enter this client’s PIN first.", text that only the rule produces.
  - Five digits: Re-arm must be disabled.
  - Six digits: Re-arm must be enabled, which catches a rule that is always on.
  - The PIN must be sent: `sent == ['482913']`, read from the actual request body under the key `step_up`.
- The stubbed value matches reality. A paired device with a `pin_hash` gets `'pin'` (queries.py:137), and test_unification.py:188 shows a real paired page offering the PIN field from Core's real answer.
- Forwarding to the local Core with `step_up` popped is necessary, not masking. That Core knows the browser as local, and a local client that sends any `step_up` is refused (earlier review 7(a)). What the e2e does not exercise is Core's judgement of the PIN through the remote host. That half is covered at the HTTP level by J01-J03b (the `remote` fixture, a real paired token, the real PIN route), which pass. The request shape the SPA sends (`{idempotency_key, step_up}`) is the shape J01-J03b send. Nothing material is masked.
- Not covered by the e2e: clearing the PIN after a network failure, which follows from the code path above, and Re-arm for a `'none'` client, which only the node case covers through the helper. Neither is a defect.
