## T-113 (a) — simulate on a no-owner Core

`archeus/core/application/authorization.py`: `_simulated_rule` takes a `standin` id
(`ids.new_id('user')`, generated once per `simulate()` call, shared across all of that call's
extra rules) and uses it for `scope_ref` only when no real owner exists — exactly
`create_rule`'s own branch (`_owner_id`: makes a real `User` and uses its id when none exists).
`simulate` then sets `ctx['chain']['USER'] = ctx['chain']['USER'] or standin` — a no-op whenever
a real owner exists (chain['USER'] is already that owner's id, truthy), so the fix changes
nothing on an existing-owner Core.

**Security check (simulate must never be more permissive than create_rule):** `_on_chain` in
`archeus/core/policy/engine.py` only matches a rule when `scope_ref == chain.get(level)`.
`standin` is a fresh random id touched by nothing else in this call — no persisted rule can have
that `scope_ref` (any persisted USER-scope rule implies `create_rule` already ran, which implies
a real owner already exists, which is the branch this fix does not touch) — so the only rule
that can ever match on `standin` is the simulated one(s) in this same call, matching what a real
request would see immediately after `create_rule` ran. `ctx` is local to the `simulate()` call
and never persisted or returned (the response is built from `_slim(r)` plus `matched_rules`/
`policy_version`/`mission_id`; `ctx['chain']` is not in it), so no state and no information
about `standin` leaks. New test `test_H04c_...`: compares simulate's answer on a no-owner Core
against the answer after the same rule is actually created, both DENY — passed.

## T-113 (d) — spawn failure class

inserted before the existing `except base.SpawnFailed as err: self.isolation.note_failure(...)`.
`SpawnWriteFailed` is a subclass of `SpawnFailed` (`archeus/harnesses/base.py:263,267`), so

`isolation_failed` too would make the registry and the database disagree on why the execution
